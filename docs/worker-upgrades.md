# 节点组件版本与升级管理

Worker 0.21.16 引入控制面过载重试：日志、回合、普通服务健康、产物和完成上报遇到暂时过载会保留数据并返回续租循环。协议版本仍为 18，不改变业务 SDK 正文或镜像。本机平台曾在 2026-11-23 通过受控升级将六台机器、13 个卡位升级到 0.21.16，并在回连后启用双 API 背压；之后又升级到下述 0.21.17。其他部署须先升级并验证目标 Worker，再启用 `DB_BACKPRESSURE_ENABLED=1`，否则旧 Worker 可能把新增的 503 当作执行异常。API 开关默认关闭，回滚 API 时可以保留新版 Worker，不能删除恢复 journal 或在运行中直接替换代码。

Worker 0.21.17 将空闲领取的单次退避总等待限制为 3 秒（包括服务端 `Retry-After`），持续重试且不设次数上限；协议仍为 18。对应 API 将无候选任务的轮询改为只读路径，候选遇调度锁忙返回本轮无任务。本机已先更新 API，再通过版本升级入口逐台将六台机器、13 个卡位升至 0.21.17；未升级的 0.21.16 仍可使用 API，但领取临时故障可能按较长 `Retry-After` 等待。本机上线结果以[双进程验证记录](validation/split-control-api-process-20261123/README.md)为准。

宿主机登录环境来源与客户端逐回合启动需要 Worker 0.18.0 / 协议 15。控制端在模板准入和调度时检查协议；旧节点继续运行旧模板，不能领取使用新字段的模板。发布包随控制端包含新的 `runner/host_episode.py`，节点升级后按每卡回连的软件版本、协议与摘要确认生效。操作与现场验证边界见 [宿主机执行](host-execution.md)及[验证记录](validation/host-shell-episode-launch/README.md)。

入口：管理设置 → 机器管理 → 查看配置 → 版本升级 → **节点组件版本与升级（Worker / Runner / Agent）**。

软件版本、协议版本和发布摘要分别展示到每个 GPU 实例。`worker/version.py` 是开发维护入口：`SOFTWARE_VERSION` 标识软件发布，`PROTOCOL_VERSION` 表示通信能力，`CAPABILITIES` 描述功能。协议版本并非可编辑的节点配置；升级应更换实际程序，不能手工修改数据库版本号。旧 Worker 未报告软件版本时显示“未知”，不根据协议号推测。

## 操作流程

1. 管理员点击“发布控制端随附节点组件包”。平台从控制端已部署的 worker/runner/node_agent Python 源码生成不可变发布包，用 SHA-256 标识内容；相同包重复发布返回同一记录。软件版本由开发发布定义，管理员选择发布包。
2. 确认目标节点所有 GPU 在线、独立升级执行器在线，选择目标版本并点击“排空并升级此机器”。
3. 节点停止接新任务，未领取预留回到队列；正在执行的任务继续续租、上报和清理。持续运行的推理服务会阻止排空，需要管理员先停止它们。
4. 全机排空后执行器取得安装许可，停止配置的原 Worker 单元、检查本地锁与所有恢复 journal、校验并展开发布包，然后替换代码并重启原单元。
5. 平台等待该节点**所有原 GPU 实例**回报目标软件版本、协议、能力和发布摘要，才确认成功并恢复接单。原来的节点停用状态不会被升级自动改为启用。

支持选择历史发布包作为目标进行受控回退；它仍需要当前 API 能兼容目标协议。发布包包含 Worker、Runner 与节点 Agent Python 程序；Agent 仅在升级执行器已配置托管时一并重启更新，不升级 Python、CUDA、驱动、业务镜像或依赖。发布列表来自当前平台保存的包，不联网下载第三方程序。

## 一次性安装独立执行器

旧节点不能直接自行升级，需要管理员先安装升级执行器。执行器使用该节点原 Worker 凭据，仅访问自身升级任务；凭据继续保存在原配置文件，不上传到界面或发布包。

先准备一份配置，路径均为该节点的实际绝对路径：

```json
{
  "app_dir": "/home/huawei/.local/share/mini-eval-worker",
  "state_dir": "/home/huawei/.local/state/mini-eval-updater",
  "config_paths": ["/home/huawei/.config/mini-eval/fleet-gpu0.json"],
  "services": [
    {"scope": "system", "name": "mini-eval-worker-nfs.service"}
  ],
  "verify_timeout": 120
}
```

`config_paths` 必须列出此安装目录共享代码的全部 GPU 配置，不只是第一张卡；`services` 填原有全部 Worker 服务单元，用户单元 scope=user，系统单元 scope=system。使用 system 服务时执行器需有管理该服务的权限，推荐以系统单元运行。示例中的账号和路径必须按节点修改。

在含本项目源码的目录执行（以系统单元为例）：

```bash
sudo python3 scripts/install_worker_updater.py --config /absolute/path/updater.json --system --start
```

纯用户服务使用原 Worker 账号运行，省略 `sudo` 和 `--system`。安装器仅创建独立的 `mini-eval-updater.service`，不修改原 `mini-eval-worker-nfs.service`、Worker JSON、NFS 配置或工作目录。它把执行器复制到代码升级目录之外，避免升级自己时中断。替换已有执行器前先停止它，使用 `--update`；安装器不接管未列出的服务。

本地恢复状态和执行器状态应在本地盘，不要放到共享资产目录。执行器会检查未列出的 Worker 配置、状态锁和残留 journal；任何一项不符合即拒绝替换代码。安装路径不能是符号链接，凭据与 journal 必须在代码目录外。

## 状态和恢复

- **等待全机任务排空**：可取消，恢复正常接单；不主动杀业务任务。
- **安装中 / 等待全部 GPU 回连**：不可取消，避免安装与调度竞争。
- **恢复旧版本中**：调度仍暂停，先恢复旧代码再重启原单元。
- **升级失败**：若旧代码已恢复，可检查后点击“确认失败已处理，解除升级暂停”，再重新发起升级。该操作不会把停用机器强制启用。
- **恢复旧版本失败**：保持暂停且不能强行取消，修复节点服务或本地 journal 后执行器会重试恢复。查看 `journalctl -u mini-eval-updater.service`；用户单元加 `--user`。

发布响应丢失按相同升级身份重试；若平台已确认升级成功，执行器不得因为丢失响应而回滚已恢复调度的节点。安装目录交换前记录本地事务，进程中断后可从旧目录备份恢复。旧包保留为安装目录旁 `.mini-eval-backup-<升级ID>`，失败的新包可能保留为 `.mini-eval-failed-<升级ID>`；确认不再需要后管理员可清理，当前不自动删除备份。

程序校验包摘要、成员路径、文件类型、总大小和 Python 语法；不接受任意下载 URL 或安装脚本。摘要校验保证包内容与平台发布一致；控制端及其管理员仍是发布信任来源。

## SDK 和使用指南是否随更新生效

节点组件发布包包含整个 `runner/`，包括原生 Python SDK `runner/sdk.py`。只拉取或提交仓库代码不会自动升级节点；先部署控制端源码、发布组件包，再对指定节点排空升级并核对发布摘要。

- 宿主机：平台入口使用节点安装目录中的 Runner；业务进程的 PYTHONPATH 默认包含该目录。业务自行更改导入路径或携带同名 runner 包时，要核对实际导入来源，不能仅凭 Worker 版本判定。
- 容器运行适配器：Worker 在新容器执行中复制当前节点的 Runner。升级节点后新执行采用新版；已有执行不热替换。
- 旧式镜像内置 Runner 或业务自行安装的 SDK：节点组件升级不修改镜像或业务环境，需单独更新并验证。
- 界面使用指南随前端版本发布；仓库操作文档和 Skill 随代码变更同步。提交文档并不等于现场页面已更新，需要部署对应前端。

原生 Python SDK 程序在客户端模板选择“直接评测协议”（`integration_mode=direct`），由业务程序导入 EvaluationClient；不是新增名为 sdk 的接入方式。

## 0.21.13 任务级 SDK 结果

新增 Worker 协议 18 能力 `task_result_reporting_v1`。新建模板使用 `integration_mode=sdk-task-result` 时，先发布兼容 API/前端，再升级承接任务的 Worker；旧 Worker 不应领取此模式任务。无需数据库迁移，模板复用 `integration_mode`，任务结果复用 Run JSON。Worker 从本次 execution 的工作目录读取 `task-result.json` 并转发；业务程序没有平台凭据。Docker 业务镜像需包含更新 SDK 包；平台注入 Runner 的宿主机进程随 Worker 包更新。退出码与业务结果分别呈现，缺少结果显示未上报，不改变退出码所对应的程序状态。此记录说明升级要求，不表示现场已部署。

2026-11-20 后续实际验收：API/前端已发布，仅 `local4090-151` 通过平台升级 API 更新至 0.21.13 / 协议 18。真实宿主机示例批次两项正常退出，分别上报业务成功与失败，并通过在线页面核验；其他节点和 Docker 镜像未升级，详情见[真实批次记录](validation/task-level-sdk-report-20261120/README.md)。

## 断联本地监督开发阶段（未启用）

新增 recovery_supervisor / recovery_runtime 模块，宿主机恢复读取 systemd InvocationID，Docker 使用完整容器 ID。journal 与单调计时持久化、执行级文件锁阻止双监督者；网络对账不能阻塞本地停止判断。普通旧执行仍走原看门狗，更新代码不会给在途执行追溯启用不限断联。生产领取能力协商、主循环接线、结果/清理应用及界面仍待完成，当前不要手工添加授权或删除 journal。验证范围见 [断联恢复实施核对](validation/disconnected-execution-20261124/implementation-audit.md)。

### 领取请求账本（开发阶段，未接入主循环）

`worker/recovery_claim.py` 在发送前持久化 request_id、Slot、boot ID、单调时间及已知执行列表；响应丢失或重启沿用原请求。收到原分配后先验证摘要、代次与策略，再交给幂等执行 journal；目标 journal 落盘成功后才清除领取请求。持久化失败保留待恢复记录，回调只能写 journal，不能启动程序。收据不是启动许可，后续仍须控制对账。当前更新 Worker 不会启用该流程，不要删除旧执行或领取记录尝试恢复。

### 首次启动边界（开发阶段，未接入生产）

`worker/recovery_launch.py` 持久保存一次性 launch_id、原分配/boot、确认请求时间、启动尝试时间及运行身份。确认响应只能在原请求的短窗口内使用；重复响应、Worker 重启不重置窗口。启动调用前必须落盘 attempt，调用失败或身份落盘失败只能核对实际运行实体，不能重试启动。运行实体需携带同一 launch_id；同名 unit、容器或 PID 不是归属证据。机器重启或身份变化进入待核对。

HostBackend 的服务 Description 和 Docker 创建 label 现支持可选 recovery_launch_id，未带该字段的旧任务保持原行为。RecoveryRuntime.start 只接受同标识且尚未启动的实体，容器按完整 ID 启动；inspect_launch 核对启动标识和实际 InvocationID/容器 ID。真实 systemd 用户服务/Docker 短程序已使用该运行后端模拟启动响应丢失并恢复原实例；Docker 创建 label 另有命令契约测试。这不是业务模型评测，未接入生产 Worker 主循环。仍须完成能力协商及完整监督/结果/清理链路后统一发布。

首次启动确认的有效窗口最长 30 秒，且不超过原分配剩余的有限断联容忍时间；即使确认返回成功，迟到超过这个窗口也不能启动。无限断联策略不等于允许任意迟到的首次启动许可。

恢复结果交付开发接口：`RecoveryDelivery(..., apply_results=True)` 要求 API 同时返回匹配摘要和 `reconciled: true` 才推进可靠结果游标；旧 API 忽略 apply 或仅返回收据时，节点保留原记录，不静默当作应用成功。该选项只供后续能力协商的恢复执行路径使用，现有 Worker 主循环尚未调用，不可通过修改配置单边启用。

恢复收尾接口（开发中）要求先核对退出、complete 确认，再删除原运行实体并 cleanup 确认；complete 的 cleanup_confirmed=false 不是失败，表示仍须安全清理。重放保持原 generation、identity 和完成正文，不能根据新连接时间重建执行。原执行存在恢复授权时，无证明旧请求返回409，禁止把它当成允许旧版 Worker 强行清理。尚未广告能力或切换生产主循环。

新恢复收尾 journal 使用 recovery={generation,identity} 和 recovery_finalization={proof,body,phase}。升级后 execute 可从 completion/remove/cleanup/done 原阶段恢复；不能手工删除此记录或用新执行身份覆盖。仅此代码更新并不启用断联恢复，尚需两端完整能力协商及正常执行路径接线。

领取响应丢失恢复要求保持原request_id；相同请求返回原快照/代次，不按当前模板重算。新请求不得接管已领取执行，旧请求也不能把恢复执行交回旧Worker；取消后的原请求仅返回停止处置。生产版本暂不声明disconnected_execution_v1能力；不要单独设置测试用RECOVERY_EXECUTION_ENABLED开关。

Worker 的领取主循环现经 recovery_poll 统一分流：未声明能力且没有待恢复领取文件时仍发原协议请求；已有 .claim.json 时即使当前版本不声明能力，也必须先按原 request_id 恢复，不能绕过待确认分配领取新任务。收据先落盘，再幂等写入执行 journal 的 recovery_assignment，最后清除领取请求。磁盘写入失败、快照冲突、停止处置均保留证据；不得手工删除文件以绕过。完整监督入口尚未接线，带 recovery_assignment 的执行会拒绝进入旧 watchdog/启动路径；这不是已启用断联执行，禁止手工添加能力标识。

启动恢复组合入口 `Worker.start_recovery()`（开发中，未从生产 execute 调用）使用原领取快照、原 boot、launch journal 和运行实体标识。准备运行文件完成后才请求短时启动确认；启动前持久写 attempt，API/运行时响应丢失后不刷新许可、不重复创建或启动。已绑定运行实例以原 InvocationID/容器 ID 恢复，父执行 journal 写入失败可以从 launch journal 补回身份。`created=true` 但实体不存在时保持待核对，不当作安全重启许可。机器重启、停止处置及身份冲突仍需完整控制核对；不要手工修改这些文件解除阻塞。


Worker.monitor_recovery绑定原启动账本与运行身份，复用原请求/启动单调时间，重启不重新计算期限。关闭监控不会杀业务；若本地检查或网络交换尚未结束则保留独占权，不能启动第二个监督者。该组合入口尚未从生产execute调用，不可手动广告恢复能力。


恢复结果采集与延后同步（开发中）：`worker/recovery_results.py` 复用 SDK 任务结果、协议事件文件、回合 journal 和 stdout 事件四种读取方式，先写可靠 outbox，再持久推进游标；磁盘满或写入失败不会丢弃结果。每种执行固定结果来源，重启重放使用原执行 ID、分配代次和源偏移。最终采集标志只在确认原运行实体退出且读完完整记录后落盘；队列为空但未完成采集，不允许清除恢复记录。

协商执行可在完成正文中设置 `pending_results=true`：完成及物理清理确认后释放资源，待补报结果仍保留在节点。结果经应用确认后，`recovery/results-finished` 校验完整性并幂等结束同步；平台取消/超时和新一次重新评测的状态不受旧结果影响。该字段不能用于旧协议绕过完整性校验。不新增数据库表或迁移，独立同步状态保存在既有恢复控制记录的 snapshot。尚未完成生产监督主循环、页面同步状态和端到端发布，不要手工启用恢复能力。

Worker 重启扫描只加载执行主 journal，忽略配套 `.json.launch.json` 和 `.json.supervision.json`；这些文件由所属执行核验，不能当作独立任务，也不能手工删除。

清理后的恢复补报入口已接通：执行记录的recovery_finalization为done且最终采集已封口时，Worker.execute只恢复原outbox的可靠交付，再请求results-finished；不启动程序、不续租。每次最多处理16条，响应丢失保留原记录重试；原outbox丢失时保留journal报错，不能创建空队列冒充同步完成。默认队列为`<execution-journal>.outbox/reliable.sqlite3`。这仅完成已有收尾记录的恢复，正常运行监督与完整生产启用仍待完成。

恢复执行现在将核验过身份的退出事实保存在`<execution-journal>.runtime-exit.json`。systemd成功停止后卸载单元时，记录“已停止、退出码未知”，不会伪造退出码0；仅凭单元不存在仍不能推断停止成功。读取证据核对原执行、代次、启动标识、boot和运行身份；同名新实例、其他启动周期或损坏记录不能替代原任务。证据用于重启后的核对及收尾，不能作为重启业务的许可。落盘失败保留待核对，不发送虚假清理确认。该能力仍属开发中的恢复路径，完整生产入口未启用。
