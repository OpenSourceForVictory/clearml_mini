# 集合运行向导与预检

入口：CS 评测批次 → 评测集合运行。也可从集合管理点击“发布并运行”或已有集合的运行按钮。

1. 选择已发布集合或自定义清单，填写批次名称。已发布集合的任务和客户端固定；临时调整需显式切换自定义清单。
2. 选择客户端并填写推理服务地址、超时和允许覆盖的启动变量。
3. 选择资源池、每项显存需求及 GPU 模式，设置最大并发。
4. 检查并确认配置。确认页列出任务/回合数和每个候选节点的准备状态。

返回上一步以及切换子页签保留输入。修改参数后旧预检失效。检查只表示当前时刻的条件，不预留资源，不保证同时启动，也不探测推理服务地址。

“需要等待资源”表示可以等待现有任务释放资源。“需要准备运行环境”提示镜像、资产、节点或容量等需要检查；合法任务仍可提交排队。磁盘、配置版本或报告过期可能需要管理员处理。参数错误、禁用资源池或越权集合不能提交。

可展开“先试跑一个任务、一个回合”，选择清单中的任务。试跑创建独立批次，并发为 1、回合为 1，保留该任务种子和其他参数。试跑进度提供任务详情及取消入口；未声明回合上报的客户端会明确提示无法验证回合报告。试跑不更改原集合和正式运行草稿，不自动提交正式运行，其结果不能代表整个集合或真实模型质量。

## API

`POST /api/v1/batches/preflight` 使用与 `POST /api/v1/batches` 一样的请求体和 Bearer 身份认证。可以传 `suite_id`（同时 `cases: []` 且客户端与集合一致），或显式 `cases`。

成功响应包括：

- `checked_at`：检查时刻。
- `can_submit: true`：参数有效，可提交；不保证立即运行。
- `status`：`ready` / `waiting_resources` / `needs_environment`。
- `task_count`、`total_episodes`、`max_concurrent`、`cases`：规范化清单与汇总。
- `reasons`：全局/用户并发限制或推理服务互斥等原因。
- `nodes`：槽位标识、节点名、GPU 型号/索引、是否当前可接纳单项任务、原因列表。
- 原因包含稳定 `code`、`category`（`environment` 或 `resource`）、中文 `message` 和 `action`。

无候选节点依然返回 200 和环境准备原因。参数、权限、集合生命周期和积压额度错误沿用提交接口的 400/404/409/429；字段错误保留位置。接口不创建任务、不占用配额、不改变调度轮转游标、不访问用户 URL，不返回宿主机路径或其他用户任务信息。

正式提交保持原 API 和幂等机制，事务内重新校验。预检不替代提交校验或调度准入。试跑和正式运行分别使用独立幂等键；相同请求响应丢失后重试不会重复创建批次。
