# 集合运行向导与预检

入口：CS 评测批次 → 评测集合运行。也可从集合管理点击“发布并运行”或已有集合的运行按钮。

1. 选择已发布集合或自定义清单，填写批次名称。已发布集合的任务和客户端固定；临时调整需显式切换自定义清单。
2. 选择客户端并填写推理服务地址、超时和允许覆盖的启动变量。
3. 选择资源池、每项显存需求及 GPU 模式，设置最大并发。
4. 检查并确认配置。确认页列出任务/回合数和每个候选节点的准备状态。

返回上一步以及切换子页签保留输入。修改参数后旧预检失效。检查只表示当前时刻的条件，不预留资源，不保证同时启动，也不探测推理服务地址。

点击一次预检只发一次平台请求，由 API 在请求内检查清单任务与候选节点，不逐台请求 Worker。任务或节点很多时，响应会包含每项的候选卡诊断，体积和处理时间可能增加；若返回 503，请按响应的 `reason` 区分并发准入、连接池等待和请求预算，再重试。预检结果不参与正式调度预约。

“需要等待资源”表示可以等待现有任务释放资源。“需要准备运行环境”提示镜像、资产、节点或容量等需要检查；合法任务仍可提交排队。磁盘、配置版本或报告过期可能需要管理员处理。参数错误、禁用资源池或越权集合不能提交。

可展开“先试跑一个任务、一个回合”，选择清单中的任务。试跑创建独立批次，并发为 1、回合为 1，保留该任务种子和其他参数。试跑进度提供任务详情及取消入口；未声明回合上报的客户端会明确提示无法验证回合报告。试跑不更改原集合和正式运行草稿，不自动提交正式运行，其结果不能代表整个集合或真实模型质量。

## API

`POST /api/v1/batches/preflight` 使用与 `POST /api/v1/batches` 一样的请求体和 Bearer 身份认证。可以传 `suite_id`（同时 `cases: []` 且客户端与集合一致），或显式 `cases`。

成功响应包括：

- `checked_at`：检查时刻。
- `can_submit: true`：参数有效，可提交；不保证立即运行。
- `status`：`ready` / `waiting_resources` / `needs_environment`。
- `task_count`、`total_episodes`、`max_concurrent`、`cases`：规范化清单与汇总。
- `reasons`：全局/用户并发限制或推理服务互斥等原因。
- `nodes`：槽位标识、节点名、GPU 型号/索引、是否当前可接纳单项任务、原因列表。
- 原因包含稳定 `code`、`category`（`environment` 或 `resource`）、中文 `message` 和 `action`。

无候选节点依然返回 200 和环境准备原因。参数、权限、集合生命周期和积压额度错误沿用提交接口的 400/404/409/429；字段错误保留位置。接口不创建任务、不占用配额、不改变调度轮转游标、不访问用户 URL，不返回宿主机路径或其他用户任务信息。

正式提交保持原 API 和幂等机制，事务内重新校验。预检不替代提交校验或调度准入。试跑和正式运行分别使用独立幂等键；相同请求响应丢失后重试不会重复创建批次。

## 基于历史批次创建新运行

在“评测运行与结果”的批次列表或详情点击“基于此批次创建”，导入五步业务评测向导。向导显示来源批次、原模板名称/版本，以自定义清单恢复当次实际任务，不重新读取后来修改过的集合。导入仅查询，不创建任务或占用资源。

逐项检查回合数、种子、参数 JSON、单项资源与服务关联。历史任务快照保存的是最终值；类型化参数按来源还原：模板默认值继续来自模板，集合公共值预填在“历史集合公共业务参数 JSON”，客户端公共输入预填在客户端步骤，任务单项值留在任务清单。各层仍使用普通向导的预检、提交和覆盖顺序，不需要额外执行“应用”操作。无类型化旧式参数无法准确反推原层级，所有任务相同的值暂预填到客户端 JSON，其余保留在任务清单；类型化快照若缺少来源则保留单项值。任务单项值仍优先；想统一取值时须逐项修改这些任务。预检的“有效业务参数与来源”默认展开，提交前按任务核对。资源仍按各项恢复，可在单项资源 JSON 中修改；清空对象才改用公共申请。无效 JSON 必须修正后才能前进。

`output_dir` 是平台保留的产物路径字段，不能作为类型化业务参数。旧式无类型化模板的任务参数 JSON 可以有同名值，基于批次创建时也能修改，但它只作为业务输入传递；不会修改平台产物目录，也不会自动拼到启动命令。业务程序需要 `--output-dir` 时，应在模板中把平台“产物目录”映射到该选项；若确需独立的业务目录参数，改用其他字段名并配置业务参数映射。

客户端恢复模板引用、运行变量覆盖、请求超时和每项总执行时限（包括不限）；服务端恢复逻辑名称、原模板、业务参数、环境、资源、固定槽位约束、实例数及结束策略。服务端历史业务参数可在 JSON 中编辑；若改选另一服务端模板，旧模板参数会清空，再按新模板填写，避免旧字段被带入。固定槽位只来自原提交约束，不复制平台实际分配结果；托管地址重新调度，外部候选地址保持原访问模式。

原模板、资源池不可用或模板内容已变化时，向导展示问题，需明确选择或确认当前配置后重新预检。旧服务“实例上限”不会直接转成实例数，必须填写明确数量。缺少关键快照、空批次、无法表达的不同客户端配置不会被首项或默认值静默替代。恢复失败可重试；重新导入会清空旧预检、试跑与提交状态。

最后检查有效业务参数和资源申请，再提交独立的新批次。原批次、执行、日志和结果保持不变。同次网络失败重试仍幂等；重新导入使用新的提交身份。本功能无需数据库迁移或 Worker/Runner 更新；API 与前端需要同步更新。普通命令仍受当前提交规则检查，历史配置不能绕过准入。

历史批次导入提示“接口不可用”时，管理员应更新 API，不能只替换前端 dist；同时检查反向代理是否将 /api/v1 转发到同一套 API。容器源码中有文件并不代表已加载：需要重建镜像并重建 API 容器。验收时确认运行中应用已注册 GET /api/v1/batches/{identity}/rerun-draft，再用有权访问的历史批次导入。此功能本身无需数据库迁移或 Worker 升级，跨旧版本部署仍需按数据库迁移指南核对其他变更。
