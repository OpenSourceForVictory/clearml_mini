初步观察：历史增长增加了对象加载量，SQL 次数未增加。当前仍全量加载历史批次，值得后续做等价性对照；本记录不证明已消除瓶颈，未修改性能算法。

工具首轮测试 2 failed、3 passed，原因是错误假设 scheduling 模块顶层导出了 orchestration_scheduler；已改为显式导入，失败日志保留。最终 10 passed，17.49 秒，包括真实独立 PostgreSQL、事务回滚隔离、参数拒绝、连接/正文失败清理、容器身份改变拒绝删除以及失败报告。新脚本单文件行覆盖率 100%、分支 88.89%（project.coveragerc）；不是 scripts 目录或全项目门槛通过。前端和未插桩独立进程未计入。

首次 postgres:16 拉取等待未完成，主动终止后改为本机已有的固定 postgres:16.8；未当作成功测试。原始运行记录在 .runtime/scheduler-benchmark-20261124/。

边界：当前还没有托管成对预约、历史未清理反例、确定性双库决策对照、并发锁等待、持锁时长及 HTTP 混合负载。测试期间本机另有关联专项运行，CPU 有共享，以上仅定位线索，不作为正式五轮旧新性能验收。完整实施清单仍保留未完成项，使用说明见 ../../scheduler-benchmark.md。
