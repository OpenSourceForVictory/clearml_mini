# 控制面连接背压验证（进行中，未部署）

本次修复以 `4d24178` 为修改前代码对照。原代码的领取请求在数据库连接内等待全局调度锁，心跳与普通请求共用连接池；执行循环外层 APIError 分支会停止业务，因此日志、普通健康及部分结果上报的 503 可能误停仍有租约的程序。这些触发路径在本轮开始前已经存在，不据此推断其他平台现场故障根因。

实现为 Worker 0.21.16，协议仍为 18；API 背压默认关闭，必须先升级并验证目标 Worker，再启用 `DB_BACKPRESSURE_ENABLED=1`。最初双池原型不新增表；后续 Agent 观察分表追加 `ad074e5` 迁移，迁移及读写兼容必须单独验收。此前模板说明迁移属于另一变更。没有升级现有节点、重建生产 API 或更改生产数据库。

## 阶梯 HTTP 负载与边界

命令（仅可指向可创建/删除测试数据库的隔离 PostgreSQL）：

```bash
LOG_TEST_DATABASE_URL=postgresql+psycopg://USER:<redacted>@127.0.0.1:PORT/postgres \
  python -m backend.tests.control_plane_load --grades 50,100,200 --seconds 30 \
  --output /tmp/control-plane-load
```

脚本每档创建唯一测试数据库，启动真实 API，退出时停止子进程并删除该数据库；不连接生产 API。测试宿主机 x86_64、32 逻辑 CPU，PostgreSQL 16.8 Docker，API 单进程，普通池 10/控制池 5，单节点单卡、每 Worker 一个模拟运行执行。每约 2 秒尝试续租/遥测、服务健康、1024 字节日志、幂等小产物和领取；心跳失败先随机退避重试。调度分配循环关闭，未测 Agent 高密度同机多卡、真实模型、长时稳定性或多 API 副本，所以不能作为生产容量承诺。

最终记录 `load-final/summary.json`：

| 档位 | 结果 | 最大续租间隔 | 过期租约 / 过期遥测 | 首次借连接 P99 |
| --- | --- | --- | --- | --- |
| 50 Worker / 50 执行，30 秒 | 满足该轮测试目标 | 5.90 秒 | 0 / 0 | 0.058 ms |
| 100 Worker / 100 执行，30 秒 | 未满足 <10 秒续租间隔目标 | 17.36 秒 | 0 / 0 | 0.055 ms |

100 档虽然没有租约到期或遥测过期，已超过更严格的测试目标，立即停止，未跑 200 档。失败主要是调度互斥及入口拒绝，不能把 503 全称为连接池耗尽，也不能宣称“最大支持 50 Worker”。原始请求状态、分接口 P95/P99 和繁忙分类全部保留。

`load/` 保留首轮固定周期脚本 50 档失败；`load-worker-retry/` 保留改为按当前 Worker 续租重试后的结果。修正的是压测器与 Worker 的行为差异，未降低验收阈值。`load-final/` 补首次借连接诊断后重新运行，最终仍保留首个失败档。

- 旧日志、回合、旧产物、任务结果使用已有 Run 行锁，不争用全局锁。超时回收取得行锁刷新租约后重新判断，SKIP LOCKED 跳过正上报的执行。

## v2 日志与心跳锁隔离专项

现有 v2 上传曾锁住整条 Run；同一执行的心跳需等日志提交，即使使用不同连接池也可能超时。现在日志只对 Run 取 KEY SHARE、防删除，以 RunLogState 行锁保护序号及滚动配额，并使用执行专属事务锁与 complete/cleanup 排序；运行中心跳取 Run NO KEY UPDATE。旧 `/logs` 仍写 Run.log_bytes、可能与心跳争行锁，不能把 v2 验证外推给旧节点或旧镜像。

`log-lock-regression.log`：56 项通过，包含真实 PostgreSQL 的心跳持锁时上传、日志状态持锁时续租、日志先于完成及完成先于日志、重复/错序、删除与迁移，以及既有日志发送、服务日志兼容和批次删除测试。最初 `log-lock-focused.log` 中 3 个新用例因测试夹具在设置测试 JWT 环境前导入 API 报错；修正夹具后 `log-lock-pg-recheck.log` 7 项通过。修正的是测试初始化顺序，保留首次失败记录。无此锁调整专属数据库迁移；本轮未部署或跑全量测试。

按项目 source/branch 配置单独采集 `log-lock-coverage.log` 的 19 项测试：`execution_logs.py` 行 90/91（98.90%）、分支 29/32（90.63%）；`execution.py` 在此窄范围下为 354/529 行、71/174 分支。后者不是该模块或业务执行功能组的最终覆盖率，不能用局部用例替代项目统一覆盖率门槛。
