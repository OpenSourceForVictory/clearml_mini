# 百人团队 API 容量专项（2026-11-26）

## 结论与边界

分类 HTTP 准入、入口队列、数据库获取等待和 SQL 总预算已分离；默认值保持兼容。资源池列表消除逐卡附加查询，批次监控避免原生诊断树的重复编码及逐任务深复制。调度、资源预约、生命周期事务规则未修改。

本机 32 逻辑 CPU、独立 PostgreSQL 16.8（max_connections=200），12 API 进程（交互8、执行控制2、数据1、批量1），池上限合计168、配置预算180、额外预留20。**100在线独立管理员会话 + 100节点/100设备Worker** 的45秒混合专项通过：3408次团队页面请求全部200，监控P99 0.849秒，心跳最大间隔4.103秒，50个编排任务完成、9个恢复生命周期完成，1782块变化日志全部接收且最终积压0。此结果不是100人同时提交、真实浏览器、百台物理机器或真实模型评测，也不是长时间容量承诺。

**100节点/800设备Worker的更重候选档失败**：心跳最大间隔38.6秒、163个租约过期、6300块日志未排空，页面与Worker出现超时；不能将上述100 Worker配置称作支持800个同时执行并上报的Worker。该档100任务批次仅完成3个结果上报；恢复目标79、完成47。负载包含790个预置活跃执行、10个领取编排任务的Worker、100人浏览100任务逐节点诊断，明显扩大了事务和响应成本。请求准入/调度锁竞争及大监控响应是观测到的现象，尚不能把全部失败归咎于连接数；盲目继续增加连接不构成修复。保留失败证据，800 Worker生产容量仍待优化验收。

用户要求暂缓长测和全项目覆盖率，本次不重启这些任务。既有数据库连接100不是数据库理论最大吞吐；本机测试200硬上限只为168个API池上限及其他连接留余量。其他硬件必须重新测量，不能照抄为容量保证。

## 复现

使用可销毁PostgreSQL，不能把测试指向生产库。候选配置见 [team-capacity-100.json](../../../deploy/profiles/team-capacity-100.json)，环境映射见 [team-capacity-100.env.example](../../../deploy/profiles/team-capacity-100.env.example)。

```bash
LOG_TEST_DATABASE_URL=postgresql+psycopg://USER@HOST:PORT/TESTDB \
python -m backend.tests.control_plane_load \
  --priority-api --mixed-ui --recovery-load --cards-per-node 1 \
  --command-workers 10 --batch-cases 50 --grades 100 --seconds 45 \
  --web-users 100 --idle-claim-seconds 2 \
  --capacity-config deploy/profiles/team-capacity-100.json \
  --independent-logs --client-per-worker --agent-telemetry \
  --log-bytes 4096 --varied-logs --drain-seconds 10 --output /tmp/team-capacity
```

800档改为`--grades 800 --cards-per-node 8 --batch-cases 100`。每个Worker独立HTTP客户端；空闲领取按真实Worker约2秒周期；活跃执行、服务健康、产物和恢复上报由驱动模拟，Agent按节点分组。100用户各持独立管理员JWT，每5秒一轮列表、资源池、详情、监控查询，起始错开0至4.95秒；不执行前端JS。共享批次管理员浏览不代表所有普通用户权限组合。控制场景另行提交、暂停、恢复；多任务档不将重评测次数冒充已覆盖，原单任务重试与专项接口测试保留。
