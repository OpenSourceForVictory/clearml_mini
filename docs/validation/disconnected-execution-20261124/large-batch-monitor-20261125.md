# 单批次 50/100 任务排队与监控验收（2026-11-25）

隔离 PostgreSQL、四个本机 API 角色和临时网关，使用真实 HTTP 提交单个批次、暂停/恢复、读取列表/详情/监控；模拟卡位持续心跳、Agent 遥测、日志/产物上传及恢复控制。空闲槽位按平台调度实际领取、上报普通命令结果、重复结果幂等确认并完成；其余卡位保持已分配恢复执行。业务本身为模拟输入，不是模型评测或生产恢复协议验收。

新增 `--batch-cases`（1–100）与 `--command-workers`，大批次不与连续小批次混用。脚本要求所有任务实际完成、批次最终成功、监控与详情无失败、曾观察到任务排队、重复结果逐项幂等，并继续核对心跳、恢复清理、日志最终积压和逐类成功延迟。参数边界及多空闲槽位种子测试 29 passed；5 任务/2 槽位真实 HTTP 冒烟通过。

首次 100 任务/10 空闲槽位/150 秒档：100 个任务全部完成、批次成功、4050 以上日志最终确认，但监控接口有 **4 次 `503 request_budget`**，档位判失败。监控 P99 包含拒绝响应约 4 秒；其余成功监控请求最慢约 1.90 秒。失败证据保留在 `/tmp/mini-eval-batch-100/summary.json`。根因是每个待调度任务重复遍历整池节点构造相同诊断；并非数据库查询数失控，原有 100 任务单元测试已限制查询数 ≤15，却没测 CPU/响应预算。

修复后，同一次监控请求中，对配置快照除展示用 `case_id` 外相同、资源申请和目标节点相同的待调度任务复用一次诊断，逐任务深拷贝输出；下次请求重新计算，资源不同的任务分别检查。没有改变调度准入或状态。`test_monitoring.py` 的 100 等价任务只计算一次诊断、不同资源任务不合并及原查询预算测试通过；监控/背压组 8 passed。
