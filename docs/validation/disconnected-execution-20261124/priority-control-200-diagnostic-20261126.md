# 200 Worker 执行控制入口诊断

使用一次性 PostgreSQL 16.8、四角色 API 和 Nginx 网关运行 60 秒模拟负载：200 个模拟设备 Worker、50 台四卡节点、独立客户端、日志/遥测/恢复控制/连续批次和页面请求，并启用 HTTP 阶段跟踪。业务进程未启动；本次是容量诊断，不是 30 分钟验收或真实模型评测。

结果 `passed=false`：24,980 次 200、5,648 次 503。503 中 5,111 次为入口 `request_concurrency`、537 次为 `scheduler_lock`；心跳 1,631 次、领取 1,322 次、服务健康 980 次、恢复控制 1,656 次（其中 519 次为调度锁）。最大心跳成功间隔 16.11 秒，未达到 10 秒目标；日志最终仍有 15 块待发。19 个模拟恢复执行均完成、清理和结果确认，不能据此把整档判为通过。

执行控制进程共处理约 15,124 个成功请求，另有 5,109 次入口拒绝；该进程请求总历时 P50/P95 为 302/335 毫秒，包含最多 250 毫秒的准入等待。PostgreSQL 采样未出现持续等待锁，初始连接获取等待 P99 约 0.082 毫秒；HTTP 客户端发出请求前 P99 约 5.6 毫秒，响应头等待 P99 约 360 毫秒。这些证据将主要瓶颈指向执行控制入口及其进程处理能力，而非单纯的数据库连接池耗尽。样本不能区分 Python 处理、GIL、数据库 SQL 和网关调度各自的精确占比。

当前心跳、服务健康和恢复控制共用 `execution_control` 类别的 24 个准入/连接额度；恢复控制的 `scheduler_lock` 重试又增加请求压力。不能仅提高 PostgreSQL `max_connections`，也不能为让档位通过而放宽心跳阈值。下一步应在相同负载下量测准入前等待和实际处理时间，并比较执行控制进程的复制与总连接预算不变的配置，确认页面、批量与可靠结果不退化后再修改默认部署。原始诊断汇总位于本机 `/tmp/mini-eval-capacity-diagnostic-200/summary.json`，原始 API 日志不入库。
