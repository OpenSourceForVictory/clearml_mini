# 在线数据库预算专项（2026-11-25）

第 2.3 项核对：单/双进程和四角色 API 均通过 `backend/app/db_budget.py` 创建在线 PostgreSQL Session；请求入口设置单调截止，SQL 前按剩余时间更新事务内 `statement_timeout`、`lock_timeout`，连接池借用有界，后台调度和迁移不继承在线请求截止。只有已识别的池耗尽、锁/语句超时、死锁及序列化冲突映射为可重试 503；未知 SQL 错误保持原错误。

使用本机独立测试 PostgreSQL 容器，测试夹具为每条用例创建、删除临时数据库；未连接平台业务库。`.venv/bin/python -m pytest -q backend/tests/test_db_budget.py`：71 通过、0 跳过，22.76 秒。场景包括真实行锁等待与连接归还、两连接死锁、SQL 语句及累计预算、HTTP 客户端 50 ms 先断开后后台 SQL 有界终止、控制池与普通池隔离、等待取消后释放入场名额，以及未知 SQL 错误不被伪装为过载。该专项不替代全量测试或生产容量验收。

成本对照：在同一独立 PostgreSQL 上预热后交替执行 100 次每组的单事务 `SELECT 42`；旧形式先后执行两条 `set_config`，新形式一条语句同时设置两个参数。旧形式“配置两次+查询”中位 0.105 ms，新形式“配置一次+查询”中位 0.084 ms；每条业务 SQL 的超时配置往返确定从 2 次减为 1 次。样本仅为本机微基准，不能推算生产请求延迟或 Worker 上限。首次用系统 Python 运行微基准因缺少 `psycopg` 失败，改用项目 `.venv` 后完成；失败不计入通过数。

运维解释见[部署与运维](../../operations.md)：`request_budget`、`connection_pool`、`lock_timeout`、`statement_timeout` 等 `reason` 用于定位单次拒绝；503 不能充当业务执行失败或释放资源的证据。
