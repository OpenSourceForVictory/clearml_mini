# API 停机 3 分钟时托管服务真机验证（2026-11-28）

使用本机平台、`local4090-151` 客户端和 `rtx4090-157` 服务端，提交单任务、单回合的宿主机 HTTP echo 批次。客户端调用托管服务后等待 420 秒；服务端是持续监听的真实 Python 子进程。该程序只验证业务进程生命周期和控制面恢复，不是模型推理或 GPU 算子验收。实验仅在确认平台无活动执行后开始，两轮中均停止四角色全部 12 个 API 容器 180 秒，保留数据库、网关与节点 Worker，按 30/90/150/180 秒检查服务端口与数据库执行状态。临时修改两台测试节点的角色、宿主机环境及服务网络，实验后按原配置恢复。

第一轮服务端为 Worker 0.21.21，未广告 `disconnected_execution_v1`，服务端执行 `37ddd297-ae66-4176-a14d-4ee86c7e05ab` 无恢复授权；客户端执行已有授权。停 API 前服务端口 200、两边 RUNNING。断联约 26 秒时服务节点 systemd 日志显示停止原 host unit；30/90/150/180 秒服务端口均不可达。停机期间数据库记录仍 RUNNING，API 恢复后调度器将服务端标记 `TIMED_OUT: 执行心跳租约过期（额外宽限 30 秒）`，客户端随后 `FAILED: runner exited with code 15`。这证明旧服务端 Worker 的本地租约看门狗会在控制面断联时停止进程，平台恢复后才写超时结果。

第一轮还暴露旧 Worker 与新版 API 清理接口兼容缺口：旧 Worker 的 `post(path)` 发送 JSON `{}`，可选 `RecoveryProof` 参数将其按非法证明体拒绝，返回 400，导致服务端 `cleanup_confirmed=false` 且槽位隔离。API 清理入口修正后，在隔离 PostgreSQL 上验证空对象旧协议清理和恢复授权禁止裸清理；部署新 API 后旧 Worker 重试成功，清理确认变为 true、槽位隔离解除。该修复不改变已经超时的结果。

第二轮通过平台节点升级入口将 `rtx4090-157` 升至 Worker 0.21.23，确认 `disconnected_execution_v1` 已上报。新批次 `facb22ba-637f-4666-b137-b1674557df55` 的客户端执行 `124ba70a-9bb5-40ce-a8b6-2c8c1f636380`、服务端执行 `b49a18f2-b937-40e0-aa71-a6baab82b7c6` 均在领取时获得恢复授权。停 API 前两边 RUNNING、服务端口 200；30/90/150/180 秒服务端口均为 200，数据库仍为原执行 ID 的 RUNNING。恢复 API 后至少 30 秒内两边仍 RUNNING，服务健康时间重新更新；服务 host unit 保持同一启动时间 `14:30:11` 和 PID `3708431`，没有重启。第二轮客户端等待 420 秒超过模板冻结的 300 秒执行时限，最终 `TIMED_OUT: 客户端执行总时限已到`；服务端按批次终止流程 `CANCELLED`，两者清理确认均为 true。故第二轮只证明断联期间服务持续运行及恢复后的原执行对账，不能作为批次成功证据。

第三轮将客户端等待改为 220 秒，仍覆盖完整 180 秒断联窗口且低于 300 秒执行时限。批次 `636e36e3-d174-4f43-bb61-e65878fb6465` 的客户端执行 `f6e70096-f766-40fc-bab6-66d2891f5732` 与服务端执行 `f484f89e-572b-4564-9e49-8254ea45258d` 均有恢复授权。API 停机前两者 RUNNING、服务端口 200；停机 30/90/150/180 秒端口均 200，数据库中原执行均保持 RUNNING。API 恢复后客户端 `SUCCEEDED`，批次 `SUCCEEDED`（1/1），服务端按批次完成流程 `CANCELLED`，两边 `cleanup_confirmed=true`，未被心跳租约判超时。测试节点临时角色、宿主机环境、服务网络均已恢复原值；`rtx4090-157` Worker 0.21.23 保留。

验证边界：本轮故障是停止所有 API 容器，节点网络、数据库和网关仍在；没有模拟数据库故障、节点重启、实际模型推理或多任务高负载。旧执行不会因升级 API/Worker 追溯获得恢复授权。
