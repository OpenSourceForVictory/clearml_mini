# 执行控制副本扩容专项

触发条件：四角色单执行控制进程下，200 模拟 Worker 同时续租、上报服务健康和恢复控制。60 秒档出现 5,648 次 503（入口并发 5,111、调度锁 537），最大心跳成功间隔 16.11 秒，日志最终待发 15 块。数据库采样未见持续锁等待，连接获取 P99 约 0.082 毫秒。详见 [入口诊断](priority-control-200-diagnostic-20261126.md)。

先试过在原 24 个控制额度内保留三分之一给心跳及清理，定向测试通过，但同负载总 503 升至 7,758；服务健康、领取退化，故该试验代码已撤销，不作为发布方案。失败汇总保留在本机 `/tmp/mini-eval-priority-reserve-200/summary.json`。

改为两个执行控制进程，各有 12 个专用连接与入口额度。其余三角色保持原额，总 API 连接预算仍为 80，唯一调度器仍在 Worker 数据进程；旧四进程运行参数仍可读取并使用原控制 24。测试驱动的临时 Nginx upstream 将执行控制请求分到两端。另用独立 Docker DNS 双后端实验验证生产网关的变量式 `proxy_pass` 能把 40 次请求均分为 20/20；这只是 DNS/网关路由验证，尚非生产 Compose 切换。

相同 200 Worker/50 四卡节点、60 秒、隔离 PostgreSQL 16.8、五 API 进程与网关的模拟负载结果 `passed=true`：33,618 次 200、5 次 201、601 次可重试 503，其中入口并发 129、调度锁 472；最大心跳间隔 4.09 秒。心跳 5,825 次成功、23 次 503；领取 5,594 次成功、9 次 503；19 个模拟恢复执行均完成、清理与结果确认。日志请求曾有 44 次可重试 503，5,255 块最终全部接受、待发 0；页面及 Agent 请求没有 503。两个控制进程分别处理 11,246、11,218 次成功请求，确认负载均分。最终定向角色/网关/纳管测试 103 通过、无跳过；PostgreSQL 角色组亦单独以 41 项通过、无跳过验证。旧四进程实际部署和五进程配置兼容仍需单独发布演练。

随后启动了新拓扑的 100 Worker/30 分钟档。按用户要求在约 13 分钟时中止，退出码 130；最后一条 780.93 秒进度记录显示最差心跳间隔 2.184 秒、35,100 块日志全部接收、积压 0、心跳和日志入口拒绝 0。原始进度留在本机 `/tmp/mini-eval-control-scale-100-30m/progress-100.jsonl`。这不是 30 分钟长测通过证据，也没有最终汇总。

60 秒改善及中止前的进度不能代替新拓扑的 30 分钟 100 Worker 基线、200 Worker 更长候选、慢数据库/锁/断网突发或真实宿主机/Docker 程序验收。当前五进程配置未在运行平台上线，OpenSpec 5.2/5.3 不勾选。

另行复测本机恢复主路径：228 项通过、40 项默认条件跳过；显式启用真实运行条件后，宿主机和 Docker 恢复矩阵 45 项通过、无跳过，覆盖正常完成、普通命令、stdout 大输出、断联完成/取消/超时、有限容忍、服务、重启、启动前取消及批量接口拒绝。这里运行的是短样例程序，不是模型质量评测，也没有涵盖清单中的全部设备与故障组合。
