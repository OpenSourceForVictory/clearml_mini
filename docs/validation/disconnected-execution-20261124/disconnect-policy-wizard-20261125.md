# 断联容忍配置的提交与快照专项（2026-11-25）

本轮只实现并验证 4.6 的配置传递：向导默认 `null`（不限），可选正整数秒；提交后每个客户端任务及托管服务实例各自保存原值，协商领取把原快照写入不可变恢复授权。历史批次导入回显原值，缺字段按不限处理；同批次快照异质或非法时阻止自动恢复。有限值在恢复开关关闭或 Worker 未声明 `disconnected_execution_v1` 时被调度准入拒绝，不会退回旧租约。旧任务、业务总时限和取消语义不因本轮改变。

验证：后端提交/领取/重评测/编排等专项 59 通过；最后一处托管服务实际 Job 断言及历史异常值补测 7 通过；前端向导与历史导入 24 通过；前端生产构建通过。新增用例覆盖 0、负数、布尔、浮点、字符串和超过持久化整数范围的拒绝，以及客户端与托管服务实际快照、能力缺失、历史值回显。初次专项失败 7 项：6 项测试错误地预期 422，平台实际统一返回 400；1 项测试未准备节点存储/运行环境，无法进入领取。修正夹具后上述专项通过。前端初次 2 项失败：原测试未等待历史导入完成或原生表单验证阻止提交；修正用例后全部通过。以上是测试假设/夹具问题，不作为业务正常运行证据。

边界：生产 `RECOVERY_EXECUTION_ENABLED` 仍关闭、Worker 尚不广告完整恢复能力；本项不能证明实际长时间断联仍执行，也不能代替 4.6 的本地监督、超时边界、取消与重连矩阵，更不能替代全量测试或目录覆盖率门槛。

后续补测：`RECOVERY_RUNTIME_TEST=1` 对真实隔离 systemd 宿主机程序和 Docker 短程序分别设置 1 秒有限容忍，先阻断控制请求、超过旧 1 秒租约并观察本地停止，再恢复连接。两个模式均以原执行 ID 对账、状态 `TIMED_OUT`、清理已确认，未生成伪造的回合完成结果；定向 2 通过，随后完整真实短程序文件 16 通过，覆盖正常完成、断联后完成、取消、业务超时、有限断联、服务、Worker 重启及启动前取消各两种执行方式。首次断言把 `result_sync=complete` 误认为业务成功并期望 failed，2 项失败；核对 `results_finished` 语义后改为检查停止原因和回合事实，重跑通过。`result_sync=complete` 只表示已有数据同步完毕，不表示业务成功。此用例是受控短程序，不是生产断联或模型验收。
