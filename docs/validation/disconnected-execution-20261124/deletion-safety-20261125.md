# 断联批次删除与最终确认专项（2026-11-25）

触发条件：用户删除仍有执行或托管服务的批次，原 Worker 可能断联，或者 `results-finished` 已在平台提交但响应丢失。旧删除接口要求全部终态并已清理，无法表达“用户已删除，但进程停止待确认”。

本阶段删除事务先写批次墓碑、暂停调度、请求取消任务和停止关联服务，立即从用户列表隐藏。Run、Job 和资源占用保留至终态、清理确认和可靠结果同步封口；调度轮询仅对仍有任务或服务记录的墓碑检查安全清除。清除时删除原始补报收据和领取任务快照，仅留原恢复授权及最小身份/终态确认快照，使同一 Worker/分配代次/进程身份可重放丢失的最终确认。已删批次的结果应用返回明确 `discarded`，保留不可变摘要，不写回业务结果。旧 Worker 的原有停止和清理语义不变。

验证：SQLite 删除、托管服务及恢复收尾专项；独立 PostgreSQL 的同组接口专项；前端批次列表 16 项及 TypeScript/Vite 构建。针对正常清除、运行中服务停止请求、等待未清理执行、结果丢弃、最终 ACK 重放和错误 HTTP 保留批次行均有测试。初次托管服务测试因仅预约未领取，按预期立即安全清除；夹具改为先领取真实服务执行，再验证保留，首次断言失败保留在工作记录中。这里的测试进程和 mock 页面不等于真实模型评测，也不证明生产恢复能力已启用。

边界：本变更不包含单侧长断联后的服务探测/就绪完整矩阵，不包含生产 Worker 升级或真实节点断网验收；完整 4.9 和 5.x 发布验收仍按 OpenSpec 逐项核对。无新增数据库迁移，需 API、前端及 Worker 结果 ACK 代码同版升级；生产恢复能力开关继续关闭。
