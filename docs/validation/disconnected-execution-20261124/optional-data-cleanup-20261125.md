# 可选日志/产物拒绝时的收尾专项（2026-11-25）

在 `Worker.execute` 恢复路径中发现：普通日志上传只有可靠结果队列本轮无交付时才尝试，旧式上传产物没有执行入口。这不是业务进程故障，但会造成恢复批次日志/产物缺失。现改为普通日志与可靠结果各自有限次尝试；退出确认后旧式产物在移除原宿主机 unit/Docker 容器前尽力读取并上传。数据 API 拒绝或暂不可用时记录类别并继续完成、原身份物理清理和可靠结果补传；可选产物与诊断日志可能缺失，不把它们当作协议结果成功。

真运行测试 `backend/tests/test_recovery_execution_real.py` 的 `bulk_rejected` 使用隔离 API/SQLite、真实本机 systemd 用户服务及 Docker 短程序，业务各写一份 `sample.json`，持续给普通日志和旧式产物接口返回 503，验证两类请求确实发生、程序终态 SUCCEEDED、可靠回合结果收到、清理已确认且原程序只创建一次。首次测试发现两种模式都没有普通日志请求（2 失败），定位到被可靠队列交付跳过的条件；修正后定向 2 通过。该短程序不等于真实模型评测；GPU/NPU 设备控制和停止失败边界仍按 4.4 待验。

本次没有新迁移，生产恢复能力开关仍关闭。旧式产物的失败不是可靠队列的一部分；需要长期保留产物时应配置共享存储目录和 API 只读访问。
