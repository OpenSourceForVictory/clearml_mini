# 恢复控制锁与 100 Worker 短测（2026-11-25）

范围：隔离 PostgreSQL、四个本机 API 角色及 Nginx，模拟 100 个卡位归属 25 个节点，真实 HTTP 调用心跳、Agent 遥测、恢复对账、日志、产物和批次页面；约 10% 的执行走完成、清理、可靠结果及重复补报。业务进程为模拟输入，不是模型评测，也未启用生产恢复能力。

触发条件：恢复对账原先对每条 RUNNING 状态报告先抢全局调度锁。100 卡位短测产生 1679 个 503，其中 1628 个来自恢复对账；完成到清理最慢 14.62 秒。稳态 RUNNING 对账只续原执行租约和控制游标，不变更资源分配，因此改按 Run → 原授权行锁；STARTING 转换、租约到期及完成/清理仍保留全局资源锁。单执行行锁忙返回带 Retry-After 的 503，预读后状态或租约越界时重试事务。

隔离 PostgreSQL `backend/tests/test_recovery_control.py`：67 passed，覆盖全局锁占用时稳态报告成功、租约过期仍拒绝、取消时行锁竞争返回 503 后重试成功。此前修改首次运行 66 passed/1 failed：Run 行锁超时直接冒出 `OperationalError`；已改为 NOWAIT 加 SQLSTATE 55P03 映射后全绿。失败证据不能当作已通过。

同脚本 100 卡位/90 秒重测：21973 次 200、9 次 201、138 次 503；503 包含恢复对账 133、完成 2、清理 3，心跳/日志/Agent 无 503。9 个模拟执行全部完成、清理、可靠结果及重复收据确认；4050 条日志全部接受且最终无待发；页面连续 9 批失败/重评/成功无错误。恢复对账成功响应 P99 4.04 秒，完成到清理最大 1.30 秒。**整档未通过**：最差心跳成功间隔 13.44 秒，超过 10 秒门槛，早期 30 秒窗口出现，后续 60/90 秒当前最大间隔约 2 秒。压测驱动事件循环延迟 P99 0.06 秒，仍需定位 API 启动突发/请求队列的瓶颈，不能简单归为压测端卡顿。输出在 `/tmp/mini-eval-recovery-load-100-fastlock/summary.json`；工作区不收录可能含运行请求信息的原始 API 日志。

第一轮仅说明锁争用和清理延迟明显改善，**不是 100 Worker 容量验收通过**。失败档保留，不能删除或按成功计数。

随后保持服务端代码、卡位数与 90 秒时长不变，增加 `--client-per-worker`：每个模拟卡位独立 HTTP 客户端，不再让 100 个卡位共用一个连接池。该轮 **passed=true**，26056 次 200、10 次 201、163 次可重试 503（恢复对账 153、完成 5、清理 5；心跳、日志、Agent 均无 503）。最差心跳间隔 4.09 秒，恢复控制成功 P99 0.14 秒，完成到清理最大 2.65 秒；9 个恢复执行全部完成、清理、可靠结果确认和幂等重复确认，4050 条日志最终确认且无待发；10 个连续页面批次均完成失败→重评→成功。无过期租约或过期遥测。输出在 `/tmp/mini-eval-recovery-load-100-client-isolated/summary.json`。`backend/tests/test_control_plane_load_gateway.py` 24 passed，覆盖多卡归属、原恢复授权与数据库最终计数。

两轮唯一的客户端连接模型差异使短测结果不同，说明共用连接队列是第一轮 13.4 秒心跳间隔的重要因素；不能由此断言服务端无容量风险。第二轮仍有首次恢复对账抢全局锁的 153 次 503，按原序号/正文重试成功；需要在 30 分钟长测和故障突发中观察是否积压。两轮均未使用真实业务进程，也未覆盖页面产物浏览。

30 分钟基线：同一隔离 PostgreSQL 与四角色网关，100 个模拟 Worker、25 个四卡节点、独立 HTTP 客户端，连续批次及页面查询，日志每卡约 1 KiB/2 秒。运行 `.venv/bin/python -m backend.tests.control_plane_load --grades 100 --seconds 1800 --output /tmp/mini-eval-recovery-load-100-30m --priority-api --mixed-ui --agent-telemetry --recovery-load --cards-per-node 4 --independent-logs --continuous-batches --varied-logs --progress-every-30s --client-per-worker`，需用 `LOG_TEST_DATABASE_URL` 指向一次性测试库。主机为 x86_64、32 逻辑 CPU；四个 API 进程合计连接配置上限 80。结果 `passed=true`：523481 次 200、210 次 201、1095 次可重试 503；其中恢复对账 1089、心跳 2、完成 1、清理 3，均标记 `scheduler_lock`，页面列表/详情/监控各 843 次均为 200。最差心跳成功间隔 4.08 秒，无过期租约或遥测；恢复对账成功 P99 0.086 秒、心跳成功 P99 0.079 秒、监控成功 P99 0.152 秒。80964 条日志全部接收，最大待发块每 Worker 为 1，最终待发 0，最大待发年龄 0.077 秒。9 个模拟恢复执行全部完成、清理、可靠结果确认及重复结果幂等确认，最慢资源释放 2.57 秒；连续页面批次 210 个完成。原始汇总与逐 30 秒采样保存在 `/tmp/mini-eval-recovery-load-100-30m/`，其中 API 原始日志不纳入仓库。它验证的是模拟 HTTP/数据库负载，不代表真实业务程序或模型评测。

按“100 基线通过才测试 200”规则，随后使用相同负载参数将 `--grades` 改为 `200`、`--seconds` 改为 `90`，输出 `/tmp/mini-eval-recovery-load-200-candidate/`。候选档 `passed=false`：最大心跳间隔 13.26 秒，超过 10 秒门槛；38042 次 200、6 次 201、8258 次 503、3 次 409。503 原因为 `request_concurrency` 7715 次、`scheduler_lock` 543 次，心跳 2424 次、领取 2030 次、恢复对账 2123 次、服务健康 1627 次。日志生成 7951 块，仅接收 7921，最终剩余 30 块且最旧等待 64.34 秒；另有 1 次日志 409 与 2 次产物 409，须单独审查清理后的发送竞态。19 个模拟恢复执行虽均完成、清理及结果幂等确认，最慢释放 8.36 秒，候选档仍因心跳与日志积压不达标，不能作为 200 Worker 容量结论，也不应通过扩大阈值掩盖。

控制 API 故障注入：100 Worker、90 秒混合负载，`--control-outage-seconds 10` 在第 31.03 秒停止控制进程，第 41.03 秒重启。运行目录 `/tmp/mini-eval-control-outage-100-10s/`。网关向心跳返回 923 次 502，向恢复对账返回 880 次 502；心跳路由确实位于控制 API，这在首轮测试口径中漏列，已修正测试允许列表及操作文档。日志 4050/4050 接收且无积压，9/9 模拟恢复执行均完成、清理、补报及重复收据确认，页面 10 个连续批次无错误，无过期租约。`passed=false` 源于最大心跳间隔 13.37 秒超过**无故障基线**的 10 秒门槛；10 秒故障本身使该门槛不适用。该档只能证明控制进程恢复后的原身份补报和收敛，不能充当无故障容量通过结果。首轮 `acceptable_responses` 还把故障窗口的心跳 502 误列为异常；修正后 38 个相关单测通过，未篡改原始故障档结果。

恢复执行方式补测：真实隔离 systemd 宿主机及 Docker 短程序各一条普通命令、无评测协议事件，控制暂断后程序退出码 0，两者均以任务成功收尾且不创建虚构回合记录。首次两项测试失败是断言错误地要求普通命令存在回合记录；修正断言后 2 通过、20 条其他场景未选中。此处仅是普通命令与现有直接协议主循环的补充，未覆盖整个 4.10 模式矩阵或真实模型评测。
