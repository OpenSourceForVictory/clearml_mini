## 多服务多客户端并发验收过程

首轮全局及单用户配额为 5，两个服务进程占用两个执行名额，因此只出现三个客户端并发，第四个排队。该轮四任务均完成，不能用作四客户端并发证据。

将配额临时调为 6 后，快速重用独立健康端口暴露 `TIME_WAIT` 误判：业务端口有 `SO_REUSEADDR`，健康端口遗漏该设置。Worker 0.14.2 补齐；真实 socket 回归复现旧行为并确认修正后可以重用、仍拒绝监听中的端口，13 项服务回归通过。异常批次保留，两个尚未启动的客户端已取消，剩余测试服务显式停止并完成清理，然后重新验收。

失败批次结束还触发了第二个问题：编排清理对终态服务调用 `cancel_job` 返回 409，使整个调度 tick 回滚，后续无关批次也无法前进。修正为已终态服务只更新停止意图，不再重复取消；新增失败批次与另一待调度批次的回归，完整编排测试 18 passed。上线后同一待调度批次继续执行，没有重复提交业务任务。

最终复测：**同一批次两个宿主机 WS 服务、四个宿主机客户端，8 回合全部成功**。两个服务运行在同一个 NPU 槽位，客户端共享本机 GPU 槽位的调度预算；每个服务绑定两个客户端。四个首回合 WS 连接的共同存续时间为 **13.973 秒**，两端 systemd 执行单元和实际 WS 回显均有记录。服务端执行标识与平台为每个客户端分配的标识逐条一致。

最终 API 镜像为 `mini-eval-api:ws-concurrent-cleanup-20261116`，两个验收节点 Worker 为 0.14.2。验收完成后恢复全局/单用户配额 5、本机并发 2、公共 GPU 池每卡并发 2，以及原宿主机环境；临时测试模板停用，历史保留。[并发执行证据](ws-concurrent-evidence.json)。
