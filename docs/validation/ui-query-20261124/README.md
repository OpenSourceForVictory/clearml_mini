# 界面查询优化专项验证

本次按用户确认只优化界面读取，不修改 scheduling.py、orchestration_scheduler.py、资源预约、租约、心跳或领取逻辑。execution.py 唯一修改是 admin/nodes 调用批量读取。无需迁移数据库或升级 Worker/Runner，尚未部署。

## 同数据 PostgreSQL 对照

独立测试 PostgreSQL（本机 15439）临时库，使用当前模型建表，完成后删除。500 节点各一张卡，20 个批次各 100 项任务；详情对照使用其中 100 项任务，各 10 个回合，回合带 4 KB 模拟 metrics。预热一次，再采样三次。计时包含 ORM 读取和 JSON 编码，不含 HTTP、鉴权和浏览器渲染；不是生产并发容量或真实模型验收。

原始结果：[query-comparison.json](query-comparison.json)。可复用的测试工具：`backend/tests/read_query_benchmark.py` 的 `run(engine)`，只能传入新建的隔离测试库；详情基线固定读取 Git e85cbb0 的 monitor 函数，列表比较兼容 full 与新 summary，节点比较逐台与批量读取。

| 场景 | 原读取 SQL → 新读取 SQL | 耗时中位数 | JSON 大小 |
| --- | --- | --- | --- |
| 500 节点 | 1001 → 3 | 217 → 14.7 ms | 130780 字节，保持一致 |
| 20 批次 × 100 任务 | 101 → 7 | 204 → 28.7 ms | 2930290 → 19180 字节 |
| 100 任务 × 10 回合详情 | 12 → 8 | 37.6 → 23.8 ms | 192297 字节，保持一致 |

详情的 summary/outcomes 在相同数据状态下显式断言相等；查询耗时存在波动，SQL 数量、统计正确性和响应字段是稳定验收指标。摘要仍需读取本页最新尝试的回合分类字段，极多回合时仍有汇总成本；未引入缓存，也未解决历史编排调度扫描成本。
