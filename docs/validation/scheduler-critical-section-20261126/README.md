# 调度临界区查询优化（2026-11-26）

基线提交 `3d09615`。本轮不删除调度全局咨询锁、不拆资源分配事务、不引入锁外快照。减少持锁期间的重复SQL和无关历史对象加载，缩短临界区的实际工作时间。无需迁移或更新Worker。

## 改动与边界

- reconcile一次联查Run/Job/恢复授权存在性，避免对活动执行反复s.get(Job)。Run的SKIP LOCKED与取锁后最新状态复查保持原样。
- 活动占用一次联查Run/Job；保留终态但cleanup未确认的占用，删除未使用的逐条Pool读取。
- 优先级、暂停与批次并发元数据只读取本轮排队任务引用的批次；空队列不加载历史批次。
- 用户公平轮转、批次优先级、服务配对、资源容量与预约期限规则不变。所有读取仍在同一个全局锁事务中；没有把大范围资源读放到锁外。

## PostgreSQL对照

使用独立PostgreSQL16.8容器，测试后清理；脚本预热后重复3次，每次回滚以保持输入完全一致，**不包含commit耐久成本、不包含HTTP或真实业务负载**。时延是小样本，不能外推生产SLA。

历史场景可用 `python -m scripts.scheduler_benchmark --history 1000 --pending 100 --repeat 3 --output <报告路径>` 复验。新测试 `test_scheduler_query_scope.py` 检查历史数增长不扩大ORM对象加载、活动数1→100不增加逐任务SQL，并用真实PG验证状态未改变。对照原始数据见本目录三个JSON。
