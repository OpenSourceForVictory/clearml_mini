# 历史批次参数编辑与运行配置复核

触发条件：从历史批次导入的每项任务带有最终业务参数。向导公共参数的同名字段被单项历史值覆盖，用户只改公共值时容易误认为修改未生效；改选服务端模板时，原实现还会保留旧模板的 `imported_parameters`，可能把旧字段提交到新模板。

处理后，向导明确提示逐项编辑与“将已填写的公共参数应用到所有任务”的区别。改选服务端模板会清空旧模板业务参数并显示新模板的类型化字段；保留原模板时，历史参数 JSON 仍可编辑。服务端资源和环境的其他字段按原草稿保留，提交仍经现有预检。

验证：`frontend/tests/batch-rerun.spec.ts` 覆盖单项参数修改、公共参数不静默覆盖与显式应用、服务端历史 JSON 编辑、切换模板后清除旧字段并将新值送入预检和提交。`frontend/tests/batch-run-configuration.spec.ts` 覆盖详情页逐任务最终值与来源、宿主机/容器动态参数拼接、任务切换、服务端定义及旧快照缺失提示。两组共 28 项通过；`run-wizard.spec.ts`、`orchestration-wizard.spec.ts`、`wizard-clarity.spec.ts` 共 47 项通过；`npm run build` 通过。后端 `backend/tests/test_batch_rerun.py` 验证历史草稿只读、参数修改后的预检/提交与原批次不变，6 项通过。首次使用系统 Python 收集失败（未安装 FastAPI），改用项目 `.venv` 复测通过。前端未插桩，不宣称覆盖率；本次未运行全项目覆盖率。

边界：浏览器测试使用模拟 API 快照，验证界面与请求载荷；不等于真机业务程序执行。历史最终值导入为新批次的单项参数，新批次来源会重新计算，不能倒推原批次来源。运行配置页显示提交快照和由已知映射推导的启动命令，节点运行时才确定的路径、端口及登录 Shell 环境不冒充已采集值。本次仅前端与文档变更，无数据库迁移或 Worker/Runner 升级；其他部署需更新前端静态资源才可见。
