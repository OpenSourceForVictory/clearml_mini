# 分类等待配置对照验证（2026-11-26）

## 方法

保持12个API进程、168个池连接上限、PG max_connections=200不变。独立PG16.8；100用户、100节点/100Worker，单批次100任务，10个Worker领取编排任务，其他Worker持续模拟上报。每个用户每5秒并发读取列表、资源池、详情和监控，错开起始时间；日志4KiB变化内容、独立上报、独立HTTP客户端。真实网关、API、数据库与调度器，Worker/Agent流量及业务结果由驱动模拟，不是100台真机或真实模型评测。

候选A为上次已部署配置；B仅将execution_control的queue_waits/pool_waits从0.5/0.5秒改为1/1秒；C在B基础上把观察与日志入口等待设1秒、连接等待0.5秒，队列分别扩为128/96。C改变了入口队列长度，不能将全部收益归于等待时间。所有候选保持SQL4秒与Worker HTTP5秒，页面配置不变。各档60秒、日志排空10秒。按结果增加D（C恢复原控制通道0.5/0.5秒）及180秒有界复验，不宣称长期生产稳定性或800Worker容量。

观察分类503原因、成功P99、心跳最大间隔、日志积压年龄/排空、任务/恢复完成与数据库锁等待。通过标准沿用原驱动：页面全部200、P99<5秒、心跳间隔<10秒、无租约和遥测过期、日志排空及生命周期完成；未降低门槛。可重试503不等于测试失败，也不能称零过载。

## 修改前基线与诊断限制

普通心跳续租不拿全局调度锁；STARTING转运行的心跳需要`fast_lock`，拿不到调度锁立即返回可重试503。恢复控制也可能竞争该锁。入口或连接等待增大不改变这条路径，不把scheduler_lock统计成connection_pool。后续按用户要求另立 `narrow-execution-state-locks` 优化执行锁，见[锁审计](../../execution-lock-scope.md)。

全部测试使用隔离数据库。本轮不跑全量测试或小时级长测；修改配置需同一指纹分发所有角色、逐副本重建验证，不能只重启某一个API容器。

诊断精度边界：测试驱动将`control plane busy; retry shortly`统一归类为`scheduler_lock`。恢复reconcile中的Run/grant行级NOWAIT冲突也返回同一消息，因此恢复类不能据此统计精确的全局锁次数，更不能确定当时持锁者。心跳这条消息在STARTING分支由fast_lock产生，来源明确；修改后已按实际来源细分 reason，不与基线的粗分类直接等同。

原始聚合结果在 `comparison.json`，保留A/B/C/D、C复验及修改后结果；包含SQL锁采样、接口分布、任务与恢复证据。修改前统一归类的291次 `scheduler_lock` 包含无法区分的行锁，不能将其与修改后的5次全局锁直接做同口径百分比比较。总体503与心跳503口径一致。
