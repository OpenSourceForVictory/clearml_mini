# 双进程混合负载专项（2026-11-23）

本页以下“生产未切换/尚未部署”描述保留各轮隔离压测当时的状态；本机平台随后已完成发布，见[发布与真机验证](../README.md)。隔离压测结果仍不能直接代表生产容量。

`backend/tests/control_plane_load.py --split-api` 在独立 PostgreSQL 测试库中启动两个真实 API 进程，并用项目的 Nginx 路由配置在随机回环端口接入。每档结束后停止网关/API、删除临时数据库；未连接或重启当前平台。每 Worker 独立 HTTP 客户端，模拟一个运行执行、每约 2 秒心跳/服务健康/产物登记/领取、独立日志生产及每约 5 秒 Agent 遥测。业务程序和调度分配循环没有运行；完成/清理、Web 交互和多卡也未模拟，故不符合 OpenSpec 5.1/5.2 的完整容量验收。

全部短测结束时租约过期和遥测 SQL 过期均为 0。200 Worker 旧统一池配额下 Agent 观察入口发生 1036 次 `request_concurrency` 503；保持每进程总连接上限 20 不变，将观察池从 2 增到 4、普通池从 10 减到 8 后，Agent 503 降至 278 次，但日志入口拒绝从 2174 增到 2876、心跳拒绝从 140 增到 238。**末次 Agent 成功距结束**不是全程最大相邻上报间隔。单轮结果有波动，不能以 8/5/4 的一次通过宣称 200 Worker 容量。

此前将**可选双进程覆盖配置**调整为按进程职责分配，但两个进程仍各创建五类池：普通进程普通/控制/观察/结果/调度为 10/1/4/3/1（19 个最大连接），控制进程为 1/8/1/1/1（12 个），合计 31，低于旧统一池两进程 40。压测器用 `--role-aware-pools --ordinary-pool 10 --control-pool 8 --observation-pool 4` 复现这一**历史配置**。200 Worker 短测 Agent 503 为 377、心跳 503 为 107，日志入口 503 为 2923，所有日志最终确认；100 Worker 短测 Agent 503 为 56、心跳 503 为 0。按角色配额改善观察新鲜度，却仍有可重试拒绝和最高约 14.53 秒的日志待发年龄，不能代替长期/完整链路验收；生产平台未切换。

用户指出新增的分类入口并发闸门不应仅凭连接池数字限制 100 Worker。对照实验中，`--no-backpressure` 关闭入口闸门并沿用旧数据库会话，即使控制与普通 API 已拆分，100 Worker 的普通路径严重排队：60 秒内 2625 次传输错误，100 条遥测 SQL 均过期，日志最终仅确认 79/3000。此配置未采用。此前候选用 `--no-admission` 关闭**分类入口闸门**，保留独立进程、分类有界数据库池和短连接等待；100 Worker 短测通过，心跳 2901 次均 200，最长心跳间隔 3.85 秒，Agent 最后成功距结束 5.84 秒，3000 条日志全部确认，租约和遥测 SQL 无过期。仍有 96 次连接池 503（Agent 35、日志 25、产物 26、领取 10），另有 743 次领取的调度锁 503，均为可重试失败。它说明池大小不是 HTTP 入口并发上限，也说明取消入口闸门后不能取消数据库边界；尚未验证长时负载、真实业务与调度分配。双进程 Compose 覆盖配置仍采用 `DB_ADMISSION_ENABLED=0`，池大小现已改为下文 40/40；生产未切换。

继续核对发现上述 31 个连接上限中有 5 个来自永远不会被该角色路由使用的池。此前候选改为两进程仍读取相同的五类额度 10/8/4/3/1，但普通进程只创建普通/观察/结果/调度 10/4/3/1，控制进程只创建控制 8；该历史候选合计上限 26。单进程仍创建五类池。隔离压测关闭了调度线程，因此普通进程本轮实际只创建 10/4/3，两个进程合计 25。按角色建池后 5 Worker 冒烟 135 次请求均 200；100 Worker 60 秒短测通过，最长心跳间隔 3.59 秒、Agent 末次成功距结束 5.82 秒、日志 3000/3000 确认、租约和遥测 SQL 无过期。普通侧连接池 503 为 247 次，领取调度锁 503 为 682 次；与上一轮同档的 96/743 次有波动，不能宣称删去闲置池提升了吞吐。两轮都没有真实调度分配或模型进程。

按用户要求将**当前可选双进程配置**改为每进程最多 40 个连接：五类额度 23/40/9/7/1，普通 API 实建普通/观察/结果/调度池共 40，控制 API 仅建控制池 40。双进程入口不再把 AnyIO 默认同步线程额度额外增到 43。隔离压测关闭调度线程，因此该压测实建普通 39 + 控制 40 个最大连接；正式覆盖配置普通侧另有 1 个调度池连接。5 Worker 冒烟通过（134 个 200、1 个可重试 503）；100 Worker 60 秒短测通过，心跳 2901 次均 200、最长间隔 4.00 秒，Agent 末次成功距结束 5.86 秒，日志 3000/3000 确认且最终无待发，租约和遥测 SQL 均无过期。总计 51 次连接池 503（Agent 20、日志 11、产物 16、领取 4），另有 731 次领取调度锁 503；短测无真实调度分配、完成/清理、Web 或模型业务。PostgreSQL 当前 `max_connections=100`，生产还有其他连接，因此 80 个 API 理论上限会明显压缩余量；尚未部署到当前平台，也不能凭短测承诺长期 100 Worker 容量。

随后按用户要求启动 100 Worker、目标 30 分钟的同配置长测；连续 24 个 30 秒采样到 **720.87 秒**时，36,000 条日志均已确认，采样点待发量与最老待发年龄始终为 0，最差心跳间隔维持 2.54 秒，采样时心跳/日志/Agent 入口拒绝均为 0。用户明确指出指标没有随时间恶化时可以停止，故主动中断，退出码 130；测试 API、网关及临时数据库已清理。中断后没有完成最终租约/遥测 SQL 检查，**不记为 30 分钟通过**，也不推断长期 100 Worker 容量。期间约 118 秒运行了另一隔离 PostgreSQL 的相关接口测试；两者共享宿主机 CPU/磁盘，进度采样未见心跳与积压尖峰。原始[提前停止进度](split-40each-100-early-stop-progress.jsonl)保留。

故意压缩普通池的双进程负载中，日志最老待发约 58.87 秒，额外排空 5 秒后仍有 564 条待发；控制心跳和服务健康均无入口拒绝，成功响应 P99 分别约 0.028/0.021 秒。它验证该短时故障注入中普通流量没有挤占控制进程，但**没有**验证完成/清理与日志排空解耦，也不能证明持续负载下无数据库/主机资源竞争。

单 API 的 100 Worker 持续观察原计划 30 分钟。按用户要求在约 5.5 分钟主动中断；最后一条 330.87 秒进度显示 16500 条日志生成、16491 条确认、9 条待发，最长心跳间隔 4.57 秒。中断后测试 API 与数据库均已清理，但没有正常结束的最终租约/遥测 SQL 检查，不能记为 30 分钟通过。
