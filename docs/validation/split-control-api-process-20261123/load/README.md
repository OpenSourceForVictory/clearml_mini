# 双进程混合负载专项（2026-11-23）

`backend/tests/control_plane_load.py --split-api` 在独立 PostgreSQL 测试库中启动两个真实 API 进程，并用项目的 Nginx 路由配置在随机回环端口接入。每档结束后停止网关/API、删除临时数据库；未连接或重启当前平台。每 Worker 独立 HTTP 客户端，模拟一个运行执行、每约 2 秒心跳/服务健康/产物登记/领取、独立日志生产及每约 5 秒 Agent 遥测。业务程序和调度分配循环没有运行；完成/清理、Web 交互和多卡也未模拟，故不符合 OpenSpec 5.1/5.2 的完整容量验收。

全部短测结束时租约过期和遥测 SQL 过期均为 0。200 Worker 旧统一池配额下 Agent 观察入口发生 1036 次 `request_concurrency` 503；保持每进程总连接上限 20 不变，将观察池从 2 增到 4、普通池从 10 减到 8 后，Agent 503 降至 278 次，但日志入口拒绝从 2174 增到 2876、心跳拒绝从 140 增到 238。**末次 Agent 成功距结束**不是全程最大相邻上报间隔。单轮结果有波动，不能以 8/5/4 的一次通过宣称 200 Worker 容量。

随后将**可选双进程覆盖配置**调整为按进程职责分配，而非提高所有池：普通进程普通/控制/观察/结果/调度为 10/1/4/3/1（19 个最大连接），控制进程为 1/8/1/1/1（12 个），合计 31，低于旧统一池两进程 40。压测器用 `--role-aware-pools --ordinary-pool 10 --control-pool 8 --observation-pool 4` 复现这一配置。200 Worker 短测 Agent 503 为 377、心跳 503 为 107，日志入口 503 为 2923，所有日志最终确认；100 Worker 短测 Agent 503 为 56、心跳 503 为 0。按角色配额改善观察新鲜度，却仍有可重试拒绝和最高约 14.53 秒的日志待发年龄，不能代替长期/完整链路验收；生产平台未切换。

用户指出新增的分类入口并发闸门不应仅凭连接池数字限制 100 Worker。对照实验中，`--no-backpressure` 关闭入口闸门并沿用旧数据库会话，即使控制与普通 API 已拆分，100 Worker 的普通路径严重排队：60 秒内 2625 次传输错误，100 条遥测 SQL 均过期，日志最终仅确认 79/3000。此配置未采用。最终候选用 `--no-admission` 关闭**分类入口闸门**，保留独立进程、分类有界数据库池和短连接等待；100 Worker 短测通过，心跳 2901 次均 200，最长心跳间隔 3.85 秒，Agent 最后成功距结束 5.84 秒，3000 条日志全部确认，租约和遥测 SQL 无过期。仍有 96 次连接池 503（Agent 35、日志 25、产物 26、领取 10），另有 743 次领取的调度锁 503，均为可重试失败。它说明池大小不是 HTTP 入口并发上限，也说明取消入口闸门后不能取消数据库边界；尚未验证长时负载、真实业务与调度分配。双进程 Compose 覆盖配置现采用 `DB_ADMISSION_ENABLED=0`，生产未切换。

故意压缩普通池的双进程负载中，日志最老待发约 58.87 秒，额外排空 5 秒后仍有 564 条待发；控制心跳和服务健康均无入口拒绝，成功响应 P99 分别约 0.028/0.021 秒。它验证该短时故障注入中普通流量没有挤占控制进程，但**没有**验证完成/清理与日志排空解耦，也不能证明持续负载下无数据库/主机资源竞争。

单 API 的 100 Worker 持续观察原计划 30 分钟。按用户要求在约 5.5 分钟主动中断；最后一条 330.87 秒进度显示 16500 条日志生成、16491 条确认、9 条待发，最长心跳间隔 4.57 秒。中断后测试 API 与数据库均已清理，但没有正常结束的最终租约/遥测 SQL 检查，不能记为 30 分钟通过。

第一次双进程 5 Worker 冒烟测试完成请求后，压测器汇总仍读取旧 `api-5.log`，触发 `FileNotFoundError` 并退出 1；修复为读取两个进程日志后，5 Worker 冒烟通过（135 个 200）。失败是压测工具文件名缺陷，原始输出保留在本机 `.runtime/backpressure-split-smoke-20261123/`，没有据此判定 API 业务失败。随后网关渲染规则增加缺失标记拒绝测试，隔离 PostgreSQL 下三组专项测试共 **92 passed、0 skipped**；全量及项目覆盖率门槛本轮未运行。

取消入口闸门后重跑同三组专项：**101 passed、0 skipped**；按 `docs/code-coverage.md` 相同 coverage 配置采集的定向报告，`backend/app/db_budget.py` 行 95.76%、分支 92.65%，`backend/app/main.py` 行 43.97%、分支 11.63%。后者大量无关接口未由定向集合执行，不能据此称目录或全项目覆盖率达标；本轮没有运行全量覆盖率脚本。
