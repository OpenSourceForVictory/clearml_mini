# 数据库容量与业务时延验收

本文定义待验证的验收目标，不代表已达到生产SLA。连接硬上限、应用池预算、实际吞吐能力分别记录；任何一项不能替代另两项。

## 当前基线

2026-11-26本机核对：PostgreSQL max_connections=200，超级用户预留3；应用预算180、运维等总余量20（包含预留，不重复相加），实际配置池合计168。执行控制2副本×12=24；交互8副本×(操作3+长操作1+页面10)=112；Worker领取6+结果7+观察8+调度1=22；批量10。池无overflow，不互借；它们仍共享数据库CPU、磁盘、WAL和锁。连接按需建立，168不等于168条查询持续并行。

分类取连接等待：控制/用户操作/长操作1秒，页面3秒，领取/结果/观察/批量0.5秒。配置覆盖通用0.25秒。SQL截止预算：Worker4秒，普通交互12秒，长操作30秒；包含入口排队消耗，不能视为任意Python函数或整个HTTP响应的硬终止时间。线程名额也不等于数据库连接数。

## 候选业务目标

以下是验收目标，尚未全部测量或实现为自动门槛；原测试判定不降低，失败仍保留。

| 业务 | 目标 |
|---|---|
| 心跳、续租、取消/状态控制轮询 | API端到端P99≤1秒；无租约误过期、重复执行或错误释放资源 |
| 领取、结果上报、用户管理操作 | API端到端P99≤2秒，重试幂等；任务启动另算调度/轮询和程序准备时间 |
| 批次列表、详情、监控 | 各路径P95≤1秒、P99≤3秒，不把快接口均值掩盖慢详情 |
| 关键通道获取数据库连接 | 等待P99≤100毫秒；现有首次获取连接日志可分类汇总，但不覆盖后续重新获取，不能从HTTP耗时推算 |
| 日志、产物字节流 | 可排队或限流，积压年龄/数量不能持续增长，不拖慢关键控制 |

普通非故障额定负载下，关键请求非预期失败为0；可重试503单独统计初次失败率、重试完成时间和最终失败率。故障注入按明确窗口与恢复目标判定，不放宽正常场景。低样本操作给出样本量和最大值，不以1次请求的P99当稳定统计。

## 可重复负载

固定版本、12进程拓扑、线程与准入额度、数据规模和硬件，只单独改变池大小或连接等待。基线168；扩大组180（每交互操作池3→4，领取6→8，结果7→9）；等待组保持168，只将操作/长操作1→2秒、领取/结果/观察/批量0.5→1秒。均不修改生产配置。

初筛100独立模拟用户每5秒查询、100设备Worker、100任务批次、10个模拟命令执行槽，叠加日志、Agent遥测和恢复生命周期。此轮模拟基础心跳2秒，是保守旧节点负载；不能宣称测到了新Worker5秒带来的收益。100Worker不等于100台多卡节点或100个真实模型。

短测180秒仅筛选。全量覆盖率并行运行的结果标记背景负载；本次另在无全量覆盖率争抢时完成三档对照及基线复测，并进行30分钟持续负载。若要据此扩大生产连接池、承诺容量上限或时延SLA，还需交换运行顺序并使每档至少重复3次、按负载阶梯寻找延迟拐点。租约在实际请求窗口内按10秒与边界时点采样，压测结束后的日志排空另记 expired_leases_after_drain；不得用收尾阶段自然过期否定窗口内心跳。100任务全部完成后不能称持续任务调度负载：长测使用持续批次模式，另做100任务队列专项。不能因168/180两档都通过就声称180是最大容量。

## 测量与决策

现有工具记录按路径请求数/状态码/P95/P99、503 reason、心跳间隔、日志生成与确认/积压、生命周期正确性、结束时连接数。开启 `DB_BUDGET_DIAGNOSTICS=1` 时，四角色 API 按类别记录入口准入成功/拒绝的等待，以及连接池每次获取的等待与超时，包括事务结束后再次获取；负载工具汇总 `admission_wait_ms` 和 `pool_checkout_wait_ms` 的样本数、P95/P99、超时数。原有 `initial_checkout_wait_ms` 仅表示 `main.db` 首次显式获取连接，不能再当成全部连接等待。诊断只输出类别、结果、时长和连接使用数，不记录令牌、SQL 或请求体；详细诊断会增大日志量，仅用于短时验证。尚缺连接持有时间、SQL/事务时延、租约过期精确时点。control_plane_metrics 每约10秒采样PG活跃/等待连接、未授予锁、事务/缓存/WAL计数；数据库CPU/IO通过可选 `--postgres-container` 采样。结束连接数不是峰值；request_budget不是连接池耗尽的充分证据。

数据库pg_stat_activity的等待采样不能直接提供连接池排队时间；连接池在应用进程内等待，必须在取连接边界测量。周期采样可能漏掉瞬时峰值，日志分类统计也不等于完整调用链追踪。吞吐不再增长且P99/锁等待/积压上升时，继续加连接可能放大竞争。

- connection_pool增加、SQL较快且数据库有余量：才考虑扩大该池。
- request_concurrency增加：检查入口名额、请求持有时长，不能直接归因池不足。
- execution_lock/scheduler_lock/lock_timeout增加：定位持锁事务、冲突对象及持有时长；不得为压测分数取消正确性锁。
- SQL变慢、CPU/IO饱和：先优化查询/事务或扩数据库资源；延长等待仅吸收短暂突发。

最终报告必须列版本、负载、配置、背景干扰、分路径指标、失败/跳过、最大已验证规模和未验证范围。没有数据的指标明确写未测，不用硬上限代替有效容量。

## 本次配置决定（2026-11-26）

独立PostgreSQL `max_connections=200`；12个API进程保持当前合计168连接池上限、预算180和余量20。无全量测试干扰的100模拟Worker/100Web用户/100任务180秒对照中，修正压测脚本收尾竞态后的168档、180档及仅延长等待档均通过，连接池超时均为0。控制池每次取连接P99约37/38/34毫秒，首次503分别21/27/33次，主要是执行/调度锁而非连接池；未见增池或延长等待带来明确收益。初始168档曾有一次产物上传409：模拟执行完成与可选上传并发，已保留失败证据、串行收尾并在同负载复测通过。完整口径见[验证记录](validation/heartbeat-cadence-20261126/README.md)。

30分钟持续批次负载下100模拟Worker、100Web用户最终通过，72,819条日志全部确认、运行窗口租约过期0；连接池无超时，数据库10秒采样连接峰值137。保持168，不因PostgreSQL硬上限200而自动扩大池。当前结论仅覆盖上述模拟负载及本机硬件，不等于100个真实模型占用GPU/NPU、800个多卡Worker、各档三轮统计稳定性或已找到数据库吞吐拐点。业务时延表仍为目标，不宣称生产SLA已验收。

百任务并行专项另记录 `batch_execution_peak`：按同一批次各执行的开始/结束时间计算实际重叠数量，不能用“批次最大并行数=100”或“100任务均成功”替代。命令执行槽不会发送恢复控制轮询；压测门槛按实际持续控制Worker数计算，报告须写明两组各有多少Worker。

发布后阶梯复验（2026-11-26）：保持168池额度与100模拟Web用户，各做一次90秒混合负载。150模拟Worker通过；200档出现73次HTTP传输错误（Web聚合71次）而未通过，首次503从187增至1377，主要是入口准入拒绝。两档连接池超时均为0，200档连接采样峰值139/数据库硬上限200、活跃查询峰值8，运行窗口租约过期0且日志最终全部确认。按现有数据，压力首先表现在API入口/请求链路，**不能归因为数据库连接数耗尽**；采样也不足以排除短时数据库CPU、锁或网关影响。负载工具现将Web传输异常按异常类名与30秒时间窗单独统计，不记录包含URL或令牌的异常消息，也不将其误计为503 busy reason。同配置200档复测失败，17次Web `ConnectError` 均在0～30秒启动窗口，池超时仍为0、连接采样峰值134；这支持连接建立突发问题的推断，尚不能区分网关、主机socket队列和压测客户端。下一步需记录底层安全错误码与网关连接状态，复跑临界档至少三次，再决定调整入口并发、进程数或其他资源。保持生产168不变。详细证据见[发布后阶梯和真机算子结果](validation/heartbeat-cadence-20261126/postrelease-scale-operators.json)。

后续200档诊断对照：默认压测进程文件描述符软上限1024时又出现13次和29次Web `ConnectError`，均在开始后30秒内；后一轮描述符采样峰值1009/1024。网关监听队列采样峰值0/511，内核ListenOverflows/ListenDrops增量均为0。将本次压测进程软上限提高到8192后，同样200 Worker/100 Web、90秒负载一次通过、Web传输错误0，采样描述符峰值860；各轮数据库池超时0、连接峰值不超过139/200、租约过期0、日志7524/7524确认。高上限单次通过支持“测试进程文件描述符额度影响结果”，但API子进程同样继承这个额度，尚未区分是客户端还是API进程描述符受限；也不能把一次90秒通过当生产SLA。工具现只保留安全异常类名、可提取的数字errno及时间窗，且在压测客户端预算大于RLIMIT_NOFILE软上限时启动前报错；200 Worker/100 Web的预算为1220。运行该档先执行`ulimit -n 8192`并核对隔离数据库，生产连接池保持168。完整对照与失败记录见[验证记录](validation/heartbeat-cadence-20261126/README.md)。

压测工具可用 `--command-hold-seconds 0..60` 让模拟命令任务在领取后保持运行，再上报结果；默认0保持旧负载。并行目标以 `batch_execution_peak` 验收，报告保持时间、实际重叠峰值及批次完成情况。保持时间需低于所测租约并让Worker持续心跳，不能把模拟保持等同真实模型算力占用。

高并行初筛须同时报告 `batch_full_overlap_seconds`，表示同批次所有完成执行共同运行的时间。2026-11-26隔离PG初筛在40秒模拟保持下100任务峰值并行100、共同运行约15.15秒，详见validation/heartbeat-cadence-20261126/parallel-100-preliminary.json；该数据与全量测试同机并行，不能代表真实模型或30分钟稳定性。
