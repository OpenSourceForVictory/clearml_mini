# 数据库容量与业务时延验收

本文定义待验证的验收目标，不代表已达到生产SLA。连接硬上限、应用池预算、实际吞吐能力分别记录；任何一项不能替代另两项。

## 当前基线

2026-11-26本机核对：PostgreSQL max_connections=200，超级用户预留3；应用预算180、运维等总余量20（包含预留，不重复相加），实际配置池合计168。执行控制2副本×12=24；交互8副本×(操作3+长操作1+页面10)=112；Worker领取6+结果7+观察8+调度1=22；批量10。池无overflow，不互借；它们仍共享数据库CPU、磁盘、WAL和锁。连接按需建立，168不等于168条查询持续并行。

分类取连接等待：控制/用户操作/长操作1秒，页面3秒，领取/结果/观察/批量0.5秒。配置覆盖通用0.25秒。SQL截止预算：Worker4秒，普通交互12秒，长操作30秒；包含入口排队消耗，不能视为任意Python函数或整个HTTP响应的硬终止时间。线程名额也不等于数据库连接数。

## 候选业务目标

以下是验收目标，尚未全部测量或实现为自动门槛；原测试判定不降低，失败仍保留。

| 业务 | 目标 |
|---|---|
| 心跳、续租、取消/状态控制轮询 | API端到端P99≤1秒；无租约误过期、重复执行或错误释放资源 |
| 领取、结果上报、用户管理操作 | API端到端P99≤2秒，重试幂等；任务启动另算调度/轮询和程序准备时间 |
| 批次列表、详情、监控 | 各路径P95≤1秒、P99≤3秒，不把快接口均值掩盖慢详情 |
| 关键通道获取数据库连接 | 等待P99≤100毫秒；现有首次获取连接日志可分类汇总，但不覆盖后续重新获取，不能从HTTP耗时推算 |
| 日志、产物字节流 | 可排队或限流，积压年龄/数量不能持续增长，不拖慢关键控制 |

普通非故障额定负载下，关键请求非预期失败为0；可重试503单独统计初次失败率、重试完成时间和最终失败率。故障注入按明确窗口与恢复目标判定，不放宽正常场景。低样本操作给出样本量和最大值，不以1次请求的P99当稳定统计。

## 可重复负载

固定版本、12进程拓扑、线程与准入额度、数据规模和硬件，只单独改变池大小或连接等待。基线168；扩大组180（每交互操作池3→4，领取6→8，结果7→9）；等待组保持168，只将操作/长操作1→2秒、领取/结果/观察/批量0.5→1秒。均不修改生产配置。

初筛100独立模拟用户每5秒查询、100设备Worker、100任务批次、10个模拟命令执行槽，叠加日志、Agent遥测和恢复生命周期。此轮模拟基础心跳2秒，是保守旧节点负载；不能宣称测到了新Worker5秒带来的收益。100Worker不等于100台多卡节点或100个真实模型。

短测180秒仅筛选。全量覆盖率并行运行的结果标记背景负载；最终复验应在无覆盖率争抢时重复基线与候选，交换顺序/重复至少3次，并进行30分钟持续负载。租约在实际请求窗口内按10秒与边界时点采样，压测结束后的日志排空另记 expired_leases_after_drain；不得用收尾阶段自然过期否定窗口内心跳。100任务全部完成后不能称持续任务调度负载：长测须使用持续批次模式，另做100任务队列专项。再按负载阶梯寻找延迟拐点，不能因168/180两档都通过就声称180是最大容量。

## 测量与决策

现有工具记录按路径请求数/状态码/P95/P99、503 reason、心跳间隔、日志生成与确认/积压、生命周期正确性、结束时连接数。已有main.db首次s.connection()耗时日志（含首次建连成本），工具汇总为initial_checkout_wait_ms；可从日志补按类别统计，但不覆盖所有会话和后续重新获取。尚缺逐请求入口等待、完整连接获取/持有时间、SQL/事务时延、租约过期发生时点。control_plane_metrics已每约10秒采样PG活跃/等待连接、未获准锁、事务/缓存/WAL计数；数据库CPU/IO通过可选--postgres-container采样，本轮未传此参数，缺少容器资源序列。结束连接数不是峰值；request_budget不是连接池耗尽的充分证据。

需要补采样并按角色/类别汇总，避免记录token、完整SQL参数或业务正文。数据库pg_stat_activity的等待采样不能直接提供连接池排队时间；连接池在应用进程内等待，必须在取连接边界测量。吞吐不再增长且P99/锁等待/积压上升时，继续加连接可能放大竞争。

- connection_pool增加、SQL较快且数据库有余量：才考虑扩大该池。
- request_concurrency增加：检查入口名额、请求持有时长，不能直接归因池不足。
- execution_lock/scheduler_lock/lock_timeout增加：定位持锁事务、冲突对象及持有时长；不得为压测分数取消正确性锁。
- SQL变慢、CPU/IO饱和：先优化查询/事务或扩数据库资源；延长等待仅吸收短暂突发。

最终报告必须列版本、负载、配置、背景干扰、分路径指标、失败/跳过、最大已验证规模和未验证范围。没有数据的指标明确写未测，不用硬上限代替有效容量。

百任务并行专项另记录 `batch_execution_peak`：按同一批次各执行的开始/结束时间计算实际重叠数量，不能用“批次最大并行数=100”或“100任务均成功”替代。命令执行槽不会发送恢复控制轮询；压测门槛按实际持续控制Worker数计算，报告须写明两组各有多少Worker。

压测工具可用 `--command-hold-seconds 0..60` 让模拟命令任务在领取后保持运行，再上报结果；默认0保持旧负载。并行目标以 `batch_execution_peak` 验收，报告保持时间、实际重叠峰值及批次完成情况。保持时间需低于所测租约并让Worker持续心跳，不能把模拟保持等同真实模型算力占用。
