# 批次暂停、恢复与整批取消

入口：「CS 评测批次 → 评测集合运行 → 查看批次」。列表和详情同时显示执行状态与“调度已暂停/开启”。暂停批次仍可能有任务运行，两者不是同一状态。

- **暂停后续调度**：撤回未被 Worker 领取的预留，释放其 GPU/CPU/内存额度，任务保持原尝试和提交顺序。已领取的 STARTING/RUNNING 继续执行，包括已领取但容器还未启动的任务。其他批次继续公平调度。
- **恢复调度**：允许排队任务重新参与调度，不撤销取消请求，不自动重试任何终态任务。
- **取消整批**：确认后先暂停调度，再直接取消等待及未领取任务，对已领取任务请求停止。成功/失败等已有终态记录和回合、日志、产物保留。按钮反馈“请求已接受”不代表容器全部停止。

取消中和待清理数量可能重叠，不能相加理解为任务总数。Worker 失联时仍使用现有租约、隔离及清理确认协议；资源可能继续被占用，不能强行重试未清理的旧执行。

暂停期间可以重试符合条件的任务，但新尝试会显示“本批次已暂停后续调度”，直到恢复。已取消任务使用现有单项重试；“批量失败补跑”仍只选择失败/超时任务。

控制确认固定用户发起时的版本。页面轮询不会更换版本，网络错误后重试原请求不会覆盖之后的控制决定。遇到版本冲突，请关闭确认，核对最新状态后重新操作。筛选与历史尝试保持不变。

## API

`POST /api/v1/batches/{id}/control`

```json
{"action":"pause","expected_revision":0}
```

`action` 支持 `pause`、`resume`、`cancel`。只允许本人或管理员；其他用户返回 404。版本不一致返回 409 且不写入。每个成功请求，包括已暂停再次暂停，都会推进控制版本。

返回 `action`、`scheduling_paused`、`control_revision`、`control_updated_at` 和 `counts`：

| 字段 | 含义 |
|---|---|
| withdrawn | 本次暂停撤回的未领取预留 |
| cancelled | 本次直接取消的等待/未领取任务 |
| cancel_requested | 本次请求停止的已领取任务 |
| already_cancelling | 此前已经取消中的任务 |
| terminal_unchanged | 本次整批取消保留的终态任务 |

批次列表、详情和 monitor 新增上述控制状态字段，原 `status` 聚合字段保持兼容。monitor 的 `summary.cancel_requested_tasks` 为取消中数量，`cleanup_pending_tasks` 为取消中或终态尚未确认清理数量，正常 STARTING/RUNNING 不计入“待清理”。排队诊断新增 `batch_paused`。

## 迁移与回退

迁移 `g730b12` 在 `f629a11` 后新增字段，旧批次默认允许调度且版本为 0，无需升级 Worker。

旧 API 不理解暂停标记，切换旧镜像可能导致暂停任务被调度。回退前排空活动执行、确认所有清理，并处理暂停批次内的排队任务；降级迁移检测到活动执行、未清理执行或暂停的排队任务时拒绝执行。不能只切换旧镜像绕过该要求。恢复数据库快照会丢失新结果，不属于普通代码回退步骤。
