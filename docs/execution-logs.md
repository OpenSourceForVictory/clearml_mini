# 执行日志

日志 v2 是滚动窗口，不是完整业务日志归档。平台每个执行最多保留 256 KiB 正文或 256 个块；新内容到达后淘汰旧块。旧 Worker 仍使用原接口，保留最前 256 KiB。Worker 0.21.0 通过 bounded_logs_v2 能力协商启用；宿主机和注入当前 Runner 的容器支持 v2，旧镜像内置 Runner 和旧执行 journal 保持旧模式。此变更仍待发布，不能据此认为已纳管节点已自动升级。

## API

Worker POST `/api/v1/worker/executions/{execution_id}/logs-v2`：`sequence` 从 0 单调增长，`content` UTF-8 最多 16 KiB，`stream` 为 stdout/stderr/system，`gap` 表示采集缺口。空内容仅在 gap=true 时允许；拒绝 NUL。请求必须使用拥有该执行槽位的 Worker 凭据，且执行租约有效。

同序号同内容重试不重复写入；不同内容冲突返回 409。已淘汰且无法校验摘要的过旧序号返回 accepted=false、resync=true、next_sequence，发送方不能将其当作当前正文被接受。每个发送方仅有一个持久 pending 块。新内容在执行关闭后被拒绝。

任务日志 GET 保留原地址与 after/limit，增加 version、first_sequence、gap、truncated、complete；chunks 增加 stream/gap。跨窗口游标会显式提示缺口。旧表读取兼容，不改写历史日志。

## 存储、并发和升级

迁移 y518b90 新增 run_log_states/run_log_chunks，保留 run_logs；先备份和升级 API 数据库，再部署 API，节点版本尚未启用前不产生 v2 记录。新表有执行外键，批次删除按子表先于 Run 清理。v2 日志以日志状态行锁保护序号、游标及配额；同一执行的追加与完成/清理通过执行专属事务锁排序。日志读取执行记录时只取防删除的键共享锁，运行中的心跳可继续更新租约。旧 `/logs` 接口仍更新 Run.log_bytes，因此旧 Worker/旧镜像的日志与心跳仍可能竞争执行行；需通过能力协商启用 v2 才有该隔离。新路径不更新旧 Run.log_bytes，无数据库迁移。

降级迁移会删除 v2 日志表及数据，必须先停止新 v2 执行、清理在途执行并备份；一般回退代码保留新增表。不能将回退描述为保留 v2 历史读取能力。

测试：test_execution_logs_v2.py、test_execution_logs_postgres.py；后者只在一次性 PostgreSQL 数据库中执行，包含迁移保留旧日志、上传幂等、结束/删除竞态，以及心跳持锁时写日志、日志状态持锁时续租和终态两种先后顺序。相关 56 项专项回归结果见 [控制面验证记录](validation/control-plane-backpressure-20261123/README.md)。测试通过数量不替代项目覆盖率门槛。

## 节点采集与界面

节点环形文件最多 256 个记录槽，每块最多 2048 UTF-8 字节；即使字符被 JSON 转义，诊断日志仍控制在 4 MiB 内。stdout/stderr 都在运行期间采集。Docker 使用有界尾部接续，断线或重启标记缺口；不承诺完整历史或跨流严格时间排序。

另外保留最多 7 KiB 的 stderr 尾部快照，避免 Docker 延迟交付的大量 stdout 将最终错误挤出共同窗口。退出补传可能重复展示这段 stderr，并标记缺口；它不是完整错误日志归档。

上传独立于执行心跳，每请求最多 16 KiB，每 2 秒至多一次，失败退避最多 30 秒；未确认块先写入独立 `.logs` journal，避免被执行恢复的 `*.json` 扫描当作任务。退出前分别保留 stdout/stderr 的最新尾部，补传最多 5 秒，期间继续心跳。未补传完整或因启动取消、数据拒绝等异常提前结束时，完成请求标记日志缺口，不让日志故障无限阻塞结果和清理。

最终协议结果与回合事件独立保存，回合 journal 有单独 32 MiB 上限，超过上限明确失败，不静默丢弃事件。容器专用 `.mini-eval-protocol` 目录不作为业务产物上传。业务参数、登录环境继承、设备可见性和成功判定不变；常驻服务退出 0 仍不是服务持续运行成功。

客户端和服务实例面板展开后增量读取，关闭后停止轮询；终态日志读尽后停止自动刷新，可手动刷新。标注 stderr/system 来源；旧日志淘汰、采集断线或结束补传不完整时显示缺口提示。界面保留最新 256 KiB，不提供完整归档。

验证范围、失败记录和性能取舍见[有界日志验证](validation/bounded-execution-logs/README.md)。

## 按执行身份定位与独立日志

Worker 0.21.6（协议版本仍为 17）声明 `process_logs_v1`。API 对具有该能力的宿主机执行、支持 Runner 注入的容器执行启用独立采集。升级后新执行生效，旧执行保留原有日志，不补造历史回合文件。任务详情的 `execution_id` 与任务 ID、Run ID 不同；历史目录从节点登记记录读取，不按当前工作目录配置推测。

Runner 在真实业务子进程边界采集 stdout/stderr，仍保留原诊断输出。逐回合启动使用 `logs/episodes/<六位回合号>/`；整任务业务使用 `logs/business/`，服务实例使用 `logs/service/`，执行诊断使用 `logs/task/`。以上都位于该执行的 `runs/<execution_id>/` 下，不同服务实例及重试独立。以界面登记的实际路径为准。每个目录保存 JSONL 分片，根 `manifest.json` 保存代次、序号和完整性状态；不要手动修改索引。

整机日志配额默认不限制，不需要普通业务账号访问 Worker 私有账本，也没有启用跨账号配额申请通道。仍有单分片 4 MiB、单 scope 16 MiB、单执行 256 MiB 的有限预算；执行预算预留四分之一用于元数据及原子更新，因此正文可用量小于总预算。轮转淘汰旧分片，不删除结果或业务产物。日志随原执行数据保留策略清理，不是永久归档。

`runner/process_log_capture.py` 使用 1 MiB 有界队列（包含在写记录）、最多 8 KiB stderr 尾部及最多 8 KiB JSONL 记录。磁盘异常、队列满和关闭超时标记缺口，不改变程序退出码或协议结果；初始化失败保留旧诊断日志。业务退出后继承输出管道的后代最多等待 2 秒，日志写入关闭最多等待 2 秒。文件系统内核调用本身无法保证可中断。

`worker/process_logs.py` 用独立线程登记和处理按需读取，不等待执行心跳处理。Worker 私有登记绑定历史根路径、设备号/inode、execution_id 和 generation；分页拒绝路径穿越、符号链接、硬链接、FIFO、被替换的分片和跨执行游标。与执行清理共享短锁，竞争返回 busy。快速结束的业务 scope 可凭启动时的 task 登记在终态补登记，不能凭任意目录创建历史日志。

### 界面操作

任务尝试、批次回合和服务实例展开后，在已登记的日志按钮中选择执行诊断、公共日志、回合或服务实例日志。单进程多回合共用公共日志；未启动的回合不生成独立日志。抽屉支持复制执行 ID/目录、来源过滤、尾部刷新、加载更早日志及自动跟随；向上滚动暂停跟随，关闭停止正文轮询。

每页最多 64 KiB，翻页替换当前页；接口允许 16–64 KiB。下载以开始时的序号固定边界，最多 8 MiB，超出时明确失败，不冒充完整文件。超过单份容量或 96 页时保存编号分片，点击“下载下一分片”继续；全部分片固定首次读取结束序号，后续新增日志不混入。失败时本分片不生成，已下载分片不代表完整范围。缺口、截断和清理会明确提示；离线请求超时后可重试，原有平台诊断日志仍可查看。数据库保存目录索引、有限请求及页缓存，不保存整份节点文件。

## 0.21.7：轮转中断恢复

修正触发条件：轮转需要淘汰旧分片时，如果新索引提交失败，旧实现可能已删除该索引引用的文件，随后历史日志读取失败。

新版先在执行日志根目录写 `prune.json` 清理意图，再原子提交 manifest，最后删除已不被索引引用的分片。下一次写入或 Worker 同步时，在执行目录锁内恢复：未提交新索引则保留旧分片；已提交则完成清理。恢复核对执行/代次、scope、文件名、inode 和链接数，不按任意路径删除文件。不要手工删除或修改 prune.json。

格式变更不新增数据库迁移，不改变退出码、评测结果或原有日志目录。节点需更新 Worker/Runner 0.21.7 才具备该恢复逻辑；前端不需要新字段。真实进程中途退出测试覆盖提交前、提交后和删除后，不能等同于断电、网络文件系统故障或任意磁盘损坏恢复。完整验证及负载边界见 [功能组补测](validation/execution-group-logs-20261119/README.md)。

2026-11-19 [独立日志真机实验](validation/process-logs-live-20261119/README.md)覆盖隔离平台上的 GPU 宿主机/Docker、逐回合与公共日志、浏览器筛选下载及 Worker 重启读取；29 节点另验证双 NPU 同名子进程采集。它不代表生产平台已升级，也不替代平台调度双 NPU 服务验收。

## 0.21.8：普通业务账号的日志目录遍历

NPU 宿主机完整链路实测发现：父级工作目录只允许业务账号穿过、不允许列出其他执行时，旧采集器用只读句柄逐级打开目录会报 PermissionError，出现 `process log unavailable; business execution continues`；业务仍可正常运行，但页面可能仅有执行诊断，没有服务实例/回合独立日志。

0.21.8 使用 Linux O_PATH 逐级取得父目录句柄，只在最终日志根打开读句柄；仍逐级禁止符号链接、校验目录和文件身份。无需放开其他执行目录的读取权限。修复适用于 service/business/episode；日志格式、设备分配、业务退出码及协议不变，无新增数据库迁移。需更新节点组件中的 Runner，新启动执行生效；已丢失的旧独立日志不能补回，可查看原有诊断摘要。

修复前异常、回归测试和普通账号 NPU 双服务完整平台验收见 [NPU 日志验证](validation/npu-process-logs-platform-20261119/README.md)。

### SDK 下载包完整性

2026-11-20 补测发现 UI 下载的 SDK ZIP 与源码不同步，并且构建清单遗漏 process_log_contract/capture/store/run：普通自测能通过，启用独立日志的执行会缺模块。下载构建器现包含这些模块；回归在仓库外解压并运行真实采集子进程、核对退出码和已关闭 JSONL 日志。必须同时重新生成 `frontend/public/integration/mini-eval-sdk.zip` 并发布前端，旧下载文件不会自动更新。独立子进程内部不计为本次 Python 覆盖率。

管理设置中的手动服务实例也提供独立日志抽屉，按“执行历史”所选任务定位；同名实例不共享选择。抽屉显示节点/加速卡和读取来源，旧 Worker 无登记时继续提供原有诊断摘要。

## 独立日志预算同步

管理设置 → 机器 → 查看配置 → 数据保留 → 展开执行数据，可设置日志分片、单份日志、单次执行的字节预算（界面单位 MiB）。三者递增，分片至少 64 KiB，最大 1 TiB。整机总量不限制；这不影响已有执行数据保留策略。

保存只增加平台期望版本；每张卡的 Worker 0.21.11（process_log_policy_v1）独立持久化并回报生效版本。旧 Worker 显示需要升级。应用失败保留上次已确认配置，不把保存成功当成节点已生效。API 不等待节点磁盘操作。执行首次领取时冻结该卡已确认版本，重领、恢复以及之后降额都不改该执行；降额仅影响后续执行，不立即清理历史文件。配置同步在独立日志线程，最多每 30 秒一次，失败不阻断心跳和业务。

该配置需要数据库 b841e23；按[迁移指南](database-migration.md)先迁移再更新 API，随后按[节点升级说明](worker-upgrades.md)选择节点升级。Worker 状态文件同级的 `.log-policy` 保存本卡回执，不修改业务账号的 shell 环境。

独立日志实时尾部不使用目录上报序号截断，目录刷新滞后仍可看到新输出；下载才固定结束序号，包含当前已显示页，后续分片沿用同一范围。该修正只需更新前端，不需要迁移或节点升级。

尾部请求只复用请求发起后 3 秒内的已完成页；仍在排队/读取的相同请求继续合并。旧订阅者的页保持原 30 秒有效期，固定范围下载的缓存不变。全局 128 槽位及用户/节点并发上限继续生效。该缓存修正需更新 API，不需要数据库迁移或 Worker 升级。

日志登记/删除迟到回包、路径切换、staging、取消下载和万scope元数据预算的补验见[复合条款验证](validation/final-contract-audit-20261120/README.md)。取消或启动失败的日志可标记不完整，不能因程序终态而假称日志完整；万scope测试不等同于一万次业务运行性能承诺。

## 控制面暂时过载的交付行为（待发布）

Worker 0.21.16 的日志发送遇到 429/502/503/504 或传输超时时保留未确认片段及序号并退避重试；旧日志通道返回执行续租循环，新日志通道在独立线程重试。日志滚动容量和结束时有界排空规则不变，不能因此保证无限积压无丢失。暂时拒绝不应作为停止有效租约业务的理由；永久协议错误及真实租约过期仍按原规则处理。API 背压启用顺序见 [部署与运维](operations.md)。
