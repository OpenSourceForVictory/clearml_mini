# 可选执行限制

业务评测向导 → 客户端 → 勾选“不限制每项总执行时长”。API 对应 `client.timeout_seconds=0`；旧模板和遗漏该字段时仍采用原默认值。有限值仍受平台上限控制。不限仅取消总执行截止时间，启动超时、请求超时、心跳租约、取消和清理规则继续生效；服务端原有生命周期不变。

向导 → 资源 → 高级资源约束，可分别勾选“不限制 CPU 上限”和“不限制内存上限”。托管服务在“服务资源与运行变量”设置；有资源要求的模板通过资源表单设置。模板锁定 CPU/内存字段时不能更改对应限制选项。

选择不限仍须提供正数调度预约量：有模板最低值时初始采用该最低值，可以增加；没有模板资源要求时必须填写。比如最低内存 8 GiB、内存不限，则按 8 GiB 判断节点容量、剩余量和已有预约，容量不足仍排队；程序启动不附加 MemoryMax 或 Docker --memory。CPU 同理。实际超出预约的用量不保证可用，系统或上级 cgroup 限制仍然有效；GPU/NPU 可见卡和显存预约不变。

```json
{"resources":{"cpus":2,"ram_gb":8,"cpu_unlimited":true,"memory_unlimited":true}}
```

预约量保存在 Run.reserved_cpu / reserved_ram_gb；领取载荷 reserved_cpus / reserved_ram_gb 保留该数量，运行限制 cpus / ram_gb 对选择不限的轴传 0。业务参数中的同名值不会影响调度。原资源池默认值为 0 的旧规则不变，与本功能“正数预约、不设硬上限”不同。

宿主机不限时长采用 RuntimeMaxSec=infinity；Docker 跳过镜像内的定时 supervisor，直接启动适配入口，仍由 Worker 租约看门狗管理退出、取消和清理。不需要重建业务镜像来改变定时器。需要 Worker 0.19.0 / 协议 16 和对应 API、前端；旧 Worker 在预检、调度及领取时被拦截。无需数据库迁移。

### 真机发现的启动兼容修正

选择 CPU/内存不限时，systemd 可能不生成相应 cgroup 限额文件。Worker 0.20.1 仅检查实际要求限制的轴；有限轴的文件缺失仍视为失败，进程数检查保持原样。旧实现会因读取不存在的 cpu.max 失败，随后恢复时显示 host unit is missing。需要升级 Worker，不能只更新 API。新增 v1/v2 无控制器文件的回归用例；真机验收记录见 [部署验证](validation/episode-limits-live/README.md)。
