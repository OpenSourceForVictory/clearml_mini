# 节点资源采集与执行边界

Agent 1.1.0 管理节点控制和整机采样；Worker 0.11.0 管理任务进程、执行租约、日志、结果及清理。执行协议仍为9，新增字段通过 API 的资源来源响应协商。本次保留每GPU一个Worker的服务布局、执行日志格式和任务资源参数，尚未迁移为单节点多卡执行服务。

## 数据与控制路径

- Agent 的CPU、内存、GPU/NPU、磁盘、Docker采样在独立后台线程执行。每个探测最多一个在途线程，失败不能解释为资源空闲。默认采样间隔 15 秒，可在节点 Agent 配置中调整。
- CPU提供逻辑核数、1分钟负载及连续两次`/proc/stat`计数差分得到的利用率；首次样本不伪造CPU利用率。内存使用`MemTotal`和`MemAvailable`。
- Agent注册声明`resource_protocol=1`。平台保留采样完成时间，45秒后数据过期，重复心跳不能刷新旧样本有效期；未来时间戳关闭准入，节点需要正常时间同步。采样间隔若配置超过 45 秒，样本间隙可能使新任务等待。
- NVIDIA GPU样本包含UUID、总/空闲显存及利用率。平台同时检查槽位索引、UUID和总容量，避免把更换设备后的数据用于旧槽位。
- Worker收到`resource_source=agent`后停止周期性GPU探测；旧Agent或无Agent时仍由Worker后台采样。任务启动前的显存复核仍保留，这是执行保护，并非整机周期采集。
- Worker的存储探测、配置应用和兼容GPU采样由单一后台控制器处理，心跳只读缓存。缓存超过10秒后上报磁盘不可用，不领取新任务。配置线程未结束时也不领取，避免路径切换和任务启动竞争。
- Agent事件确认在控制线程落盘；没有变化不执行fsync。配置只有持久化成功才公布已应用版本，慢盘不会让心跳误报配置成功。
- Agent网络请求每通道最多一个在途请求，总等待期限5秒；控制许可与心跳使用独立通道，阻塞的DNS或慢响应不会积累无限线程。

NFS进入内核不可中断等待时，后台线程不一定能被终止。这里保证控制路径隔离和并发数量有界，不承诺消除内核故障。Worker启动恢复、执行日志及任务清理仍需其存储可用；本变更不把执行数据I/O声明为非阻塞。

## 调度消费

配置的CPU/内存容量仍作为管理员预算上限。新版Agent的有效主机样本提供物理容量与内存压力检查：

1. CPU总预留加新任务申请不得超过配置容量或探测核数。
2. 内存总预留加新任务申请不得超过配置容量或物理总内存。
3. 新任务内存加未启动任务预留不得超过实时可用内存；已运行任务的实际占用不重复扣减。
4. 主机采样失败、缺失或过期时，新任务等待；已有任务的租约续期独立进行。

GPU继续使用已有显存预留账本和实时空闲显存双重检查。CPU利用率作为监控信息，不当作可预留的CPU核数。此次没有修改每卡/节点/全局任务数限制；取消固定数量限制属于后续统一调度策略变更，不能将本次采集优化当作已完成该功能。

## 异构设备

`devices`清单以`kind`、`vendor`、`device_id`、`index`、`model`、`sampled_at`、`status`、`memory_total_mb`、`memory_free_mb`、`utilization_percent`和`execution_ready`描述设备。未获得的指标保留为null，不用0表示未知。

- NVIDIA：已实现采集和现有GPU槽位兼容。
- CPU-only：Agent不要求安装nvidia-smi，仍可报告CPU及内存；现有SSH自动纳管/任务槽位仍以GPU执行为主，不代表CPU-only纳管全流程已完成。
- 昇腾：已在8卡910B3、npu-smi 25.5.1上只读验证批量采样。静态映射区分物理卡号、芯片号和逻辑设备号，过滤MCU；动态读取HBM总量/可用量、AI Core利用率和健康状态，设备标识为节点范围的PCI地址加芯片号。静态映射缓存60秒，之后每轮一次批量命令。未知表头、缺失设备或非法容量失败关闭。执行适配尚未完成，因此execution_ready=false，不能通过CUDA槽位参与执行。

昇腾完整支持仍需要驱动与CANN兼容检测、容器设备挂载和可见设备隔离，并调整SSH纳管、设备调度和执行后端；其他机型/驱动格式仍须独立验证。不能将NVIDIA共享能力默认套用于NPU。参考[昇腾设备查询说明](https://github.com/Ascend/agent-skills/blob/master/skills/npu-smi/references/device-queries.md)与[Ascend Docker Runtime参数](https://www.hiascend.com/doc_center/source/en/mindx-dl/300/dluserguide/clusterscheduling/dlug_guide_03_000105.html)。

## 升级与回滚

先升级API，再升级Agent和Worker。API兼容旧Agent/Worker；新版Agent不能先于API升级，因为旧版API会拒绝新增注册字段。Agent重新注册时清空旧资源快照，等待新样本后恢复准入。回滚Agent也须重新注册以恢复Worker资源来源；不要手工伪造新鲜时间戳。

升级前排空节点并保留发布包/服务配置，单节点验证心跳、资源来源、任务领取及清理后再推广。此次源代码测试完成不等于所有生产节点已升级。
