# 异构 GPU 资源池与共享调度

物理资源池可以混合不同机器、不同型号 GPU，例如 RTX 8000 和 RTX 4090。型号和总显存由 Worker 登记在每张卡上；资源池 `gpu_model=*` 表示物理池，`virtual` 表示无 GPU 模拟池。旧物理池升级后也改为 `*`。任务默认不限制型号。

GPU 独占表示一张卡同时只运行一个平台任务，池内其他卡仍能并行。共享显存是准入额度，不是 CUDA 显存硬限制；任务超过声明额度仍可能造成 OOM。GPU 利用率是采样负载，不能换算成可保证的算力百分比。

## 管理员配置

在管理设置中创建物理资源池，或调整现有池的 GPU 策略：

- `allow_shared` 默认 false，显式允许共享。
- `max_tasks_per_gpu` 默认 1，范围 1–32；共享两个任务设为 2。
- `vram_reserve_gb` 默认 2，给驱动、桌面和其他进程留下安全余量。
- `max_gpu_utilization` 默认 90：采样值达到阈值时停止新共享准入，不抢占已有任务。

`PATCH /api/v1/admin/pools/{id}` 提交上述四项完整策略。`PATCH /api/v1/admin/nodes/{id}` 可调整 `max_concurrent`、`cpu_capacity`、`ram_gb_capacity` 或 `enabled`，未提交项保留。节点并发也须至少为 2；每个任务仍受到池中 CPU/RAM 配额及全局/用户限制。降低额度不会中断执行，当前执行的资源快照持续计费。

将空闲卡移入同一个池：修改对应 Worker 配置的 `pool_id` 并重启。存在活动或未确认清理的执行时，API 拒绝迁移。GPU UUID 和节点身份不能被其他 Worker 冒用。

## 提交任务

`POST /api/v1/jobs` 在原任务字段外接受：

```json
{"gpu_mode": "shared", "requested_vram_gb": 8, "required_gpu_model": null}
```

`gpu_mode` 默认 `exclusive`；共享要求资源池已开启共享、显存为正整数 GiB，且 Worker 支持协议 v2。独占可不指定显存（0），仍独占整卡。`required_gpu_model` 可选，填写 Worker 上报的完整型号进行精确匹配；不填则使用池内任意合格设备。无匹配设备时任务保持排队。

共享预算同时满足：设备总显存减安全余量减所有持有的显存预留，以及实际空闲显存减安全余量减尚未启动的预留。遥测缺失或超过 15 秒时不新接共享任务。候选卡优先按新鲜利用率从低到高，再按活动数和设备名排序；用户轮询和用户内可调度任务的 FIFO 保留。Worker 创建声明显存需求的容器前复查，容量不足则本次安全失败，可在资源恢复后重试。

管理页面显示每卡型号、容量、实际空闲、利用率和平台预留。预留与实际用量含义不同，不能相加理解为物理使用量。未清理超时执行保留额度并隔离整卡，确认所有遗留容器停止后才恢复准入。

## 升级与回滚

先排空活动任务，备份数据库，停止 API 和 Worker，再执行 Alembic 升级及部署新代码。旧 Worker 继续支持独占，但不接共享任务；新 Worker 每卡仍只有一个监督进程，同时运行多个独立任务。每执行 journal 放在 `<state_path>.runs/<execution_id>.json`，旧单任务 journal 自动迁入。

回滚前必须排空全部共享执行。数据库 downgrade 会恢复单卡唯一活动索引；存在重叠活动任务时应失败而不能强制删除记录。保留升级前数据库备份，恢复旧代码和数据库应成对进行。
