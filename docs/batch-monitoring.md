# 批次监控与补跑

在「CS 评测批次 → 评测集合运行」选择「查看批次」，或在提交、试跑成功后打开对应批次。详情使用 `#/cs/batches/<id>`，可收藏、刷新；返回列表保留当前运行草稿和列表页码，再次打开批次保留本会话的筛选条件。

详情汇总每项任务的**最新尝试**。目标成功率为所有已完成回合的成功数之和除以完成数之和；没有完成回合时显示暂无数据。客户端未声明回合上报时，显示未上报，不推算进度。执行成功但目标失败的任务不会纳入批量补跑。

可按任务名、执行状态、等待原因筛选。等待诊断每约两秒刷新，包含批次/用户/平台并发限制、推理服务互斥，以及各 GPU 的镜像、环境、显存、磁盘等条件。检查不预留资源，不保证启动时间；有符合要求的节点时仍由调度器公平分配。已提交任务使用保存的配置快照，不受模板之后停用影响。

「排查任务」集中展示所选尝试的日志、回合、产物。切换历史尝试后，自动刷新不会跳回最新尝试。「详情 / 重试」保留原有单项操作。

批量补跑需显式选中失败或超时任务。每项绑定选择时的尝试 ID；轮询不会替换该 ID。旧容器未确认清理、额度不足、状态变化或尝试变化时逐项跳过，显示原因。网络错误后保留原选择，可安全再次提交；想补跑新的失败尝试，需要清空并重新选择。历史日志、回合和产物保留，但不会重复累计到最新汇总。

## API

`GET /api/v1/batches/{id}/monitor`：仅本人或管理员可读，其他用户返回 404。保留批次原字段，增加：

- `checked_at`：诊断时间。
- `summary.states`、`execution_failures`：最新任务状态计数及执行失败/超时数。
- `summary.completed_episodes/successes/goal_failures/episode_errors`：最新尝试上报数据；`success_rate` 为加权比率或 null。
- `summary.reporting_tasks/unreported_tasks`：声明上报与未声明上报的任务数。
- `cases[].waiting`：仅排队任务有诊断，包含总体原因和逐 GPU 节点原因；已执行任务为 null。
- `cases[].reason_codes`：筛选用原因码；包括候选节点原因，某节点不满足不代表所有节点都不满足。
- `cases[].config`：提交时的客户端版本、推理地址、资源要求和池名称；不公开宿主机目录。
- `cases[].node_name/gpu_index/cleanup_confirmed`：当前尝试分配和清理状态。

`POST /api/v1/batches/{id}/retry-failed`：

```json
{"items":[{"job_id":"任务 ID","expected_run_id":"选择时的尝试 ID"}]}
```

1–100 个不重复任务。归属或成员校验失败时整批不写入。返回 `retried`、`skipped` 和 `items`，逐项包含 `job_id/outcome/run_id/attempt`；跳过项增加 `code/message`。原因码为 `attempt_changed`、`not_retryable`、`cleanup_pending`、`backlog_limit`。同一事务内持有调度锁和用户额度锁，与单项重试串行化。同一预期尝试最多创建一个后继尝试；重复请求不保证相同响应，但不会重复补跑。

原单项重试仍允许取消任务重试，批量入口仅允许执行失败和超时。
