# Proposal

## Why

当前集合运行将集合、客户端、服务地址及资源参数集中在一个表单，用户提交前难以判断节点是否具备运行条件。需要把现有能力组织成分步流程，并区分参数错误、环境待准备和资源暂时占用，减少无解释的排队。

## What Changes

- 将集合运行拆成选择集合、客户端与服务、资源配置、预检确认四步，保留自定义清单及发布并运行入口。
- 新增只读批次预检，复用提交校验与调度判定，提供逐节点原因及任务/回合汇总；预检不创建任务、不预留资源。
- 参数合法但没有可用资源时允许明确提交排队；节点、镜像或资产缺失不能被描述为参数错误。
- 可选单任务单回合试跑，通过现有批次执行链路验证客户端，保持完整集合及正式运行参数不变。
- 本阶段不包含推理服务配置库、运行预设、历史批次比较、镜像自动分发及全局队列页面。

## Capabilities

### New Capabilities

- `evaluation-launch`: 评测集合运行向导、只读预检、确认提交与可选试跑。

### Modified Capabilities

无。保留有效请求先入库、集合不可变版本及现有调度规则。

## Impact

涉及 frontend/src/cs.tsx、批次提交 backend/app/batches.py、调度及运行环境判定函数、相关后端与浏览器测试。新增 POST /api/v1/batches/preflight；已有批次提交契约兼容，不新增数据库依赖。主规格尚含早期 ClearML 投递描述，本变更沿用现有 PostgreSQL 队列和 Docker Worker，不恢复旧投递实现，也不在本次整理历史规格。
