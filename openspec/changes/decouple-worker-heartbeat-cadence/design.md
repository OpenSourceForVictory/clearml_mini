# Context
当前主循环每轮心跳后领取、后台采样。执行控制另有RecoveryMonitor循环；服务端环境有效期60秒、资源45秒。已有全量测试在主工作区运行，本变更独立工作区避免源码混用。
# Decisions
- 使用单调时钟，基础周期worker_heartbeat_seconds默认5，允许2到10秒；完整回执worker_report_seconds默认20，允许10到30且不得短于基础周期。拒绝bool、非数、非有限和越界。每次成功基础心跳后随机0.9至1.1倍间隔；首次立即发送。
- 仅成功响应推进发送时间和回执指纹，失败沿用Retry-After与有界退避，不吞上报。
- software/storage/runtime/host完整回执按变化或完整周期发送；storage.capacity容量数值不作为配置变化触发器，但随完整回执刷新，disk和telemetry仍按基础心跳发送。报告失效/错误变化及时触发发送。
- 最后成功心跳响应保留为配置/恢复能力上下文；跳过心跳仍可领取。后台采样和配置刷新保持原循环；领取失败等待不阻止到期心跳。主循环等待min(2秒,下次心跳剩余)，避免固定2秒量化成6秒。
- 只降低完整配置回执频率，不缓存服务端授权，不替代claim的最新服务端检查；取消/恢复/任务超时的执行控制保持原样。
# Validation
虚拟时钟验证周期/错峰/失败不推进/配置变化及20秒兜底；从Worker.run验证5秒心跳不阻塞2秒领取、领取退避期间持续心跳、成功回执后不重复完整上报。保持宿主机/容器/恢复取消专项。相同当前版本再做全量与压力对照，不合并旧版本覆盖率。
# Risks
管理配置通过心跳返回，发现延迟可增加到基础周期加网络耗时；默认最大随机间隔5.5秒。旧节点仍2秒。不存在界面编辑入口，配置写入Worker实际JSON并重启服务；默认升级即可生效。

完整报告到期后合并到下一次基础心跳，不为周期刷新单独发请求；默认完整回执间隔不超过约25.5秒加请求耗时。允许配置上限30秒+11秒仍小于服务端60秒环境有效期。配置/检查状态变化仍可提前触发。
