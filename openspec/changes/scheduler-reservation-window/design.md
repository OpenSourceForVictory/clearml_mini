# Design

## Context

tick 在候选读取前后取一次时间，再将该时间传给 reserve 和服务就绪对账；同一事务后续工作越长，提交时的有效期越短。确认复现见 proposal。

## Goals / Non-Goals

目标：提交前重新为本轮新开启的窗口计时。非目标：更改 TTL 配置、延长已有预约、改变心跳/运行时限、优化调度性能、改锁或升级部署。

## Decisions

在 tick 所属 Session.info 中存放本轮窗口登记表（Run、执行 ID、时长）。reserve 与服务就绪解除 waiting_service 的路径共用设置期限函数；该函数先设置原期限，存在本轮登记表时记录窗口。tick 写完调度状态并 flush 后取当前时间，刷新登记的仍处于 RESERVED 且执行身份一致的窗口，再 commit。显式传入 at 的确定性测试继续使用固定时间。

登记表仅存在本轮 Session，提交前移除；异常时 Session 关闭回滚，不污染下轮。多次登记同一 Run 只保留最新窗口。reserved_at 保持实际预约决策时间，不能用 expires_at-reserved_at 推断配置值。未就绪的托管客户端保留 startup_timeout + STARTUP_TIMEOUT_SECONDS 时长，服务就绪后新领取窗口使用 RESERVATION_SECONDS。

不选择为所有 RESERVED 自动续期，因为会掩盖失联和无法领取；不提交后补写，因为会留下可见的过期预约且破坏原子性。

## Risks / Trade-offs

最终期限写入、数据库提交和网络轮询仍消耗少量窗口；本修复去除之前的调度计算耗时，不能保证数据库长时间卡住后仍有完整窗口。期限最终写入失败必须连同预约事务回滚。保持领取的过期检查与服务就绪复查。CPU/显存/环境采样新鲜度不因刷新领取期限而自动延长。

## Migration Plan

无迁移。发布只需更新运行调度器的 API 代码；本任务不部署。旧预约按原期限继续，新代码下轮生成的窗口按新行为。通过代码回滚恢复旧计时方式，不修改正在执行的任务。

## Validation

虚拟时钟覆盖 0、29、30、31、120 秒后续计算，旧实现保留失败证据；普通新预约、托管配对、补实例、服务就绪窗口、旧未领取预约、旧未就绪窗口、到期重新预约及显式 at 均验证。事务失败后无新预约落库，下一轮不继承登记。运行调度、编排、暂停恢复及领取专项；按项目口径报告覆盖率，不以专项统计冒充全项目达标。
