# Design

## Context

动机见 proposal.md。`worker/workspace.py` 创建 `workspace_root/runs/<execution UUID>/{work,output}`；`worker/storage.py` 保存 bootstrap/effective 配置并在空闲时切换，每卡可使用 `/slots/<slot_id>` 根。API 只能看到逐卡容量，不能访问宿主目录。

`Run` 已保存 slot、execution_id、finished_at 和 cleanup_confirmed。`Worker.cleanup()` 当前先通知服务端再删除容器；正常完成路径也在上报 complete 后删除容器、清空 journal。因此服务端终态和 cleanup_confirmed 不足以证明本地可删除。supervisor 在 `<state_path>.runs/*.json` 恢复执行，不能将这些日志当作垃圾。已有 storage probe 会删除自身临时目录，不是业务数据清理机制。

## Goals / Non-Goals

**Goals:** 为可证实归属的执行数据建立可恢复、幂等的清理流程；扫描不阻塞租约心跳；迁移和旧 Worker 兼容；明确容量估算、异步实际状态及默认行为。

**Non-Goals:** 不做任意目录文件浏览、公共资产/cache 清理、Docker prune、磁盘硬配额、服务端产物删除、回收站恢复或自动下载归档。没有可靠归属的旧目录只展示原因，不自动接管。首版仅管理员发起清理，普通用户不获宿主路径权限。

## Decisions

### 1. 服务端意图与 Worker 执行分离

新增执行目录盘点、清理操作及逐项结果表，Worker 增加独立的保留策略 revision/config。盘点唯一身份包含 worker/slot、execution_id 和受信执行根 ID；关联 Run 校验归属，不能单靠 Worker 声称终态。每次完成扫描保存 generation、目录 device/inode、树元数据指纹、逻辑字节、分配字节估算、状态和时间。部分扫描单独标记，不能覆盖完整报告为“0”。

服务端保存操作/预览快照，指令仅携带服务器生成的目标 ID、run/execution 身份和期望版本，不接收任意删除路径。原始宿主路径仅在管理员视图显示。Worker 凭据和 slot 必须匹配操作所属节点；新协议 v6 承载清理能力，v5 和更旧 Worker 保持现有执行功能。

### 2. 可信根和历史目录

Worker 在现有凭据/恢复文件旁持久化清理专用记录，记录已实际验证的执行根身份及根路径。新版本起，目录切换前保留旧根身份；已恢复执行的路径快照也能登记根。当前根可扫描 UUID 目录，但必须由服务端匹配本 slot 的 Run.execution_id 才能成为候选。没有持久化来源的升级前旧路径不会自动全盘搜索，探针目录、未知 UUID 和身份冲突均不删除。

每次执行的本地数据可清理标记只能在容器移除成功、结果/产物处理结束、本地 journal 安全完成后记录。升级前历史目录通过服务端归属、终态和本地 journal/容器复核重新认定，不能假设“没有标记就是垃圾”。同机多个 supervisor 按根身份及执行 UUID 使用跨进程文件锁，避免共享 bootstrap 根重复处理。

### 3. 有界扫描与盘点 API

扫描由独立后台工作单元进行，最多单槽一个，不在主心跳同步递归目录。每轮有目录数/条目数/时间预算并可继续扫描；请求和报告每页最多 100 项，UI 每页 50 项。对已完成、无写入者的目录生成完整树指纹；正在运行的目录可显示明确标记的估算，不成为候选。15 秒心跳仍决定在线性；完整扫描超过 24 小时标为过期，需扫描后再预览。每次删除前再次复核，不把 24 小时视为文件稳定保证。

建议接口：`GET admin/nodes/{id}/execution-data`、`POST .../execution-data/scan`。返回批次/任务/尝试、slot、根标识、目录占用、扫描状态、保护原因和可清理资格。占用使用不跟随链接的 stat；硬链接在同一目录内去重，跨目录或其他文件引用可能导致实际释放少于估算。展示实际文件系统剩余空间的前后观测，不把两次观测差值宣称为删除精确释放量。

### 4. 预览、确认和异步指令

`POST .../data-cleanups/preview` 接收最多 100 个盘点 ID 和期望 generation；仅预览、不删除。返回逐项可清理/保护原因、估算量、10 分钟有效的 preview_id 和明确数据范围。`POST .../data-cleanups` 只接受 preview_id，按唯一约束返回同一 operation，避免响应丢失后重复扩大目标。`GET .../data-cleanups` 及详情提供审计分页。API 返回 202 代表已提交，不代表文件已删除。

确认、策略保存和指令领取在短事务中锁定相关记录并复核 Run/slot；不在调度全局写锁内扫描或删除文件。单项状态为 queued、running、succeeded、skipped、failed；整个操作派生待执行/执行中/成功/部分失败。Worker 轮询领取只属于本 slot 的指令，服务端持久化投递与回执；超时只重新投递同一操作，不授予另一个节点删除权。提供“重试失败项”动作，重新扫描/预览和确认，禁止后台扩大范围或反复永久失败。

### 5. 执行时双重保护和文件系统边界

Worker 在执行前检查服务端有效授权、Run 终态/cleanup_confirmed、本地 active threads、恢复日志、预览绑定根/目录身份、完整树指纹和 Docker 容器引用。容器查询异常即跳过；任何容器仍引用该目录都阻止删除，不主动 kill/prune 容器。使用同一执行互斥保护任务启动和清理接管；新尝试使用新 execution UUID，不复用旧目录。

已验证目录先在同一执行根下原子移动到仅 Worker 可访问的清理暂存区，并把 intent/源身份/目标/阶段写入 fsync 的清理 journal。先落 intent、再 rename、再记录已接管：任何一步崩溃都根据两处 inode 对账，源和目标冲突时停止而不猜测。暂存不是回收站，不提供恢复承诺。移动后再次检查身份和内容指纹，发生变化保持数据并报告冲突；真正递归删除以目录 fd 为基准，不调用拼接路径的 shell rm。

根/执行目录不允许 symlink；内部 symlink 只处理链接本身，不遍历目标。使用 Linux fd 相对操作和不跟随链接的打开方式，检查 device 及 mount identity（同文件系统 bind mount 也要排除），不得跨嵌套挂载或路径边界。若平台无法提供这些检查则拒绝清理。稀疏文件、硬链接、权限异常、路径替换和嵌套挂载均需测试。清理 journal、凭据、state、公共 assets/cache 永不进入候选目录。

删除过程分段执行并记录进度；删除后持久化完成回执再上报。服务端未收到回执时保持待对账；重启用同一操作恢复暂存目录，已经删除的原身份返回同一结果，不能删掉同路径新建目录。部分删除无法撤销，必须显示已处理/未完成，不误报“全部保留”。

### 6. 显式保留策略

机器级配置为 enabled=false、retention_days=30（可设 1–3650）和 revision。按 Run.finished_at 计算已结束时长，所有终态一致处理。管理员修改策略须先预览候选数量/估算量和规则，再以 expected_revision 保存；同时启用影响现有满足期限的历史执行，界面必须明确。未启用或仅空间不足不产生自动清理。

服务端每小时为启用节点生成最多 100 项自动操作，每机最多一项未结束自动操作；使用策略 revision 和候选身份去重，不依赖 API 单进程定时器。Worker 真正开始前复核策略仍启用且 revision 相同；关闭/修改使未获得开始授权的项失效。开始授权在服务端复核策略的同一事务内将单项置为 running，作为关闭策略与开始清理的串行化边界；有效期短且绑定操作/执行身份，未落本地接管记录便过期时须重新申请。已经开始的项继续完成自身对账；停用不表示恢复数据。离线时不开始新的自动清理，只有已经接管的操作可按持久化授权恢复。自动清理同样受新鲜完整盘点、终态和本地安全检查约束。

### 7. UI 和默认假设

机器管理增加“执行数据”入口，与存储路径设置分开，展示容量、扫描状态、候选/保护项、分页选择、预览确认和审计；自动保留策略单独开关，默认关闭。选项与草稿不被轮询覆盖，过期预览必须重做；操作尚未回执时不把目录消失或请求成功当作释放完成。普通用户无管理入口。允许从有权限的任务详情看到本地数据已清理的状态，但不改历史结果。

## Risks / Trade-offs

- [不可逆删除或边界判断错误] → 默认关闭自动清理、显式预览、执行时复核、fd 限定根、跨挂载检测、隔离故障注入；生产验收只读，不删除历史业务目录。
- [大目录扫描抢占 I/O] → 后台限额扫描、完整/部分状态区分、缓存稳定终态扫描；测试心跳和任务领取不被拖住。
- [历史根未记录] → 保守报告未纳管，不扩大到宿主全盘搜索；新版本开始记录根历史。
- [清理任务与目录切换/重试竞态] → 身份绑定、短事务和执行互斥，过期预览重新扫描，旧尝试和新尝试隔离。
- [多文件删除非原子] → 暂存接管和持久化 journal，部分失败可见且可继续原操作；无数据恢复保证。
- [外部宿主 root 进程修改数据] → 本功能不是对抗宿主管理员的安全隔离；任何可检测的引用或身份变化均拒绝，不声称能保护人为破坏的宿主。

## Migration Plan

先备份、迁移新表和关闭状态的策略字段，上线兼容 API/UI；空闲时分别升级两台 Worker 到 v6，确认原任务恢复、存储配置和心跳正常。隔离环境运行真实容器及临时目录清理，包括崩溃、磁盘不足、断线和多槽竞争；生产只读取盘点和预览，不提交清理、不启用自动策略。

回退先关闭策略并停止创建新操作，等待进行中清理完成或明确处理未决 journal，再降级 Worker/API。迁移降级应拒绝存在进行中操作或启用策略。回退代码不恢复已经删除的本地文件，已上传平台的产物、指标不受影响。保留必要审计/备份，不能通过删除 journal 强行回退。
