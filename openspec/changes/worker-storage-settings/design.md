# Design

## Context

见 proposal.md。当前每卡一个 `worker.client.Worker` 监督进程，协议 v3；`workspace.prepare()` 创建固定 assets/cache/runs/state 子目录。CS 容器在 `Worker.create()` 绑定固定宿主路径。`child()` 复用父 config，执行 journal 目前不记录路径快照。管理界面的 Node 仅支持额度和启停；磁盘遥测只有工作目录的容量。配置保存必须与现有全局调度锁、claim 和恢复协议一起处理，不能只添加表单字段。

## Goals / Non-Goals

**Goals:** 管理员可在纳管后修改机器存储路径，看到逐卡实际效果；共享资产、隔离执行；旧任务不中断、恢复不失联。

**Non-Goals:** 文件浏览器、上传/自动下载资产、自动搬迁数据、配额/自动清理、修改 Docker 数据根目录、通过 SSH 操作主机、远程修改 Worker token 或本地 state_path。容器内路径与客户端 SDK 保持不变。

## Decisions

### 1. 期望配置属于机器，确认状态属于槽位

在 Worker 数据库记录中增加 `storage_revision`（初始 0）及可空 `storage_config` JSON。配置包含 `workspace_root`、`assets_root`、`cache_root`（绝对路径）和 `min_free_disk_gb`（沿用现有容量边界，允许 0）。`workspace_root` 在机器级表示工作基目录。新增管理员 `GET/PUT /api/v1/admin/nodes/{id}/storage`：PUT 必须提供 `expected_revision`，基于调度锁递增版本，过期返回 409；PUT config=null 表示恢复本机原始配置，也递增版本。相同配置的显式重新提交可触发重试校验。

Slot 保存 applied revision、校验版本/状态、实际路径、每目录容量、错误（有界）与报告时间。GET 返回 desired 和逐卡 effective，不将一次保存包装成“成功应用”。状态聚合考虑所有已登记槽位，离线/不支持不能被另一个在线槽位的确认掩盖。未设置任何远程版本的机器行为不变。

替代方案：仅将新路径写入 Node 并立即用于任务会造成“保存成功但挂载失败”；以整机一个确认状态无法表达多卡部分生效。

### 2. 协议 v4 与受版本约束的任务准入

新 Worker 注册协议 v4，上报本地实际存储信息。监督进程心跳接收服务器期望版本，并在报告中带校验/已生效版本和实际配置；子执行心跳仅续租，不覆盖监督进程存储确认。v1–v3 兼容保留，未配置远程存储时仍可调度。

保存新配置时在现有调度锁内将尚未领取的 RESERVED 执行退回 PENDING，并清理它们的槽位分配与资源预留；已 STARTING/RUNNING 及待清理执行保留。调度和 claim 均检查 storage 版本与状态，配置不匹配时不分配/领取新任务。已领取执行的恢复与 cleanup 不受该准入限制。

Worker 发现新版本后，等待自身无 children、无待恢复 journal、无服务端待清理项，才校验并切换。确认时服务端在同一锁内复核槽位无持有执行；过期版本确认不能打开准入。新任务携带确认的存储版本，Worker 启动前比对。这样保存、确认和 claim 的竞争有明确先后次序。

替代方案：仅停止本地 claim 仍会被调度预留占住配额，且可能读取到旧响应；整机等待所有卡空闲会使一张长期任务卡阻塞其他空闲卡，因此采用逐卡切换与清晰状态展示。

### 3. 宿主机路径与权限校验

API 只校验字符串形状和数值范围，不冒充对远端文件系统的检查。Worker 在主机规范化路径，拒绝相对路径、逗号/换行/控制字符、任何父路径软链接及根目录；禁止 `/proc`、`/sys`、`/dev`、`/run` 等特殊文件系统和凭据/系统配置目录作为共享挂载。禁止资产/缓存包含工作可写树、state_path 或 Worker 配置文件。资产和缓存可共享，但不能把任务输出或私有恢复信息通过共享挂载暴露。

资产/缓存目录必须预先存在并可遍历读取；工作基目录可由 Worker 在有权限的位置创建，只调整新建执行目录的权限，不递归 chmod/chown 既有宿主数据。用固定已批准 runner 镜像进行有超时、无网络、无 GPU、低资源的容器探测，确认只读挂载可读及 work/output 可写；只在配置版本变化或显式重试时做容器探测。每次任务启动仍复查目录/容量，避免校验后目录变更造成误挂载。路径错误不以忽略软链接或创建空资产目录规避。

机器管理员仍负责确认公共资产中没有私人数据；本次不是资产内容扫描器。远程配置权限等同于指定任务可读取的主机数据目录，仅管理员能编辑。

### 4. 多卡目录与持久化配置

启用机器级远程配置后，每卡实际工作目录采用 `<workspace_root>/slots/<slot_id>`，其下 `runs/<execution_id>/work|output` 隔离。assets_root/cache_root 是独立目录，各卡共享。容器内继续挂载 `/opt/mini-eval/assets`、`/opt/mini-eval/cache`、`/tmp/mini-eval-work` 和 `/tmp/mini-eval-output`。资产按客户端约定组织，例如 RoboTwin 的版本化子目录，平台不要求通用资产遵循 RoboTwin 布局。

监督进程状态位置固定为启动时确定的 state_path；切换配置不移动该位置。将本机初始设置和最新已确认设置保存于 state_path 旁的独立、原子写入的存储记录文件，不覆写 token 配置。子执行 journal 保存实际 workspace/assets/cache 路径与配置版本，child 恢复以该快照为准，不使用最新 desired 替代旧任务路径。旧 journal 缺少快照时，使用首次启动的旧配置，在修改任何路径前补写快照。已完成数据保持原处；页面明确不自动迁移。

替代方案：把 state_path 随工作目录一起迁移容易导致重启找不到执行，破坏现有对账机制；用每卡 GPU index 做唯一目录不足以覆盖重新注册，slot_id 更稳定明确。

### 5. 展示、失败恢复和磁盘门槛

管理设置的每台机器增加“存储配置”面板：期望值表单、保存/恢复本机配置、版本、逐卡实际路径和状态、最后报告时间、各目录容量。展示待校验、等待执行结束、已生效、校验失败、离线、需升级；普通用户不获得修改能力。轮询刷新只更新服务端状态，不能覆盖用户正在编辑的草稿。

工作目录使用管理员设置的最低可用空间，资产/缓存容量只展示；只读资产不预留每任务磁盘。检查失败或报告过期停止新任务准入；空间恢复自动继续，不取消正在执行的任务。权限/挂载校验失败保留旧 effective，允许管理员修正配置或触发新版本重新校验。恢复本机配置也需等待空闲、验证并确认。

## Risks / Trade-offs

- [多个槽位部分生效] → 明确逐卡状态，已确认的空闲卡可以工作，不以整机状态隐藏差异。
- [校验期间服务端又保存新版本] → expected revision、服务端锁、过期确认拒绝、启动时版本校验。
- [文件系统在校验后变化] → 启动时重新校验路径和容量；保留任务错误，不能承诺磁盘容量硬隔离。
- [Docker 权限或镜像缺失] → 显示挂载探测失败，不新拉取大镜像或绕过探测。
- [机器注册后暂未装新 Worker] → 仍能保存设置，但显示待上报/需升级，并阻止未确认的槽位执行新任务。
- [旧数据占用空间] → 提示旧路径仍保留，由管理员在无活跃执行时单独清理；不实现自动回收。

## Migration Plan

1. 添加向后兼容数据库列和接口；默认 revision=0、config=null，不改变既有机器行为。
2. 部署后端及前端，旧 Worker 继续使用本地设置。
3. 升级一台空闲 Worker 至 v4，先验证本地默认路径与旧 journal 恢复，再通过界面配置并检查报告。
4. 使用测试目录做本机/R8000 小任务现场验证，记录生效版本、实际挂载及旧任务路径保持；多卡隔离先做确定性双槽位测试，不宣称已经完成真实多卡硬件验收。
5. 回滚前排空涉及切换的任务并确认遗留容器清理，恢复本机配置并获确认，再回滚 Worker/API；数据目录与恢复记录不得删除，数据库降级只在备份和排空后进行。
