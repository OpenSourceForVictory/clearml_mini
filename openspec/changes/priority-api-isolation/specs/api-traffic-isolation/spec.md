# Spec Delta

## Purpose

为评测平台不同重要性与可靠性的请求提供可验证的处理容量边界，使节点执行控制和用户主动管理操作在日志、遥测及页面刷新高峰期间仍能得到明确响应。

## ADDED Requirements

### Requirement: 关键请求容量保障
系统 SHALL 分别为执行控制和用户主动管理、调度操作保留处理与数据库容量；批量日志或页面读取饱和时，不得占用这些预留容量。

#### Scenario: 日志与页面高峰期间提交批次
- **WHEN** 日志持续上传且页面持续刷新，用户提交有效批次
- **THEN** 系统在用户操作预算内确认已提交或明确返回可重试的繁忙错误
- **AND** 不因日志上传占满处理线程或连接而等待到客户端超时

#### Scenario: 长事务不挤占执行续租
- **WHEN** 一个用户提交操作在数据库事务中等待调度锁
- **THEN** Worker 续租仍可使用独立预留容量
- **AND** 未提交的用户操作不返回成功确认

#### Scenario: 预检不占满提交额度
- **WHEN** 多个用户同时运行耗时的向导预检
- **THEN** 用户提交批次、恢复服务或取消任务仍可使用独立的用户写入额度
- **AND** 预检不会与页面自动刷新共用唯一处理额度

### Requirement: 数据按可靠性处理
系统 MUST 将执行身份、领取、终态和协议结果作为需确认的数据，将遥测中间采样和页面自动刷新作为可合并或退避的数据；日志达到限制时 MUST 显示截断或缺口，不得伪装成完整记录。

#### Scenario: 结果上报暂时繁忙
- **WHEN** 可靠回合或任务结果上报收到暂时性繁忙响应
- **THEN** 平台不得记录未接收的结果为成功，Worker 按既有协议重试原执行身份

#### Scenario: 遥测高频覆盖
- **WHEN** 同一节点在短时间内上报多个有效观测样本
- **THEN** 平台可合并中间样本，但仍按现有规则保持最新有效值与新鲜度判断

### Requirement: 日志传输与交互隔离
系统 SHALL 将 Worker 日志上传与页面 API 的处理容量隔离；用户查看日志属于页面读取，不得因路由到日志上传入口而失去原鉴权或访问语义。

#### Scenario: 上传日志时查看批次
- **WHEN** 日志上传达到其容量上限且用户查看批次或日志
- **THEN** 页面请求仍可使用独立容量，日志上传按可重试或明确截断的原有协议处理

### Requirement: 路由与部署一致
系统 MUST 按 HTTP 方法和准确路径给请求确定唯一类别；网关与服务端分类 MUST 一致。单 API 与现有双 API 部署 SHALL 保持可用；新隔离部署 SHALL 显式启用并可回退，不得超出配置的数据库连接总预算。

#### Scenario: 新增路由未显式分类
- **WHEN** 一个新 API 路由未加入高优先级分类清单
- **THEN** 该请求只能使用受限普通容量，不能借用执行控制或用户操作预算

#### Scenario: 网关误路由
- **WHEN** 网关把请求发往错误的隔离进程
- **THEN** 该进程拒绝请求而不在错误类别中执行数据库操作

#### Scenario: 数据库预算不足
- **WHEN** 各进程配置的最大数据库连接之和超过可配置预算
- **THEN** 隔离部署启动前拒绝该配置，不能以无限溢出连接继续运行
