# Design

## Context

见 proposal.md。当前单 API 是默认部署；可选双 API 将少数控制 POST 送到 `control-api`，其余进入 `api`。`db_budget.request_category` 对非 POST 一律归普通类，因而用户的 `PATCH/PUT/DELETE` 管理操作、批次提交、领取、页面查询、日志与产物共享普通进程。双 API 的池为普通 23、控制 40、观察 9、结果 7、调度 1，合计上限 80；PostgreSQL 当前 `max_connections=100`，但这不是已验证的业务并发上限。100 个模拟 Worker 的 30 分钟测试没有实际用户提交、重页面查询、真实调度与程序结束循环，不能直接用于新架构的容量承诺。

`worker/heartbeat` 同时承载续租与少量最新遥测、配置回执；`agent/heartbeat` 同时承载采样与配置 ACK/事件。不能把整条心跳当作可丢弃观测。回合/任务结果和日志在现有 Worker 逻辑中部分先于完成上报，入口隔离本身不能解决日志持续拒绝时的收尾阻塞；这一点与 `worker-control-plane-backpressure` 中尚未完成的 outbox/完成摘要设计相接。

## Goals / Non-Goals

**Goals:** 给用户主动操作与执行控制同等级的容量保障，但以独立池/进程避免批次提交持锁时阻塞续租；把页面读取、Worker 状态/结果与日志传输从处理资源到数据库连接分开；保持一个外部地址和单 API、双 API 兼容；用混合负载及数据库余量给出可复现的容量边界。

**Non-Goals:** 不把 `max_connections` 当吞吐目标，不在本变更修改调度决策或数据模型，不以隔离入口代替可靠补报与断联对账，不将所有日志强制持久保存，不把普通前端 GET 自动提升为用户控制操作。

## Decisions

### 1. 以端到端后果定义类别，先覆盖每个已注册路由

维护一份唯一的“HTTP 方法 + 路由模式 → 类别/进程/数据库池/可靠性”清单，测试枚举 FastAPI 所有已注册 API 路由并检查没有遗漏。网关配置由清单生成或在构建时验证与清单完全一致；服务端再次按相同类别拒绝误路由。未知新路由默认受限普通类，测试阻止未经审查的新增路由发布；只靠 Nginx 手写正则会漂移，因此不继续逐条补正则。

| 类别 | 示例 | 处理原则 |
|---|---|---|
| 执行控制 | Worker 续租、服务健康转换、停止许可、完成/清理确认、升级控制 ACK | 最短响应与独立容量；提交后 ACK；日志不得借用 |
| 用户操作 | 登录、创建批次/编排、取消/重试、暂停/恢复、优先级、节点/模板/资源配置 | 独立于执行控制的保留容量；事务提交后 ACK；幂等键/修订号沿用现有语义 |
| 用户预检 | 向导资源预检、编排预检等昂贵但不写库的主动请求 | 单独受限容量，高于自动刷新，但不得占满真正的用户写入预算 |
| 领取与可靠结果 | 领取、回合结果、任务结果、执行授权相关回执 | 独立 Worker 数据容量；结果幂等重试；领取锁顺序不变 |
| 最新观测 | Agent 采样与配置 ACK、节点状态 | 可合并采样但不能丢配置 ACK/事件；目前整条请求按可靠 Worker 数据处理，待拆负载后才可仅覆盖纯采样 |
| 页面读取 | 批次详情、监控、日志查看、产物浏览 | 分页/限频；自动刷新前端退避；不挤占用户操作预留 |
| 批量传输 | 日志上传、日志目录/回读数据、历史产物字节 | 有界大小/队列；保留现有序号 ACK 与显式截断；不得挤占页面或控制 |

用户主动点击查看与页面自动刷新若共用 GET 路径，服务端无法安全地从客户端声明区分优先级；先使用同一页面读取预算，通过现有前端退避限制自动请求。未来若要分别保障，须提供可核验的独立交互接口，不能信任一个任意优先级请求头。`preflight` 虽是 POST，但只读且可能昂贵，归用户预检；批次创建归用户操作，二者不共用许可。日志 GET 仍归页面读取，Worker 日志 POST 归批量传输。所有用户写方法（含 PATCH/PUT/DELETE）逐个审计，不能仅凭方法推断权限。

### 2. 四个处理角色，数据库类别是角色内部的预算

新模式使用单一网关和四个 API 角色：`execution-control`、`interaction`、`worker-data`、`bulk-transfer`。`interaction` 内的用户操作、用户预检与页面读取分别有数据库池和入口许可，处理线程容量至少为三类已准入上限及少量清理余量；`worker-data` 内领取、可靠结果、Agent 观测与唯一调度线程分别有预算。`bulk-transfer` 只收 Worker 批量上报；页面日志 GET 不经过它。执行控制单独进程，不与长用户事务共用同步线程。每个进程只创建本角色池，全部连接的 `max_overflow=0`；类别许可在鉴权、借连接和同步线程分派之前取得，有界排队且取消后释放。

保留现有单 API 与双 API 配置及路径语义，四角色配置作为新显式覆盖文件；同一镜像、同一数据库、同一外部地址。只在 `worker-data` 运行一个调度线程。角色不健康时网关不把请求回退到低优先级进程；`/healthz` 检查所有必需角色，角色自己的存活与数据库就绪分开诊断。入口和池隔离只保护排队/连接借用；PostgreSQL CPU/WAL/磁盘、共享行锁和机器 CPU 仍需专项监控。

不采用“每个路由一个进程/连接池”：会扩大连接常驻上限、运维成本和误路由面。不采用“只增加 PostgreSQL 最大连接数”：已有等待可能来自调度锁和单进程线程，不会因连接数上升自动消失。不采用“把全部用户操作放入现有控制进程”：批次提交持调度锁、可能构建大量任务，能拖慢短时续租。

### 3. 总连接预算先算上界，再用占用时间调整

启动前统一检查 `Σ(角色 × 类别池上限) + 其他数据库使用者 + 管理/迁移余量 < max_connections`；不能仅在单个进程内验证自身配置。示例候选保持现有 80 个 API 上限：执行控制 24，交互用户操作 10/用户预检 4/页面读取 10，Worker 观察 8/结果 7/领取 6/调度 1，批量传输 10，合计 80。这只是待验证的初始分配，不是“100 Worker 推荐值”；各角色线程许可也不机械等于数据库池大小。启动检查读取配置清单并拒绝预算超额或角色/网关缺失，运行时暴露各类连接占用、等待、拒绝与延迟指标。

理论估算用 `平均同时占用连接≈峰值请求速率×数据库连接持有时间`，再按同步突发与尾部延迟增加余量；这是估算起点，必须用真实事务和混合负载校正。监测 PostgreSQL 活跃/空闲连接、锁等待、CPU、WAL、I/O 与 API 线程排队。不能把 100 个 Worker、每进程 40 个线程或 `max_connections=100` 直接解释为需要 100 个业务连接。

### 4. 锁与确认边界不随路由改变

批次/编排提交仍使用幂等键与用户行锁，调度相关事务的全局锁范围要单独测量；不得因移动到新进程而删除锁或改变资源预约顺序。Worker 领取先只读、候选才尝试锁的现有逻辑保留。执行控制与用户操作同时更新同一行时，连接池隔离不消除数据库行锁；锁等待预算和明确的可重试 503 仍生效。需记录每类请求的事务持有时间、锁等待及 p95/p99，先定位锁内重复查询/大视图组装，再做等价优化。用户操作成功响应必须在提交后发送；浏览器失败后重试沿用现有幂等/修订规则。

可靠结果与日志的交付顺序需要与 `worker-control-plane-backpressure` 衔接。此次入口隔离只保证批量上传不能占用控制处理容量；在 Worker 完成摘要/持久 outbox 尚未完成前，不宣称“日志持续故障也不会拖慢任务结束”。Agent 心跳中的配置 ACK/事件暂不可合并丢失。保留日志配额/缺口和结果幂等规则，不因新进程而改变内容语义。

## Risks / Trade-offs

- [四角色新增进程增加 CPU 与内存开销] → 显式启用、保持双进程可回退；测主机 CPU/内存与网关延迟。
- [池从控制 40 重分配后续租容量下降] → 24 仅是候选，必须在 100 Worker 加真实 Web/提交/结果/日志的长测中验证；不满足即调整分配或停止发布，不能以降低可靠性换通过。
- [用户写接口遗漏或网关/服务端分类漂移] → 枚举所有注册路由并生成/校验网关；错误角色拒绝，不静默转普通池。
- [数据库共享锁、WAL 与 I/O 仍会互相影响] → 混合负载观察锁等待与数据库资源，按证据优化锁内工作，不承诺绝对隔离。
- [多进程启动导致双调度器] → 角色配置仅允许一个调度器，启动检查和真实 Compose 验证。
- [历史 Worker 暂时性错误处理不一致] → 发布前核对版本与重试行为；保持单/双 API 回滚，节点执行未完成时不清除 journal。

## Migration Plan

1. 固化完整路由清单、事务/锁清单和混合负载基线；在隔离数据库验证当前双进程原始失败/成功边界。
2. 实现四角色分类、网关配置生成/校验、统一连接预算预检与可观测指标；先只在隔离 Compose 启用，单/双 API 不变。
3. 跑路由矩阵、真实 PostgreSQL 并发/锁测试、含用户提交和页面监控的 100 Worker 长测；再测日志持续拥塞、角色故障与恢复、任务结果幂等及服务控制。记录 p99、拒绝/重试、租约新鲜度、积压年龄、数据库余量；失败档保留。
4. 完成代码/指南/Skill 同步与覆盖率检查后，备份并排空目标平台，先灰度切换网关。验证唯一调度器、四角色健康、用户提交与控制、节点续租及回退；未通过时恢复原双进程覆盖文件和网关，不重建数据库卷或 Worker。

## Open Questions

无影响架构的待决问题。具体池数值以混合负载和目标 PostgreSQL 的实测结果确定，不视为需要用户选择的产品语义。
