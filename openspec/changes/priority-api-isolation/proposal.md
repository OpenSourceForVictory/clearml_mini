# Proposal

## Why

当前双 API 部署只把部分执行控制请求从普通进程分离。日志上传、页面查询、用户提交批次、Worker 领取任务和结果上报仍共享普通 API 进程的线程与数据库容量；已有 100 Worker 长测没有加入实际 Web/提交负载，不能证明这些关键操作在日志高峰时可用。需要按业务后果统一划分流量、事务和容量，而不是逐条增加例外路由或盲目扩大连接池。

## What Changes

- 建立完整的请求分类契约：执行续租与停止确认、用户主动管理与调度、可靠结果、调度领取、最新观测、页面主动读取、页面自动刷新、批量日志与产物传输；逐接口登记鉴权、时效、可靠性、锁、数据库与线程预算。
- 为执行控制和用户主动管理操作分别保留容量；日志上传不与页面 API 共用处理进程。页面日志读取仍由页面 API 服务，避免日志查看与上传互相挤占。
- 将现有只按少数 POST 路径分类的实现改为与 HTTP 方法和已注册路由一致的明确规则；未知新路由默认进入受限普通通道，不能自动取得核心预算。
- 所有 API 进程与后台调度的连接上限统一纳入 PostgreSQL 可用连接预算；保留单 API 与现有双 API 部署兼容，新增隔离模式必须显式启用、可回退。
- 通过含真实用户操作、页面查询、Worker 续租/领取、Agent 观测、结果和连续日志的混合负载验证容量，保留失败与跳过证据。此变更不改变任务、回合或调度结果的业务语义。

## Capabilities

### New Capabilities

- `api-traffic-isolation`: 按时效与可靠性保护平台 API 的关键操作，并限制批量流量对其他通道的影响。

### Modified Capabilities

无。

## Impact

影响 FastAPI 请求分类和数据库会话分配、Nginx 路由、Compose 部署、混合负载工具及回归测试；同步运维指南和项目 Skill 参考。无需数据库迁移或 Worker/Runner 协议变更。与 `worker-control-plane-backpressure` 的可靠补报和断联恢复任务保持独立；入口隔离不能替代尚未完成的持久化 outbox。
