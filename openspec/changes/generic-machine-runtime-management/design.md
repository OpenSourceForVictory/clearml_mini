# Design

## Context

现有 React Admin 将凭据创建和所有机器配置堆叠；Worker 与物理机器一一对应，Slot 按 GPU 建立。backend execution/memberships 已有调度锁、租约、排空与恢复；clients 保存模板快照；runner.sdk/episode_contract 提供逐回合 JSONL。Worker 目前只支持 Docker，配置和回执也以镜像为中心。控制端 Docker 内不具备用户 SSH 配置，不能直接假定可执行本机 ssh。

## Goals / Non-Goals

Goals: 通用管理、可执行两类模板、真实 SSH 纳管与服务实例闭环，兼容旧 API 和当前五节点部署。
Non-Goals: 不做 Kubernetes、多节点分布式推理、自动安装任意业务依赖或通用镜像构建；不迁移既有数据库/日志到 NFS，不把宿主机执行宣称为强隔离，不引入推理地址池。

## Decisions

1. **ClearML 参考与差异**：参考官方 [Agent 仓库](https://github.com/clearml/clearml-agent)、[执行环境](https://clear.ml/docs/latest/docs/clearml_agent/clearml_agent_execution_env/) 的环境/任务分离和 [Workers and Queues](https://clear.ml/docs/latest/docs/fundamentals/agents_and_queues/) 的拉取队列模型。沿用当前数据库调度与 Agent 拉取，保持模板/实例快照可追溯。ClearML [services-mode](https://clear.ml/docs/latest/docs/clearml_agent/clearml_agent_services_mode/) 面向轻量后台控制服务且要求 Docker，官方明确不建议推理任务进其默认 services 队列；本项目 GPU 推理仍需真实资源预留，不能直接复制 launch-and-forget。
2. **兼容模型**：在 Worker 加 roles、纳管状态/撤销时间、SSH 非敏感元信息；旧数据默认 client。服务端与客户端可以兼任且共用 Slot，角色变更不得绕过运行资源。解除纳管用墓碑和令牌撤销，不物理删除历史外键。停用不让持有执行失去续租/结果上报权限。
3. **SSH 执行器**：独立控制端纳管进程负责 SSH，API 提供有界操作队列/状态；临时凭据只存在短生命周期内存，通过受控通道交接，不落日志/数据库。使用主机密钥校验和可见指纹，不关闭校验。先检查系统/Python/GPU/Docker或host能力/API连通性/目录，再明确执行安装；失败可重试，所有步骤幂等。既有五节点只探测，不能重复覆盖 NFS 系统单元。业务依赖缺失展示修复项，不自动 apt 升级驱动。
4. **模板层**：保留 ClientTemplate 表/API以兼容集合外键；新增 execution_mode、integration_mode、host 环境引用，Docker默认兼容。新增 ServerTemplate，复用纯配置校验器；相同 name/version 唯一，修改通过复制新版本。禁止运行时拼接 shell 字符串；命令为 argv，参数/环境变量独立解析，保留平台变量不可覆盖。逻辑资产与 host 环境按节点解析，不能把某台绝对路径写死为模板唯一身份。
5. **执行后端**：Docker 后端保留现有行为；宿主机后端使用受管理 systemd 执行单元/进程组，以 execution ID 命名，绑定 Worker 用户、GPU可见性、CPU/内存及超时，日志有界、本地 journal 与终止确认可恢复。禁止仅保存 PID 后直接 kill。每次执行的输入/工作/输出独立，宿主机环境需管理员配置和就绪探测。GPU显存仍为准入估算，不宣称硬隔离。
6. **SDK业务命令**：新增 SDK 命令适配器，按回合生成参数/环境与结果文件约定，校验 success/metrics/artifacts 后生成原协议事件；直接协议模式复用现有 JSONL/输出协议。业务 stdout 不推断成功。Docker和host共用同一输入和产物格式，Agent续租/重试去重仍由既有协议负责。
7. **推理实例**：复用 Job/Run 资源预留与清理生命周期，以独立服务类型与目标 Slot 约束加入统一调度；ServerInstance记录目标、端口、模板快照、期望状态和健康报告。持续运行不使用评测回合超时，启动健康有期限。端口按主机唯一预留，失败清理前不释放；停止触发取消，重新启动产生新执行记录。实例详情提供日志和地址复制，已有评测的地址列表独占/共享机制不变。
8. **界面与账号**：拆分 Admin 子组件，列表/注册/详情独立；资源池复用 memberships 修订检查，删除采用归档且拒绝活动引用；账号复用现有密码哈希与权限，增加账号列表、状态和重置，保护最后一个管理员。

## 模块边界与故障控制

采用模块化单体，保持现有部署形态；模块边界按业务职责划分，不以页面或文件拆分代替职责隔离。优先将校验、超时、重试、错误转换及恢复控制在所属模块；涉及共享资源与执行安全的风险必须通过明确协作契约处理，不承诺所有故障均可完全局部化。

| 模块 | 拥有的状态与责任 | 对外契约及失败边界 |
| --- | --- | --- |
| 机器接入与管理 | 身份、角色、纳管操作、批准环境、目录配置修订 | 输出能力和就绪状态；SSH 操作有界超时与独立执行，失败不影响已纳管 Worker 的心跳和任务 |
| 资源池与成员 | 池策略、GPU 归属、期望成员关系与排空修订 | 向调度提供资源范围；成员迁移复用排空接口，不能直接终止执行或释放占用 |
| 运行模板 | 类型、版本、配置校验、启停与归档 | 输出不可变快照及能力需求；不安装环境、不选择 GPU、不管理进程，配置错误仅拒绝对应提交 |
| 评测编排 | 集合、批次、任务展开、并发上限和回合汇总 | 提交规范化任务并消费执行结果；不自行启动进程或另设 GPU 账本，单任务失败按批次策略处理 |
| 服务实例 | 部署目标、期望状态、端口预留、健康与执行历史关联 | 向统一调度提交服务任务，通过执行接口停止；健康异常不伪装完成，也不自行释放 GPU |
| 调度与资源账本 | 准入、预留、租约、资源占用和释放条件 | 唯一资源分配入口；评测和服务共用事务与调度锁，清理未确认时保留占用 |
| Worker 执行 | Docker/host 启停、执行身份、本地恢复、清理确认 | 消费任务快照与分配结果；后端错误转为统一执行状态，取消/租约失效由本地看门狗终止进程树 |
| 协议与结果 | 输入和事件校验、去重、日志与产物边界 | 使用 execution ID、任务及回合标识关联；畸形或过期事件不能修改其他执行或重复增加进度 |
| 权限与审计 | 身份验证、管理权限、操作审计 | 所有入口统一鉴权；业务模块不自行实现密码与令牌规则，敏感凭据不进入审计内容 |

### 依赖和状态一致性

主要路径为：机器接入 → 能力/目录就绪 → 资源池成员；模板快照 + 集合/服务请求 → 统一调度 → Worker 执行 → 协议结果 → 批次汇总/服务状态。账号权限覆盖入口，管理界面只调用应用接口，不承担状态转换规则。

- 跨模块调用使用明确应用接口及输入/输出结构；共享纯校验器和协议类型不得反向依赖业务模块。现有共享 ORM 可暂时保留，但新增业务逻辑不得绕过状态拥有者直接修改其生命周期字段。
- 明确区分期望配置、已回执配置、期望停止、实际退出和已确认清理。节点/成员配置通过 revision 检查；执行事件通过 execution ID 和有效租约校验，拒绝过期回执。
- 端口预留与 GPU 准入必须纳入明确的事务/锁约束；远程启动不持有数据库长事务。数据库提交与远程执行之间通过持久执行身份、重试及恢复协调，不依赖跨机器原子事务。
- 模板校验失败不创建执行；节点环境不匹配仅阻塞对应候选节点；日志、健康探测与结果处理使用有界超时/大小，不能阻塞续租和取消。
- 重试由负责该操作的模块管理，保持幂等身份并限制次数/期限；不能在多个层级无限重试。停止失败保留资源并暴露待清理原因，不通过删除记录掩盖故障。
- 变更优先限定在拥有状态的模块；契约变化必须检查所有调用方，保持旧模板、旧 Worker 和历史数据兼容，并补充跨模块测试。

### 跨模块验收

除模块单元测试外，必须验证：SSH 失败时现有任务继续运行；模板错误不消耗资源；环境失效阻止领取；机器停用/成员迁移期间已领取执行仍能上报和清理；服务与评测并发争抢不超卖；停止或断线时清理前不释放资源；重复/过期回合事件不影响计数；模板新版本不改变运行快照。测试应覆盖状态转换及失败恢复，不能仅验证接口返回成功。

## Risks / Trade-offs

- SSH 凭据泄漏 → 专用执行器、临时内存、日志脱敏、操作过期，不把 Web API 容器挂载整个 ~/.ssh。
- host 程序权限较大 → 管理员批准环境/模板，明确可信程序边界；系统级进程管理及资源限额，缺能力则拒绝准入。
- 兼任 GPU 超卖 → 服务与评测同一调度锁和资源账本，终止未确认保留占用。
- 升级失联 → 新 Agent 能力版本门槛、分步滚动、保留已有 journal、旧模板继续运行。
- NFS 中断 → 沿用挂载守卫，不把凭据/恢复记录迁到共享盘。

## Migration Plan

备份数据库及当前五节点配置；新增兼容字段/表并验证升级。先发布 API 与界面，新能力仅对新 Agent可用；在本机验证 Docker/host 客户端及服务双模式，再滚动升级五节点，验证身份/NFS/池和历史任务保留。SSH 纳管以隔离测试主机或明确新实例验收，不解除当前五节点纳管。回退前排空新增host/服务执行，回退代码保留新增字段和历史表，不做破坏式 downgrade。每个完成的功能提交 Git；记录真实验证与未覆盖边界。

## 模板参数分层与挂载契约（待实现）

当前模板字段只覆盖基础命令、环境变量、逻辑资产和宿主机环境；以下是新增设计，不代表已部署能力。

### 参数所有权

| 参数分类 | 典型内容 | 配置与取值责任 |
| --- | --- | --- |
| 平台参数 | 执行身份、已分配 GPU、服务地址/端口、输入文件、工作/输出目录、回合身份 | 模板声明所需接口及容器内目标；平台按任务分配，Worker 按已回执节点配置解析；业务不能覆盖保留字段 |
| 业务参数 | task_name、任务配置、seed、episodes、场景、相机及业务选项 | 模板声明类型和绑定，集合任务项保存取值，运行时仅允许显式开放的覆盖 |
| 运行参数 | Docker/host、镜像/批准环境、argv、cwd、env、CPU/内存/GPU显存申请、共享模式、超时、健康检查、挂载 | 模板提供默认需求，提交方在允许范围内调整；调度统一准入，Worker 执行，不把资源申请当作实际分配 |

业务 seed/episodes 的默认值可来自模板，但最终进入既有任务输入与回合协议；不得同时维护两份不同的回合数。平台 endpoint 为分配结果，仍沿用用户提供地址列表及独占/共享语义，不建立推理服务池。模板注册信息（名称、版本、说明、客户端/服务端）位于独立基础信息区。

### 类型、覆盖和程序绑定

业务字段使用有界 schema：name、label、description、type、required、default、enum、min/max、运行时是否可覆盖及绑定定义。支持 string/integer/number/boolean/enum/object/array，数值拒绝非有限值；明确缺失、null、空字符串差别，拒绝未知字段和类型不符。目录和设备使用专门引用字段，不作为未经校验的业务字符串使用。

有效业务值按“模板默认 → 集合任务项 → 允许的本次覆盖”计算，先校验再创建批次；重试复用已保存快照，不重新读取可变默认值。实例保存模板版本、有效参数、映射规则和资源申请；执行时另存实际分配及节点配置修订，前端提供运行配置预览。

绑定支持结构化输入 JSON、argv 和显式 env。所有业务值默认可在标准输入 JSON 中取得；绑定到 argv 的标量各形成独立参数，不经 shell 拼接，布尔值明确选择 flag 或字面值，数组明确选择重复参数或 JSON 字符串，object 仅 JSON 编码。保留 MINI_EVAL_* 和 GPU 可见性变量由平台设置，不能通过业务绑定覆盖；日志只记录脱敏后的有效配置。

### 集合、调度与执行的关联

集合每个任务项包含稳定任务身份、业务取值、回合计划及允许的运行需求覆盖；批次展开形成独立执行快照。平台明确知道每个客户端运行哪项任务、哪些种子和回合，而不根据命令文本猜测任务。

调度输入来自规范化资源需求、执行能力和挂载需求；业务字段如需影响调度，必须声明到资源/能力需求的确定映射，并经过同一资源校验。不得执行用户表达式或脚本来计算准入。业务 task_name 的区别本身不产生未经声明的资源权重。预检和领取使用同一校验契约。

### 目录、设备与端口

容器目录挂载项为逻辑 source、容器 target、ro/rw、required。source 可引用任务工作区、输出区、节点批准资产/缓存或管理员批准的额外目录。模板不固化某台宿主机路径；节点登记逻辑名称到物理路径的映射，检查修订、存在性及权限。资产默认只读，工作/输出目录按 execution 隔离。共享可写目录必须显式批准；目标重叠、平台协议目录覆盖、路径越界及未批准源均拒绝。

设备挂载项为逻辑设备名称、容器目标和明确访问权限；管理员在节点配置可用设备映射及共享/独占策略。Worker 校验设备实际存在、类型与就绪状态；缺失设备仅排除该节点并报告原因。独占设备必须进入统一资源预留，清理确认前不得复用。GPU 仍由分配的 GPU UUID 和运行时注入，不能用设备挂载绕过；不通过通用参数开放 privileged、Docker socket 或任意 Docker flags。

端口声明区分容器监听端口与宿主机发布端口，支持固定值或平台在批准范围自动分配；按物理主机及传输协议防冲突。平台预留后 Worker 校验实际占用，启动失败报告原因并进入清理，不能私自换端口导致地址快照失真。

### 模块责任和兼容验收

模板模块拥有 schema/绑定校验，集合模块拥有任务取值与覆盖，调度拥有资源/端口/独占设备分配，机器模块拥有本地映射及能力回执，Worker 拥有解析执行和清理，结果模块仍按执行/任务/回合身份计数。共享参数契约是纯校验/解析模块，不依赖 Web API 或调度器。

升级采用参数契约版本；旧模板和任务保留旧解释规则，禁止静默重新解释已有快照。新能力带 Worker 版本门槛，旧 Worker 不领取含新挂载/绑定的任务。测试覆盖类型与覆盖、批次原子校验、含空格参数传递、不同节点路径映射、未批准设备、设备/端口竞争、取消与租约丢失后释放、旧模板回归和客户端/服务端两种模式。先完成契约与执行端再开放表单，不交付只能保存但不能运行的配置。

## Worker 发布与升级管理

软件版本与协议号独立，源码内 worker/version.py 集中定义版本和能力；注册上报软件版本及安装收据中的发布摘要，旧实例显示未知。发布包由控制端已部署源码生成，仅包含 worker/runner Python 文件；管理员发布不可变摘要包，不接受任意 URL、脚本或 Docker flags。API 保存有界发布内容、每节点升级历史和修订。

独立节点升级执行器使用原 Worker 凭据轮询。管理员指定原服务单元、安装目录和全部 GPU 配置文件，执行器不重写它们。升级状态 DRAINING → APPLYING → VERIFYING → SUCCEEDED；回滚先取得 ROLLING_BACK 屏障，失败为 FAILED 并继续阻止准入，管理员确认后取消或重试。只有 DRAINING/FAILED 可取消；安装中的状态不能超时自动释放，以免迟到执行器替换正在运行的代码。

请求升级在调度锁内释放未领取预留；排空检查包含全机所有 GPU 的活动/未清理执行。执行器必须持有本地单实例锁，停止配置的全部原服务，再持有所有 state.lock 并检查主 journal 与 .runs，拒绝遗漏实例或残留执行。校验 SHA-256、归档路径和大小；在同盘准备新目录、记录事务，再替换安装目录。重启原服务后等待所有已注册 GPU 回报目标摘要。失败恢复备份并重启旧服务，保留升级 journal 以恢复中断流程；回滚失败不恢复调度。

执行器需独立安装，不能由正在被替换的 Worker 自更新。现有五节点本期不自动安装或改写 NFS 服务；UI 显示执行器在线与否。旧节点通过文档引导接入后才可升级。测试使用隔离目录与受控服务夹具，生产升级另作部署验收。

Worker 升级验收：隔离 API + 两个真实 systemd 用户 Worker（模拟 GPU）完成 0.9.0→0.10.0 发布升级，全部 GPU 摘要回连验证通过；原身份、凭据、恢复路径及服务挂载依赖保留。PostgreSQL 隔离迁移至 n407c89 通过。测试和操作说明见 docs/worker-upgrades.md，未改动五节点生产部署。
