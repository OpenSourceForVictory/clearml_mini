# Proposal

## Why
管理页已有评测机器、资源池和客户端 Docker 模板，但缺少 SSH 接入闭环、解除纳管、服务端实例和宿主机执行。需要把业务无关的机器、资源、模板、实例和评测协议分开，让用户接入自己的仿真和推理程序，不依赖 RoboTwin 特定实现。

## What Changes
- 区分 Worker 软件版本、协议和能力，提供逐 GPU 版本展示、管理员不可变包发布及全机排空升级；独立执行器负责校验、替换、原单元重启和失败恢复。
- 模板参数分为平台、业务、运行三类，定义类型化业务参数与 argv/env/输入文件绑定，贯通集合与逐任务执行；容器支持节点批准的逻辑目录及设备挂载，运行资源申请复用统一调度。
- 按业务模块明确状态归属、接口契约和故障恢复责任；优先控制模块内风险，共享资源和执行安全通过统一账本及跨模块一致性测试保障。
- 管理设置固定为机器管理、资源池管理、运行模板管理、账号管理；机器和模板各分客户端/服务端。
- 机器支持多角色，提供 SSH 环境检查、纳管进度、配置详情、停用/启用、排空后解除纳管；已有机器默认客户端，保留身份和配置。
- 复用 GPU 单池归属与排空迁移，补齐池编辑、停用、删除保护及清晰列表；不引入推理服务池。
- 两类模板均支持 Docker 与宿主机模式；客户端提供 SDK 包装业务命令与直接评测协议两种接入，支持逐回合事件、断线重试和最终结果。
- 服务端提供有资源预留的实例部署、健康状态、停止/重新启动和日志；服务地址可供现有客户端地址列表使用。
- 宿主机执行限管理员批准环境及命令，沿用租约和清理确认，使用独立执行目录和进程生命周期管理。
- 保留现有账号能力并补齐账号列表、角色/状态管理与密码重置，保护最后一个管理员。

## Capabilities

### New Capabilities
- `machine-administration`: 角色、SSH 纳管及机器生命周期。
- `resource-administration`: 已纳管 GPU 的资源池管理和删除保护。
- `runtime-templates`: 两类模板、两类执行方式及版本化配置。
- `host-execution`: 宿主机任务的准入、生命周期与恢复。
- `inference-instances`: 服务实例部署、健康、资源和日志。
- `administration-navigation`: 管理入口及账号管理。

### Modified Capabilities
无。保留 platform 的异构槽位与任务入库行为；既有已完成 change 中的成员排空、存储回执及地址列表语义继续有效。

## Impact
涉及 backend 模型/Alembic/API/调度器、worker 执行器、runner SDK、React 管理页面、部署配置、测试和文档。仅使用现有五节点验收，不纳入 .174。已有 Docker 模板默认兼容模式，不重建当前 NFS 单元或删除历史数据。SSH 纳管需要控制端独立执行器，凭据不落数据库或日志。参考 ClearML 官方 Agent 的队列拉取、执行配置和环境分离，不引入 ClearML 服务依赖。

重新纳管补齐：恢复原机器身份、一次性轮换凭据、分发完整节点包（Worker、runner/SDK、独立升级执行器和安装脚本），经 SSH 执行安装及全部实例回连验收后恢复准入。
