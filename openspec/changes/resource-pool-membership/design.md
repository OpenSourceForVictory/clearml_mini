# Design

## Context

见 proposal.md。当前 Slot.pool_id 非空；Register、Worker.run 及安装器要求 pool_id。Worker 启动时注册，换池通过重启时的本地配置触发；运行中换池返回 409。调度已使用 PostgreSQL 全局事务锁，机器 CPU/内存与并发按 worker_id 合计，存储 v4 已提供独立版本确认。管理页面包含成员、资源池、机器等长表单，计算资源页准入栏仅判断 quarantined。

本次涉及数据模型、注册协议、执行恢复、页面和上线迁移，需要设计文档。

## Goals / Non-Goals

**Goals:** 无池接入；平台管理 GPU 单池归属；批量操作、排空迁移、旧配置不覆盖；复用现有存储配置与任务恢复；交付包含上线。

**Non-Goals:** 一张 GPU 同时属于多个池、物理 GPU 切片、自动跨池溢出调度、一次性邀请认证、自动安装 Docker/驱动、镜像分发、动态 GPU 热插拔管理、机器任意远程命令、资源池物理删除及历史任务归属迁移。本轮不扩展全部资源池 CRUD；沿用已有建池和共享策略编辑。

## Decisions

### 1. 用可空归属表示未分配

Slot.pool_id 改为可空外键，仍表示实际生效的唯一池；增加 membership_revision（初始 0）、desired_pool_id（可空）、membership_applied_revision、membership_updated_at。revision=0 的既有设备保持本地注册管理；首次无 pool_id 注册的新设备进入平台管理模式（revision=1，desired_pool_id=null，applied_revision=1）。管理员首次写入后始终由平台管理，不提供退回本地管理开关。

迁移中旧记录保持原 pool_id，将 desired_pool_id 回填为该值、两个 revision 为 0。成员变更审计单独记录操作者、槽位、旧实际池、目标池、版本和时间，不借用要求 job_id 的任务事件表。历史 Job.pool_id 和 Run 身份不因换池修改。

替代方案是建一个默认“未分配池”，但那会让待配置设备看起来可执行任务，还会混淆真实与模拟设备。

### 2. 成员变更由服务器生效，不绑定 Worker 本地配置

注册请求允许省略/传 null 的 pool_id。对从未平台托管的旧设备保持原注册约束；对平台托管设备忽略本地 pool_id 归属意图，包括其已失效的旧池 ID，仍严格校验机器凭据、GPU UUID、GPU index 及物理/模拟身份。legacy 模式通过注册换池时同步实际/期望池，保持版本为 0。重连只更新硬件和在线状态，不回写实际/期望成员关系。已登记设备不能通过改变物理/模拟身份绕过目标池校验。

归属只影响服务端调度，Worker 执行仍读取 claim 返回的任务快照，因此无须像目录设置那样等待 Worker 应用本地路径。注册/监督心跳可返回实际和期望归属，用于诊断；不要求旧 Worker 解析新增字段。新 Worker 仍声明 v4，省略 pool_id 是兼容扩展；先升级 API 再升级 Worker。`claim` 处理原执行与 cleanup 在检查池和新准入之前，保证 pool_id=null 不破坏恢复路径。

替代方案是远程改 JSON 再重启，涉及宿主文件写入、重启与旧配置竞争，没必要用于服务端资源分配。

### 3. 原子接受，逐卡排空生效

新增管理员成员批量 PUT 接口（建议 `/api/v1/admin/resource-memberships`），请求包含 1–256 个唯一 slot_id、各自 expected_revision，以及统一目标 pool_id 或 null。使用现有全局调度锁，先完整验证再写入。任何权限、版本、目标池启用状态、物理/模拟类型、最低显存问题均整体拒绝，返回有界逐项原因；重复槽位拒绝。

保存时递增各卡版本、记录目标和审计，将未领取 RESERVED 退回原任务的 PENDING 并清空资源预留。已 STARTING/RUNNING/CANCEL_REQUESTED、终态但 cleanup_confirmed=false 的执行保留。保存、调度、claim、cleanup 共用锁。调度和新 claim 在 desired/applied 不一致时拒绝准入，恢复和续租不受影响。

保存事务内及后续 reconcile/cleanup 中，若槽位无任何持有执行，则重新验证目标池，更新实际 pool_id 和 applied_revision；否则持续排空。目标失效则保持旧实际归属、停止新准入并显示原因，允许管理员用新版本修正。管理员可提交原池作为新目标取消迁移；同样按无持有执行的条件完成确认，不把待清理执行强行释放。

整批请求原子接受不等于整批同时完成；每卡独立生效，界面显示差异。离线空闲设备可保存并生效归属，但仍显示离线，不计为就绪；有遗留执行的离线卡持续等待清理。

### 4. 统一成员状态，区分设备就绪与任务匹配

管理员列表返回当前/期望池、版本、变更时间和成员状态（unassigned、assigned、draining、blocked），另给在线、存储和磁盘/清理等基础准入原因列表。注册凭据尚无槽位的机器显示“等待连接”。已分配、在线不直接等同于任意任务可调度，GPU 型号、显存、客户端镜像与全局额度仍在具体任务准入中计算。

池详情按实际归属统计卡数、在线数、基础就绪数、型号及总显存分布；待加入成员单列。排队及运行任务按 Job.pool_id 统计，迁移中的执行继续算原池，不重复算两池资源。普通用户保留摘要访问，不获得成员修改或凭据权限。GPU 不同型号不合并成“算力百分比”。

### 5. 注册与安装维持简单

管理设置拆成机器管理、资源池管理、账号管理子页签；现有客户端模板功能继续可达，避免重复注册入口。机器页先创建凭据，下载配置允许“暂不分配资源池”。接入地址可编辑，回环地址提示其在 Worker 主机上的含义，不直接禁止用户已建立的合法隧道。真实/模拟设备显式选择，默认真实。没有资源池也能完成接入。

安装工具继续支持既有 --config/--instance 单卡用法，新增 --gpus all 或编号列表：本机发现 GPU 列表、验证编号，生成稳定的逐卡实例名、配置和独立 state_path，安装前打印计划。已存在实例默认不覆盖，显式更新不得更换 state_path；更新程序需空闲时进行。提供只读的 Worker 身份/服务能力查询接口（建议 GET /api/v1/worker/self）用于认证诊断，返回机器身份及支持能力而不返回凭据。--check 检查 API 可达性及凭据有效性、Docker、所选 GPU 与批准镜像，输出可操作原因但不输出 token，不把 --check 当作机器注册或成员修改。多卡检测是在安装时完成，不额外引入机器监督守护进程。

资源池页提供池列表/详情、已有成员、未分配设备和其他池设备筛选；按机器分组支持全选当前已登记卡及逐卡选择。操作前显示来源、目标和是否等待排空。轮询不覆盖筛选与选择草稿，版本冲突要求刷新；展示部分完成及拒绝原因。CPU/内存预算沿用机器级管理员额度，不因整机加入多个池而复制。

## Risks / Trade-offs

- [可空 pool_id 影响原代码] → 审计注册、claim、列表、统计、测试构造及类型定义；新任务分配要求有效池，恢复保持在先。
- [旧配置重连夺回成员] → 平台托管模式持久化，旧 hint 永不覆盖实际/期望值，覆盖反复重启测试。
- [双写导致重复准入] → 与现有调度锁共用事务，测试保存/claim/cleanup 并发、资源记账及 PostgreSQL 唯一约束。
- [多卡共享 CPU/内存重复计数] → 继续以 worker_id 汇总所有池持有执行，跨池双槽位验证。
- [离线迁移长期等待] → 明确区分离线与未清理，不新增不经清理的强制释放按钮。
- [资源池与目录同时修改] → 两个版本独立，只有成员、存储、磁盘等准入全部满足时才投递。
- [批量安装覆盖正在工作的实例] → 默认拒绝覆盖，记录每卡安装结果及失败位置，不删除已有恢复记录。

## Migration Plan

1. 备份数据库/代码/镜像，升级迁移与 API/前端，旧成员归属原样保留，旧 Worker 继续运行。
2. 升级 Worker 与安装器，验证无池接入、两卡选择及旧配置重连。先使用专用测试身份和池验证迁移，不改生产 GPU 归属做测试。
3. 执行回归和浏览器验收，以及本机/R8000 专用 Worker 的无池接入、加入、运行中换池、移除、重启及再加入。双机单卡测试不替代真实多卡硬件验收。
4. 正式上线 API、前端、两台 Worker；检查现有池成员不变、服务在线、管理页面可用，记录证据和回退位置。
5. 回滚前排空变更并处理所有未分配槽位（分配兼容池或清理从未执行的测试槽位）；确认无 null pool_id 再恢复非空约束。不得删有历史执行的设备以强行降级。回滚 Worker/API 时恢复相符的配置，保留任务和目录快照。
