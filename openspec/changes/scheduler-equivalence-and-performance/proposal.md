# Proposal

## Why

调度必须先保证资源不超分配、任务不重复执行及清理后才释放，再讨论性能。当前调度轮次含历史编排遍历、重复资源规划与候选排序；需要用隔离数据建立瓶颈基线，以行为等价测试约束优化，而非依据静态代码判断直接拆锁。

## What Changes

- 保存当前流程、跨模块资源账本与状态转换约束，并标出既有规范和实现的差异。
- 建立可重复的 PostgreSQL 调度基线、确定性决策对照及竞争故障测试；区分历史增长、排队增长、执行并发的影响。
- 实施阶段仅按测量结果逐项优化批量查询、候选组织和单轮计算复用，保留原有事务与锁边界、调度顺序、领取复查和清理语义。
- 每一项优化独立验证及提交，无收益或决策不一致则不发布。当前请求仅完成方案，不实施、不部署。

## Capabilities

### New Capabilities

无。本变更是现有行为等价重构与验证工具，设置 `skip_specs: true`，不新增业务规范。

### Modified Capabilities

无。`batch-priority` 的用户内部优先级与跨用户轮转不变。`platform` 的历史 ClearML Task 恢复描述与现有 Run/Worker 实现不同，记录在设计中，不在性能变更里重定义生命周期。

## Impact

拟涉及 `backend/app/scheduling.py`、`orchestration_scheduler.py` 及对应测试、隔离基准工具；领取、取消、重试、健康检查、清理路径作为关联验证范围。第一阶段不修改 HTTP/Worker 协议、数据库结构、CPU/RAM/显存准入算法、用户界面或部署拓扑，不引入新依赖。实现时同步运维说明及项目 Skill 索引；不以已有控制通道压测宣称调度容量。
