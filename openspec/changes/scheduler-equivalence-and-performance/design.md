# Design

## Context

审查基线：`3393a94`，2026-11-24。以下是当前代码行为，不代表所有历史设计均已实现。动机见 proposal.md。

### 调度链路与责任

| 阶段 | 实现 | 行为与边界 |
| --- | --- | --- |
| 提交与预检 | orchestration_scheduler.structural_pair、提交接口 | 检查结构容量，不预约实际设备 |
| 周期入口 | scheduling.loop / tick、main lifespan | 普通 API 内调度线程；控制 API 不启动调度。每轮结束后等待配置间隔，实际周期间隔包含 tick 耗时 |
| 对账 | scheduling.reconcile、orchestration_scheduler.reconcile、memberships.reconcile | 未领取预约过期退回；执行超时复查；服务绑定与池成员对账 |
| 账本 | tick 与 Planner | ACTIVE 或 cleanup_confirmed=false 的所有尝试均计账，不限最新尝试 |
| 排队 | tick | 用户轮转；用户内部优先级降序、批次创建时间、任务创建时间和 ID；跳过暂不可满足的任务，不抢占 |
| 放置 | eligible/node_codes、Planner.pair | 卡、节点、池、角色、环境、遥测、端口及配额联合判断；服务端和客户端共同消耗资源 |
| 预约 | reserve、allocate_pair | 同一事务保存执行 ID、设备和资源快照；托管客户端可先绑定地址但处于 waiting_service |
| 服务补齐 | fill_desired_instances | 正常客户端分配后按编排 batch_id 扫描补实例；与普通任务优先级不是同一排序路径 |
| 领取 | execution.claim、binding_ready | 无候选免全局锁；有候选锁内复核。服务必须就绪、健康新鲜、当前执行 RUNNING 且租约有效，并匹配绑定执行代次 |
| 运行/结束 | execution heartbeat/complete/cleanup | 普通续租采用局部行锁；首次启动转换、完成与清理等保留全局互斥；清理确认后资源才可复用 |
| 用户控制 | batch_controls、retries | 暂停撤回未启动预约；运行中取消是请求；旧尝试未清理不得重试，新尝试获得新的执行 ID |

`LOCK_ID=82510401` 的事务级 advisory lock 串行化资源写决策；运行续租不被它全面串行化。超时对账另取 Run 行锁，刷新并复查租约。数据库普通隔离级别下多条读取不是同一时刻的物理快照；遥测仍可能更新，不能把本轮计算上下文描述为全库一致快照。

显存和主机内存的准入同时参考总量、观测剩余和全部未清理预约；缺少按进程归因数据时有保守重复计入。逻辑预约与执行硬限制不同，本次不得调整计算公式或将可见设备变量宣传为安全隔离。

### 规范与实现的已知差异

- durable `platform` 仍提及 ClearML Task 恢复和拒绝 RoboTwin，不能用它推断现有 Worker 行为；本次记录差异，不借性能重构修改业务规范。
- 用户要求的断联执行完再补报，与现有租约超期停止/超时路径存在差距；这是另一个生命周期变更，本次不实现也不宣称已实现。
- 服务补实例的 batch_id 顺序是否应服从批次优先级属于策略问题；本次保持原顺序，单列后续评审，避免性能修改暗中变更公平性。

## Goals / Non-Goals

**Goals:** 建立决策等价及资源安全证据；定位历史、队列、并发三种增长的实际成本；降低已证实的重复读取/计算成本。

**Non-Goals:** 不拆锁、不多调度器并行写、不引入 Redis 或跨轮缓存、不截断队列、不新增抢占/回填、不改失联/超时/重派，不变更协议、表结构或部署。事件唤醒和独立调度进程仅作后续方向。规划完成不等于实施完成。

## Decisions

### 1. 先测量，再逐项优化

优先在隔离测试工具中按函数阶段计时和 SQLAlchemy 事件统计查询，避免给生产日志引入每任务高基数采样。记录 tick 总耗时、各阶段耗时、事务持锁时长、查询数、实际物化对象数、CPU/RSS、PG 锁等待与连接等待。集成负载另采集 heartbeat/claim/complete 的 p50/p95/p99、错误数、排队到预约时延及最长等待。

静态风险候选：全量历史批次/编排/实例扫描；每次配对重建 Planner；逐记录查关联 Job；每用户每轮重新过滤排序、设备候选反复排序。先验证贡献，不预先承诺排序、缓存或数据库连接池就是瓶颈。

基准数据按单一变量增加：

| 维度 | 规模与固定条件 |
| --- | --- |
| 历史 | 0 / 1,000 / 10,000 已完成批次，固定活动与排队；包含未清理旧尝试、待停止服务、可重评测批次 |
| 排队 | 100 / 1,000 / 10,000 任务，固定节点；分别全不可满足、前部不可满足后部可满足、多用户多池 |
| 活动 | 50 / 100 / 200 模拟 Worker，固定任务分布；心跳、日志、遥测、领取、完成并行，注明是否一个 Worker 对应一张卡 |
| 编排 | 无托管服务、每批一个服务、同节点不同卡多个同名实例，包含端口不足、就绪等待、失败恢复 |

不用全组合笛卡尔积；先单变量，瓶颈点再混合。固定数据库版本、数据种子、机器/池配置、HTTP 连接复用和线程配置。预热后至少五次交替运行旧/新版本；各自数据库使用同一数据副本，不同时压同一数据库。性能运行不插桩覆盖率。保留失败、超时、跳过与资源不足证据，不把跳过档计成功。是否支持 100/200 Worker 以实测为准。

### 2. 第一阶段的候选实现边界

先批量关联读取与单轮候选分组，保持原排序键、稳定排序和既有候选遍历次序；数据库本来未承诺排序的路径，不顺手新增不同择优策略。

需要复用 Planner 时，使用同一事务内、仅存活一轮的资源上下文：设备/节点/用户/批次占用、端点占用、完整未清理 Run 集合及必要关联。每次客户端、服务端或额外实例预约后统一更新上下文，再进行下一次判断。任何未覆盖写路径都禁止复用该上下文。端口选择及领取复查仍按既有数据库边界执行。

历史筛选必须证明覆盖所有后续动作：未结束任务、等待服务的预约、未清理历史尝试、仍 desired_running 的托管服务及需自动停止的服务；不能只看批次终态、最新尝试或缓存“已完成”标记。已完成批次重新评测后须自然重新进入候选集合。若无法证明筛选等价，保留扫描并只减少关联查询。

不使用生产双调度器作对照。决策对照在两份隔离数据库运行；只读影子评估不能调用 reserve/flush/commit 或触发服务创建。

### 3. 等价性与测试矩阵

旧实现作为固定提交的测试参考，不在生产维护两套调度器。固定时钟、实体 ID 和事件序列；随机执行 ID 用一一映射归一，但须额外断言唯一性、代次变化和引用一致，禁止忽略身份错误。比较每轮任务/设备/服务绑定、预约额度、状态/原因、事件顺序、轮转游标及最终清理结果；并发测试按合法串行结果与不变量断言，不要求线程抢锁顺序相同。

| 场景 | 已有测试入口 | 本次需补强的证据 |
| --- | --- | --- |
| 优先级/FIFO/轮转/不可调度跳过 | test_scheduling.py、test_batch_priority.py | 长队列、多轮、改优先级后、同时间键的旧新决策对照 |
| 同机多卡/共享/CPU/RAM/外部占用 | test_scheduling.py、test_gpu_sharing.py、test_resource_reporting.py | 跨池联合预算、服务补齐后下一任务不能超配；零运行限制仍保留预约 |
| 托管服务/多实例/就绪代次 | test_orchestrations.py、test_service_readiness.py | 不就绪不得领取；旧代次 ready 不解锁新执行；端口耗尽和启动失败回滚 |
| 暂停/恢复/重评测/清理 | test_batch_controls.py、test_execution.py | 已终态历史重新入队、旧尝试未清理仍占账、延迟清理幂等 |
| 租约与局部锁 | test_execution_lock_scope.py | tick 读取后续租更新、取消并发、跳过忙行后下轮回收 |
| 多调度器/提交竞争 | integration/test_scheduler_concurrency.py、test_orchestration_race.py | 真 PostgreSQL 中领取/取消/完成/清理竞争；不依赖 SQLite 证明锁正确 |
| 故障边界 | 现有恢复测试作为关联回归 | 预约事务提交前/后杀进程，重启不重复预约、端口/资源无泄漏；补实例失败整事务回滚 |
| 性能 | 现有 control_plane_load 仅作 HTTP 负载参考 | 新增实际 tick 与真实预约/释放循环基准，不以静态心跳压测替代调度测量 |

每次优化正常、边界、失败路径都要测试；不只增加与实现逐行对应的断言。沿用 `python -m scripts.test_coverage` 统计，关键功能行/分支至少 90%/80%，每目录至少 80%/70%；独立进程未合并不得宣称统计，专项通过数不替代覆盖率。

### 4. 发布判据

正确性门槛为零决策差异（除已说明的 ID 归一）、零重复执行、零资源超配/提前释放，所有竞争与故障场景通过。性能方面每项优化必须降低目标查询/物化量或重复计算计数，且同配置五轮中位 tick 耗时改善；端到端心跳/领取 p99 与队列尾部等待不得出现可重复退化。暂以大于基线 10% 且超出旧版本自身重复运行波动范围的恶化作为阻断信号；噪声不确定则追加配对测试，不能称验收通过。没有收益则不合并该优化。

### 5. 优秀实践的取舍

- [Kubernetes Scheduling Framework](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/) 将调度周期与绑定周期区分，调度决策串行，提供 Filter/Score/Reserve/Unreserve 等阶段。借鉴阶段边界与预约回滚，不照搬其完整插件框架。
- [Slurm Scheduling Configuration](https://slurm.schedmd.com/sched_config.html) 结合事件触发与周期扫描；后续可研究，但本阶段不新增通知可靠性问题。回填依赖资源与时间预测，我们有不限时任务，不能将“跳过不可满足任务”称为保证不延误高优先级的回填。
- [ClearML Agent](https://clear.ml/docs/latest/docs/clearml_agent/) 的排队领取、环境准备和执行报告可参考；不能据此认为其天然覆盖本项目成对服务预约、NPU 共享与清理账本。
- [Ray Resources](https://docs.ray.io/en/latest/ray-core/scheduling/resources.html) 区分逻辑资源调度与物理限制，支持我们保留预约与运行限制的两条语义。

## Risks / Trade-offs

- 历史过滤漏掉释放或恢复动作 → 用历史未清理、重试和服务停止反例验证；无法证明则不裁剪。
- 单轮复用导致账本陈旧 → 每种预约路径统一增量维护，领取复查不变；不跨轮复用。
- 排序缓存改变公平性/占用优先级 → 占用变化后维护原排序，不能一次排序沿用整轮。
- 长事务仍存在 → 第一阶段接受单写者边界，记录剩余持锁成本，后续拆锁另案设计。
- 差分把既有错误固化 → 参考实现违反资源/生命周期不变量时保留失败，单独修复评审，不能为了等价接受错误。
- 大压测影响业务 → 只用独立测试数据库/容器及可控测试程序，不重装现有业务节点，不向生产灌造历史数据。

## Migration Plan

2026-11-24 已进入实施，隔离基准工具第一阶段完成；性能算法、迁移与部署尚未变更。实施顺序为基线与正确性测试、逐项等价优化、专项回归/覆盖率、隔离负载和真机小批次，最后按用户发布安排部署。真机验证覆盖宿主机/容器及 GPU/NPU；算术/样例测试只证明调度执行，不冒充模型评测。

第一阶段不增加数据库字段或 Worker 协议；通过 API 代码回滚恢复旧实现，保留既有 Run、预约与执行 ID。发布和回滚都确保只有一个有效调度写入口，避免旧新调度在切换期分别占用写窗口；HTTP 控制通道按现有部署保持可用，不停止 Worker 业务来作性能对照。上线前检查活动/清理状态，采用现有发布步骤。

## Open Questions

测量后才能确定各阶段占比与收益排序，以及目标硬件上的稳定规模。它们不影响先保持语义和锁边界的方案；若数据表明需要索引迁移、拆锁或策略变化，停止相应优化并另写设计。
