# Design

## Context

worker/services.py 使用同步 socket/urllib，单次超时 1 秒；worker/client.py 在日志处理后探测并上传。API 保存 health_ready/health_at，service_dependencies.py 采用固定 15 秒有效期并校验在线和执行租约。已有测试覆盖 HTTP/TCP、重定向、启动超时及过期报告，但没有 WS 和非阻塞检查。

## Goals / Non-Goals

**Goals:** 协议适配与生命周期隔离，模板可声明、调度可消费、用户能诊断；宿主机和容器一致。

**Non-Goals:** 不引入推理服务池；不实现任意脚本探测、自动重启、业务重放或完整密钥托管系统；不使用 ping/pong 代表模型就绪。不将外部地址探测失败解释为平台有权停止该服务。

## Decisions

### 配置和协议适配

新增版本化 readiness 对象：kind=tcp/http/websocket，port=business 或独立声明端口，path、TLS 设置、headers/headers_from_env、subprotocols，以及 WS mode=handshake/message、可选 send_text 和 expect。expect 只支持 text_equals 或 JSON Pointer 指定标量相等；HTTP 配置允许状态码集合及可选 expect。不支持正则、脚本、二进制编码适配和多轮会话，避免将探测变成业务工作流。用户侧给出握手、接收欢迎消息、发送健康消息三种 WS 示例。

建议新配置默认 interval=5s、timeout=2s、startup_timeout=120s、success_threshold=1、failure_threshold=3，stale_after=20s；验证 stale_after >= 2*interval+timeout。完整探测共享截止时间，禁止逐阶段无限累积。上限初值：响应 64 KiB、WS 16 条消息、单 Worker 同时 4 个检查；调度采用结束后间隔加小幅抖动。实际默认值以验收耗时确认，但不改变有界语义。

HTTP 禁止重定向和环境代理，WS 同样禁用隐式代理与重定向，默认 TLS 验证，允许节点已批准 CA 引用。业务地址继续由平台分配；独立健康端口纳入同一服务端口预留、容器映射和清理，不接受随意探测其他主机的 URL。宿主机程序通过平台绑定获得健康监听端口。

认证采用节点本地专用探测凭据配置：模板仅保存允许的环境变量引用名；由管理员在 Worker 服务环境中提供对应值并批准引用名。业务进程不自动继承探测密钥。引用在节点缺失时预检失败；普通请求头禁止明文 Authorization/Cookie 等敏感字段。模板复制、API 快照、日志仅保留引用。完整平台密钥管理另案处理。

### 模块和数据流

- 模板/API：共享配置校验、兼容转换、快照和能力要求；不执行网络检查。
- Worker 探测模块：独立异步事件循环，受限并发和真正可取消 I/O；协议适配器只返回结构化结果。DNS、TLS、接收也受总期限约束，不依赖无法终止的阻塞线程作为保证。
- Worker 主循环：读取最近结果并非阻塞上报；日志失败不能跳过检查、启动超时或停止处理。上报队列只保留最新结果，不堆积旧报告。
- API 状态聚合：统一阈值和 freshness 计算，实例展示、预检、依赖选择和领取前复核复用同一规则。
- Agent：维持机器监测与版本管理；不承担业务服务探测。

ProbeResult 包含 execution_id、API 签发的 probe_epoch、单调 sequence、检查时间、duration_ms、success、phase、error_code 与脱敏摘要。API 校验租约/当前执行/代际，按序接受结果；持久化最后序号、成功失败计数和聚合就绪状态。重复上报幂等且不更新 freshness。Worker 恢复时向 API 获取新代际并重置计数为未知，旧代际结果失效。队列上报不得将过旧本地结果包装成新结果；携带采样年龄，使用服务端接收时间减采样年龄确定有效期并校验合理范围。

### 生命周期和调度

进程状态与 readiness 分开：STARTING/READY/NOT_READY/UNKNOWN 是就绪视图，停止/失败沿用执行终态。首次就绪前失败阈值不会提前终止加载；总启动期限必须独立于日志上传和探测结果检查。Worker 重启不能重置总启动期限。报告过期即 UNKNOWN；恢复从成功阈值重新确认。

就绪下降只阻止新分配和尚未启动的领取，不迁移、重放或杀死既有客户端。启动超时走现有停止、清理确认与资源释放；一般运行期健康失败不自动重启。检查间隔可配后统一替换 API 展示和调度器中的固定 15 秒规则，防止两个模块判断不一致。

客户端执行前检查属于客户端 Worker 的启动阶段：TCP 业务验证仅连通，HTTP/WS 根据协议验证连接/TLS/握手，不重复发送可能有副作用的健康消息。检查具有短期限，失败结束本次尝试并完成清理，使用现有显式重试机制，不无限占卡等待、不自动重放业务。诊断携带客户端节点、服务执行与目标地址。此路径也适用于用户提供的外部地址，但无停止外部服务权限。连接成功不宣称业务模型健康。

### UI 和诊断

服务端模板增加健康检查功能页，按类型显示字段、说明与示例；注册/查看/复制共用表单逻辑。实例和批次关联服务展示检查阶段、最近探测时间、耗时、阈值计数、启动剩余期限及脱敏错误。错误码映射配置位置（路径/端口/认证引用/TLS/Worker 升级）与日志入口；权限不足显示需要管理员处理。只读页面不得展示完整响应。

## Risks / Trade-offs

- [探测占用服务连接] → 轻量消息、周期与并发上限、每次关闭，不调用真实推理作为默认探测。
- [短暂失败造成调度抖动] → 连续阈值；失联仍按有效期停止新分配。
- [老 Worker 将未知配置忽略] → 新能力准入；同时核查重新纳管和升级包中的依赖。
- [节点凭据不一致] → 引用按节点预检，缺失明确阻塞，不回退无认证。
- [健康端口冲突或泄漏] → 沿用服务端口锁扩展端口集合，覆盖并发分配和清理测试。
- [客户端检查不能消除检查后的网络故障] → 明确只证明检查时连通，运行期业务错误仍走现有任务失败机制。

## Migration Plan

1. 增量数据库迁移和 API 兼容读写先部署；旧 flat health_type/health_path/startup_timeout 归一化为 legacy 语义（阈值 1、原 freshness），不得改变既有快照。
2. 发布带新协议和探测凭据预检能力的 Worker，通过升级/重新纳管安装依赖并验收。
3. 发布 UI，只有具备所需能力的节点能运行新配置；所有相关准入与服务恢复入口必须检查能力。
4. 本地协议矩阵通过后，在可用纳管机器做两节点服务/客户端验收，记录实例、批次、心跳和清理证据。
5. 回滚前暂停新配置提交并排空使用新检查的执行；保留增量字段与快照，旧 Worker 只接收 legacy 模板。不能让旧 API 将新模板按 TCP 启动。
