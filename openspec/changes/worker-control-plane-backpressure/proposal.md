# Proposal

## Why

多 Worker 并发时，入口处理容量、连接池、长事务、全局锁和重试会共同放大负载；局部扩池无法保证调度和执行不被日志等流量拖住。需要贯通请求到资源释放的统一预算与可靠补传设计，并以真实 PostgreSQL 混合负载确定验证范围。

## What Changes

- 按执行安全与生命周期、调度所需最新状态、可靠业务结果、日志与产物区分交付语义，贯通入口、处理并发、数据库及 Worker 重试预算。
- 为续租、服务就绪/失效、取消、完成和清理保留处理能力；调度拥有独立预算，领取轮询不能挤占执行续租。
- 心跳和监控继续更新最新数据，允许合并非权威采样；权威租约必须落库确认，不用内存排队伪造续租成功。
- 缩小全局锁及事务范围，分离 Agent 期望配置与观察状态，审查设备记录上的剩余竞争，保留身份、序号和资源预约原子性。
- 已领取任务支持可配置的断联最大容忍时间（有限时长或不限制），与心跳新鲜度和业务执行时限分离；容忍期内继续执行，超限由 Worker 停止业务并保留结果，平台等待停止及清理确认后释放资源；恢复后核对及补报，禁止自动重派。
- 分离业务结束、资源释放与数据同步；节点可靠缓冲及终态补传必须有容量、期限、权限和幂等边界，日志拥塞不阻塞业务收尾。
- 补齐领取响应丢失、Worker/机器重启、取消删除及客户端/服务端关联的恢复边界；首版不自动迁移或重跑。
- 统一过载退避、观测指标、故障注入和混合负载验收，保留失败档位，禁止将连接数等同于 Worker 数量。

## Capabilities

### New Capabilities

- `worker-control-plane-backpressure`: 执行控制流量保护、有限背压、可靠延后上报及可验证容量。

### Modified Capabilities

无。此能力补充过载下的交付与隔离约束，既有业务结果判定、调度优先级及资源清理安全条件保持不变。

## Impact

涉及 API 入口及鉴权、数据库会话、调度、Agent/设备观察、Worker 执行循环、结果/日志/产物交付和界面同步状态。需数据库迁移、API/Worker 能力协商及分阶段发布；迁移期间禁止新旧 API 混写观察状态。宿主机与 Docker、GPU/NPU 共用交付约束，不改变业务程序接入协议。

本变更的断联执行、恢复对账及可靠补传仍为待实施设计。四角色 API 隔离已由独立变更 priority-api-isolation 完成并部署，不能据此认为本变更的恢复机制已上线。实施时同步运维、节点升级、日志与产物指南、界面指南及项目 Skill 参考；不引入 Redis 或外部消息队列，不承诺数据库整体不可用时仍能执行续租。
