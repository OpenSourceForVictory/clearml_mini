# Design

## Context

已核对：session_factory 未设置连接池参数，PostgreSQL 默认每进程 5+10、等待 30 秒，Worker HTTP 等待 5 秒。claim、旧日志、回合、产物及完成接口使用阻塞事务级 advisory lock。执行心跳使用 try lock，但随后 Worker/Slot/Run 行锁仍会等待；Agent 持 Worker 锁更新采样。调度 tick 从状态整理到预约和服务补足才提交。隔离 PostgreSQL 两连接实验已确认阻塞领取会让心跳拿不到连接。

新日志按 Run 行锁写，不应误述成所有日志都使用全局锁。共享产物直读已在文件 I/O 前释放 Session，应保留。节点心跳 commit 后的响应查询可能重新取得连接，应将响应查询计入总预算。此前 heartbeat-db-contention 修复用 Worker 行锁保护 connection JSON；不能直接移除，否则引入配置或采样丢更新。

Worker 的执行续租对 503 特殊重试，但普通服务健康、部分日志/结果/产物/完成路径的 APIError 会落入外层 stop_container；所以服务端快速拒绝不能单独上线。HTTP 请求超时也不会自动取消同步 SQL，客户端重试可能与原请求重叠。

## Goals / Non-Goals

保留所有权、租约、状态机、日志顺序、幂等与清理确认，防止过载被当成业务失败。保留真实业务时限和看门狗。第一版不引入 Redis/消息队列、不异步缓存权威租约、不删审计/结果、不承诺无限 Worker。NPU/GPU、宿主机/Docker共用执行保护。

## Decisions

1. 连接预算分普通与控制两类。采用两个明确配置且有上限的连接池，控制请求只覆盖确切的 Worker 心跳、Agent 心跳与服务健康报告；普通请求、领取、日志、产物、页面和调度不借用控制池。鉴权必须与处理共享同一分类 Session，防止鉴权先卡普通池；不根据客户端传入标记决定池类别。总预算按 API 进程数累加，保留 PostgreSQL 管理余量。控制池保证的是可获取连接，不保证数据库CPU、行锁或线程池完全无争用。相应路由并发必须有界且在借连接之前快速拒绝。
2. 在请求事务内设置有限 lock_timeout，连接 pool_timeout 和语句预算短于客户端等待时间；多个语句的累计时间另用请求预算控制，不声称单个 statement_timeout 就是整个请求时限。超时回滚、释放后返回 503 和 Retry-After，不把所有 SQLAlchemy 异常笼统转成繁忙。迁移、备份不继承在线请求的短超时。
3. 高频领取使用非阻塞调度锁；保留正确的调度锁→Worker→Slot/Run顺序。心跳没有必须写整机状态时，是否可减少 Worker 锁须由并发授权/升级/重纳管撤销测试证明，不能仅靠压测移除锁。改写连接 JSON 必须继续锁定并刷新。缩短长事务内非数据库计算，产物解码/哈希移到取锁前但保留内容大小和幂等校验。
4. Worker 引入可重试错误元数据和统一退避工具，但不在共享 HTTP 客户端里无限重试；由领取、续租、上报调用层按身份/租约分别决定。监测只保留最新样本，日志/事件/完成保持原 journal 与游标，确认后推进。等待期间仍有独立续租或切回续租循环；每次重试受剩余租约与取消信号限制。带抖动的退避上限不越过看门狗截止；旧日志及普通探测同样覆盖。404/409/400/413/422等既有终止语义不混入过载重试。
5. 分阶段验证：先回归历史锁保护与失败恢复，再真实 PostgreSQL 小连接池故障注入，最后带实际 HTTP 的阶梯混合负载。模拟 Worker 压测不是 GPU/NPU模型验收；真实短任务分别验证宿主机和 Docker 在日志/产物暂时拒绝后不被误停。
6. 提供结构化诊断字段：请求类别、连接等待/事务时长、繁忙原因、checked-out连接及超时计数，不输出SQL参数、凭据、日志正文。容量按50/100/200等档位逐步测试，首次不满足目标时停止加压，记录P95/P99、续租余量、采样新鲜度及失败路径，不将最大已测档位称为系统理论上限。

## Risks / Trade-offs

- 新503可能终止旧Worker业务 → 先发布新版Worker（兼容旧API）并在选定节点完成受控升级，再启用API背压；旧Worker常态可用，但过载可靠重试保证要求新版，明确升级范围。
- 多池提高数据库连接总量 → 配置校验并公开每进程预算；测试多API进程，不能通过无限增大pool掩盖慢事务。
- 分池不能解决行锁长期占用或同步线程耗尽 → 同时加有限锁等待、入口并发预算和重试，不作绝对可用性承诺。
- 单纯加重试导致结果重复 → 用既有执行ID/序号去重，响应丢失、进程重启和取消并发都需要回归。
- 限制调度事务可能影响批次优先级、公平性和联合资源预约 → 初版不随意拆事务；逐条优化查询并测量，任何分批调度改动必须验证同一原子预约和优先级要求。

## Migration Plan

不新增数据库表。API发布配置和运维说明同步。先验证新版Worker在旧API上正常，再升级选定节点，再启用服务端策略；需要软件版本更新，不改变执行协议正文。回滚服务端可保留新版Worker；在途任务不热替换代码、不删除恢复journal。本变更尚未实施或部署，容量值仍待测试。
