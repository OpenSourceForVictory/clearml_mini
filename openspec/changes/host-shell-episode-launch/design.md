# Design

## Context

当前 `HostBackend` 固定构造环境并用 systemd 以节点批准账号运行 `runner.cs_entry`；它与纳管 SSH 账号不是同一概念。`runner.command_sdk` 已在一个客户端任务内逐回合启动业务命令；直接协议程序自己循环，普通命令只能执行一次。Docker 和宿主机共用 `cs_entry`，因此新分支必须显式限制为宿主机模板。任务模板存储 JSON，可向 `host_runtime` 增字段而不改数据库列。

## Goals / Non-Goals

**Goals:** 保留 systemd 资源预约及设备隔离；使业务进程得到批准账号的登录环境；逐回合启动时统一参数与报告；旧模板和 Docker 行为不变。

**Non-Goals:** 不读取某个临时 SSH 会话的 `/proc` 环境；不允许模板自行选择 Unix 账号；不将服务端长驻进程按回合重启；不承诺从登录脚本还原交互式终端状态或自动加载未导出的 shell 变量。

## Decisions

1. `host_runtime.environment_source` 为 `explicit`（缺省）或 `login`；只在宿主机启动前，以节点批准的业务账号和其 passwd shell 运行有界的非交互登录 shell，读取 NUL 分隔的导出变量。失败显式报错。与让 root Worker 继承自身环境相比，这保留身份边界；与读取纳管 SSH 环境相比，可在重新纳管后稳定复现。仅接受正常变量名、限制环境大小，不在日志输出值。
2. 登录变量先合并，平台入口所需的 Python 路径、任务输入/输出和设备分配最终覆盖；模板和任务覆盖位于登录变量之后。NPU 已批准 CANN 安装环境仍在登录变量之后合并，最终设备变量由平台固定。平台 runner 使用最小安全启动环境；业务完整环境保存在私有执行输入中并只交给业务子进程。
3. `host_runtime.episode_launch` 为 `whole_task`（缺省）或 `per_episode`，仅宿主机客户端可选。SDK 命令已有逐回合适配器，不重复实现；直接协议新增适配器，每次以单回合输入启动业务，解析其 `final` 单回合结果并由外层发事件与汇总；普通命令新增适配器，以退出码决定该回合是否完成，不生成业务成功率。宿主机执行单元和资源预约跨全部回合保持不变，取消或超时杀整个控制组。
4. 单回合输入另存于执行工作目录，包含原任务业务参数、`episodes=1`、该回合种子和原任务标识，并提供 `MINI_EVAL_EPISODE_ID`、`MINI_EVAL_EPISODE_SEED` 等变量。类型化业务参数与平台映射沿用现有 `bind_values`/`bind_platform`；不通过 shell 拼接 argv。直接协议输出由适配器解析，拒绝重复、缺失或不一致的最终汇总，避免把退出码 0 当作业务成功。
5. 普通命令只有选择宿主机逐回合启动时可提交多回合；API/向导/报告需按此模式显示回合数和完成进度，但继续区别于评测目标成功率。旧普通命令限制仍为一次。设置下发需 Worker 协议门槛，旧节点不能接收新模式。

## Risks / Trade-offs

- 登录脚本可能访问网络、打印文本或等待输入 → 非交互、无 TTY、有时限，输出用 NUL 帧解析，超时和无效输出显式失败。
- 登录环境可能含敏感变量 → 私有执行文件只允许业务账号读取，API/日志不回传变量值；环境值长度和总量有界。
- NPU CANN 登录环境与节点批准环境可能重复 → 保留当前 CANN 检测与设备覆盖顺序，真机验证 `torch_npu` 导入及设备可见性。
- 直接协议已有程序可能以整任务为假设 → 只有显式新模板采用逐回合，旧模板不改变。

## Migration Plan

先发布 API/前端及 Worker/runner，升级选用此能力的节点，之后创建新版本宿主机客户端模板并显式启用。回滚时停用新模板，旧模板及 Docker 模板继续运行；无需数据库迁移。真机用短小的 CPU/GPU/NPU 程序验证进程身份、导出变量、设备分配、逐回合输入及结果，不把模拟程序验收称为模型质量评测。
