# Design

## Context

当前 `HostBackend` 固定构造环境并用 systemd 以节点批准账号运行 `runner.cs_entry`；它与纳管 SSH 账号不是同一概念。`runner.command_sdk` 已在一个客户端任务内逐回合启动业务命令；直接协议程序自己循环，普通命令只能执行一次。Docker 和宿主机共用 `cs_entry`，因此新分支必须显式限制为宿主机模板。任务模板存储 JSON，可向 `host_runtime` 增字段而不改数据库列。

## Goals / Non-Goals

**Goals:** 保留 systemd 资源预约及设备隔离；使业务进程得到批准账号的登录环境；逐回合启动时统一参数与报告；旧模板和 Docker 行为不变。

**Non-Goals:** 不读取某个临时 SSH 会话的 `/proc` 环境；不允许模板自行选择 Unix 账号；不将服务端长驻进程按回合重启；不承诺从登录脚本还原交互式终端状态或自动加载未导出的 shell 变量。

## Decisions

1. `host_runtime.environment_source` 为 `explicit`（缺省）或 `login`；只在宿主机启动前，以节点批准的业务账号和其 passwd shell 运行有界的非交互登录 shell，读取 NUL 分隔的导出变量。失败显式报错。与让 root Worker 继承自身环境相比，这保留身份边界；与读取纳管 SSH 环境相比，可在重新纳管后稳定复现。仅接受正常变量名、限制环境大小，不在日志输出值。
2. 登录变量先合并，平台入口所需的 Python 路径、任务输入/输出和设备分配最终覆盖；模板和任务覆盖位于登录变量之后。NPU 已批准 CANN 安装环境仍在登录变量之后合并，最终设备变量由平台固定。平台 runner 使用最小安全启动环境；业务完整环境保存在私有执行输入中并只交给业务子进程。
3. `host_runtime.episode_launch` 为 `whole_task`（缺省）或 `per_episode`，仅宿主机客户端可选。SDK 命令已有逐回合适配器，不重复实现；直接协议新增适配器，每次以单回合输入启动业务，解析其 `final` 单回合结果并由外层发事件与汇总；普通命令新增适配器，以退出码决定该回合是否完成，不生成业务成功率。宿主机执行单元和资源预约跨全部回合保持不变，取消或超时杀整个控制组。
4. 单回合输入另存于执行工作目录，包含原任务业务参数、`episodes=1`、该回合种子和原任务标识，并提供 `MINI_EVAL_EPISODE_ID`、`MINI_EVAL_EPISODE_SEED` 等变量。类型化业务参数与平台映射沿用现有 `bind_values`/`bind_platform`；不通过 shell 拼接 argv。直接协议输出由适配器解析，拒绝重复、缺失或不一致的最终汇总，避免把退出码 0 当作业务成功。
5. 普通命令只有选择宿主机逐回合启动时可提交多回合；API/向导/报告需按此模式显示回合数和完成进度，但继续区别于评测目标成功率。旧普通命令限制仍为一次。设置下发需 Worker 协议门槛，旧节点不能接收新模式。

## Risks / Trade-offs

- 登录脚本可能访问网络、打印文本或等待输入 → 非交互、无 TTY、有时限，输出用 NUL 帧解析，超时和无效输出显式失败。
- 登录环境可能含敏感变量 → 私有执行文件只允许业务账号读取，API/日志不回传变量值；环境值长度和总量有界。
- NPU CANN 登录环境与节点批准环境可能重复 → 保留当前 CANN 检测与设备覆盖顺序，真机验证 `torch_npu` 导入及设备可见性。
- 直接协议已有程序可能以整任务为假设 → 只有显式新模板采用逐回合，旧模板不改变。

## Migration Plan

先发布 API/前端及 Worker/runner，升级选用此能力的节点，之后创建新版本宿主机客户端模板并显式启用。回滚时停用新模板，旧模板及 Docker 模板继续运行；无需数据库迁移。真机用短小的 CPU/GPU/NPU 程序验证进程身份、导出变量、设备分配、逐回合输入及结果，不把模拟程序验收称为模型质量评测。

## 验收恢复补充

首次执行握手 HTTP 503 与运行期暂时忙碌使用相同原则：等待后重试但不自行延长租约，取消/停止/租约到期禁止启动；其他 HTTP 拒绝保持现有处理。准入需区分真正来自未来的报告与 tick 开始后、读取候选前合法更新的报告；显式传入的测试时刻保持确定性。现场已发现首次握手 503 中断和自动准入异常，修复需自动领取端到端验收，不能用手动 tick 代替。

组件升级展示：统一发布入口与目标标签，单独说明 Runner 宿主机更新、容器适配器复制和旧镜像内置三种边界；不添加虚构 Runner 版本或无数据支持的安装状态。Agent 托管前提保持明确，不改变发布接口或升级执行器。

## 登录时限修正（2026-11-18）
用户确认业务账号登录环境读取超过 10 秒，旧 Worker 在业务启动前泛化为 could not be loaded。默认改 60 秒，节点 Worker JSON 顶层 host_login_timeout_seconds 可设整数 1–300；不从模板或业务环境读取该运维设置。超时给出账号与实际时限，不回显 Shell 输出；其他启动失败保持原逻辑。平台 STARTUP_TIMEOUT_SECONDS（默认120）仍是独立总启动预算，延长登录读取不豁免租约或启动期限。Worker补丁0.20.2、协议17，无迁移；更新后空闲时重启相应每卡Worker。

## Bash 导出函数兼容修正
现场 ml/module 导出函数被普通变量名校验误拒绝。解析时仅过滤 BASH_FUNC_*%% 项，不执行或传播函数定义；登录脚本已导出的 PATH/LD_LIBRARY_PATH 等仍保留，总数据上限保持在过滤之前。其他非法名称、过大普通变量和无效编码仍拒绝。Docker/显式模式不变，无迁移。

## 登录环境变量名放宽
登录环境通过 env 字典传递，不按 Shell 赋值语法限制名称。接受非空 UTF-8 名称，包括中划线、点、空格和非 ASCII 字符；NUL 分隔条目、首个等号分隔名称和值，名称不可能包含这两个分隔符。空名、缺等号、无效编码仍拒绝；保留函数过滤和大小限制，不改变模板字段规则、Docker 或平台覆盖优先级。

## 启动准备期间续租
初始 started=false 心跳成功后，独立线程按最多2秒间隔继续续租，覆盖等待启动锁、连接检查、create及start。业务线程离开启动阶段时停止并等待续租线程退出，随后沿用运行期心跳。仍按请求发出时刻计算本地期限并预留2秒；晚于本地租约的响应不能复活执行。503/网络超时只在原租约内重试，其他错误交回主线程既有清理路径；取消和停止在启动前、准备后、启动后检查，watchdog可并发停止已启动的执行。续租不把STARTING提前标为RUNNING，不绕过API启动总预算。此前两个任务成功、第三个报笼统超时尚无现场根因证据，本修复只解决代码已确认的启动阶段心跳空窗。

## 单回合映射时机修复
已复现 per_episode 输入为 episodes=1，但 cs_entry 在循环前把 task.episodes 映射成总量10。Worker 的旧占位符展开也会提前固化 seed、输入/工作/输出路径。宿主机显式 per_episode 客户端应推迟这些动态占位符到单回合上下文生成后，并在该上下文绑定 argv/env。SDK 命令显式 per_episode 同样采用单回合输入；旧 whole_task SDK 和 Docker 保持原契约。外层任务总量、事件编号与 journal 路径保持不变。无需数据库迁移，更新节点 Worker/Runner；不能将本地复现等同于不可访问现场的确定根因。

## 可选业务 PID 上限
节点 Worker JSON 的 execution_pids_limit 为 null/缺省或正整数（布尔值、字符串、0、负数拒绝）。缺省显式传 TasksMax=infinity 或 Docker --pids-limit=-1，不校验未申请的 pids 控制器；仍受运行时默认值、父级 cgroup 和系统资源约束。显式值在宿主机 create 时写入 launch.resource_limits.pids，start 从同一快照设置 TasksMax 和启动后校验，supervisor读取相同字段，避免不同默认值漂移。旧未带 pids 的 launch 在启动前补入节点当前配置；已启动执行不改写。Docker直接使用同一配置解析器。32进程的短时探测保持独立。无需迁移或重建业务镜像，更新并重启所有相关Worker后新执行生效。

0.21.4调整：null/省略改为显式不限制执行实例PID，请求运行时取消实例额度，但不绕过运行时systemd scope默认值、父级cgroup和系统资源限制。已有正整数保留，已启动实例不修改；升级需排空相关Worker后运行新实例验证。

真机边界：Docker -1在现场被规范化为PidsLimit=null，scope仍采用系统默认76745/57402。验收区分平台参数已取消与内核实际值；不为获得max而擅改daemon/系统默认配置。
