# Proposal

## Why

宿主机业务现在只收到 Worker 构造的固定环境，无法直接复用业务账号在机器上登录后可用的解释器、CANN 和自定义变量。客户端三种入口的回合启动语义也不一致：SDK 命令逐回合，直接协议由业务自行循环，普通命令固定只运行一次。

## What Changes

- 宿主机模板可选择读取已批准业务账号的登录 shell 环境；在该身份下取环境，并由平台最终覆盖保留的工作目录、输入、设备可见性等变量。
- 宿主机客户端模板可选择逐回合启动。每次启动获得单回合输入、回合编号和种子、类型化业务参数及平台映射；逐回合结果汇总为任务结果，失败停止并保留证据。
- SDK 命令沿用现有逐回合契约；直接评测协议和普通命令增加逐回合启动方式。旧模板保持原有行为；服务端长驻进程不逐回合启动。
- Docker 执行、环境和回合契约不变；增加针对性回归和真实节点宿主机验证。

## Capabilities

### New Capabilities

- `host-login-environment`: 宿主机业务账号的登录环境读取、合并、失败处理及身份边界。
- `host-episode-execution`: 宿主机客户端的单次与逐回合启动、参数传递和结果汇总。

### Modified Capabilities

无。

## Impact

涉及宿主机 Worker、客户端 runner、模板与提交校验、前端模板及任务向导、文档和 Skill。无需数据库列迁移：新设置保存在已有模板 JSON 中，旧模板按缺省值运行。节点 Worker 协议需要能力门槛，升级后才能接受新宿主机选项。

验收修复补充：首次执行握手在控制面 503 时按原租约重试；调度读取候选后刷新准入时间，避免新报告被旧 tick 时刻误拒绝。Worker 补丁版本 0.18.1、协议仍为 15，无数据库迁移。

后续 PID 修复范围：宿主机与 Docker 业务不再写死256；节点 execution_pids_limit 未设置/null时继承运行时默认值，正整数时统一设置和校验。Docker 的其他生命周期、协议和环境不变，无数据库迁移。
