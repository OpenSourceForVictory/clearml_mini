# Spec Delta

## Purpose

统一宿主机客户端在不同业务接入方式下的逐回合启动与参数传递，使平台能准确显示每回合结果，同时兼容已有整任务执行方式。

## ADDED Requirements

### Requirement: 宿主机客户端逐回合启动可选
系统 SHALL 允许宿主机客户端模板选择逐回合启动；旧模板及服务端 SHALL 保留原生命周期，Docker 模板 SHALL 保留现有执行行为。

#### Scenario: 多回合任务
- **WHEN** 用户以逐回合宿主机模板提交 N 回合客户端任务
- **THEN** 平台在同一资源预约和宿主机执行单元内依次启动 N 次业务程序，并逐次传递回合编号、种子和业务参数

#### Scenario: 旧模板与 Docker
- **WHEN** 模板未启用逐回合启动或使用 Docker
- **THEN** 它仍按原有单次、SDK 或直接协议行为运行

### Requirement: 不同入口的逐回合结果
系统 SHALL 对 SDK 命令、直接评测协议和普通命令提供逐回合结果契约，按实际结果生成回合事件和最终汇总，不把进程退出成功等同于评测成功。

#### Scenario: SDK 命令
- **WHEN** SDK 命令完成一个回合并写入有效结果 JSON
- **THEN** 平台记录该回合的 success、指标和产物，并继续下一个回合

#### Scenario: 直接评测协议
- **WHEN** 直接协议程序在单回合输入下退出并输出有效的单回合最终结果
- **THEN** 平台记录该回合结果，并将 N 次结果汇总为原任务最终结果

#### Scenario: 普通命令
- **WHEN** 逐回合普通命令退出 0
- **THEN** 平台记录该回合命令完成，并继续下一个回合；命令结果不伪装成目标成功率

#### Scenario: 某回合失败或超时
- **WHEN** 第 k 回合退出非零、结果无效或任务超时
- **THEN** 后续回合不启动，失败回合、日志和已完成回合保留，任务不标记成功

### Requirement: 单回合参数一致性
系统 SHALL 为每次启动提供稳定且可追踪的回合输入，包括原任务参数、平台映射、回合编号、回合种子、输入和结果路径；业务参数映射 SHALL 与整任务模式一致。

#### Scenario: 类型化参数和平台映射
- **WHEN** 模板把业务参数和服务地址映射到 argv 或环境变量
- **THEN** 每个回合的业务进程收到解析后的值以及该回合的编号和种子
