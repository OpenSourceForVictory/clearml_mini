# Why

用户目标为百人团队正常使用、百台节点并行执行；多卡节点须按设备Worker数计算，100节点×8卡的800Worker是候选验收规模，不能用100次心跳替代。当前四角色将HTTP准入数量绑定数据库池、入口等待绑定连接获取等待，导致数据库空闲仍有页面突发503。需要独立预算及可重复混合负载验证。

# What Changes

- 四角色内独立配置HTTP在途数量、有限队列长度、入口等待、数据库连接等待和请求SQL预算；默认兼容现有配置。
- 同步线程数量覆盖已准入同步处理及清理，保留用户操作、执行控制、调度、可靠结果和批量隔离。
- 提供面向百人/百节点的候选配置与容量说明，数据库总预算与余量校验不放宽；通过测试后才能称推荐生产容量。
- 验证多人页面与管理操作、Worker控制/观察/结果/日志和调度同场负载。暂缓长测和全项目覆盖率，保留短测与硬件边界。

# Capabilities

- api-capacity: 分类独立的HTTP和数据库容量配置。

## Modified Capabilities

无业务调度语义修改。

# Impact

backend/app/priority_runtime.py、db_budget.py、四角色Compose、容量测试工具、运维与项目Skill参考；无数据库迁移。单/双API配置兼容，不自动提高PostgreSQL max_connections。

2026-11-26后续：用户恢复全量与长测，并明确容量对照应固定API副本、检验数据库池设置。补充业务时延目标及测量缺口，不能将原专项通过等同长期SLA。
