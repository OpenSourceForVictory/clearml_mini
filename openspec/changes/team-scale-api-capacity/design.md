# Context

当前五进程四角色共有80个数据库连接上限；同步线程每进程至少40。Admission持有许可至响应结束，不等于数据库全程占用。API排队与取连接均用0.25秒，短SQL预算4秒；Worker单次HTTP5秒。数据库CPU/WAL/锁仍共享。

# Goals / Non-Goals

分开控制HTTP和数据库容量，让页面突发适度排队且不挤占控制通道。保留有界队列、鉴权前准入和配置指纹；不改变调度优先级、资源占用或事务语义，不承诺数据库无限连接。长压测与全项目覆盖率按用户指令后置。

# Decisions

1. 每类可覆盖 admission_limits（正整数）、queue_limits（非负整数）、queue_waits（非负有限秒）、pool_waits（正有限秒）及request_budgets（正有限秒）。未知类别拒绝；缺失按旧默认继承，scheduler不能配置HTTP准入。
2. 入口开始到SQL完成共用总截止，入口等待+连接等待须小于该类请求预算；Worker相关类别预算仍小于5秒，Web可配置更长预算。SQL锁等待保持独立且不得超过请求剩余时间。
3. 数据库连接上限只受pool_sizes控制。HTTP准入可以更大，线程额度据HTTP名额计算；不能以扩大线程数冒充吞吐提升。队列满与等待超时返回503并Retry-After。
4. 所有角色共用同一配置清单/指纹，角色仅创建自己的池，唯一调度器不变。增加连接须核对全部副本预算、PostgreSQL max_connections和其他客户端余量。
5. 候选配置先维持80连接、提高页面HTTP突发容纳和分类等待；只有混合测试表明连接获取成为瓶颈且数据库有余量才提高数据库总预算。不能预先宣称800Worker达标。

# Risks / Trade-offs

更长等待可能占同步线程、更高准入可能增加CPU与内存；故需要独立观测成功延迟/503原因、积压和生命周期正确性。页面可等更久但用户控制操作仍独立保留。用户需求中的百人按100在线会话与突发操作测试，不假定每人持续满速提交。

# Migration Plan

新增配置默认兼容，Compose显式透传；同一镜像全部角色更新。无迁移，回退删除新增参数恢复旧行为。不能重启有活跃执行的节点。

# 2026-11-26 实测修订

100用户+100设备Worker+50任务短测：80连接候选页面1245次503；页面池10→32、总连接102后仍596次页面503，连接等待P99约2秒，不能视为达标或直接上线。增加交互角色显式副本支持（默认1、最多8），按副本计连接预算并校验总进程数，调度角色仍单副本。下一档4交互+2控制+数据/批量各1共8进程，每交互页池16，总136连接，测试PG200硬上限，仅为候选。完整保留前两档失败，不能宣称加连接解决全部问题。

资源池列表的逐卡查询是实测放大点：summary对每slot调用view读取Worker与未清理Run，百人页面刷新把此线性查询重复放大。优化只限请求内只读上下文（workers/pools/cleanup集合），并按SQL分组统计历史Job状态；不改变资源分配或迁移逻辑，不跨请求缓存。101卡一致性与查询数测试验证后，用相同80连接候选负载对照，避免将多进程或更大连接数的收益混为一谈。

百节点/百用户分路径测试页面3012请求全部200，但monitor的P99仍7.1秒；列表/资源池/详情分别约2.86/2.00/1.93秒。对大诊断树改用原生JSON编码，非原生日期等叶值保留FastAPI转换，避免完整重复Python遍历；不裁剪字段、不缓存、不改调度。需要响应等价、非有限值拒绝和相同负载复测。

最终短测：保持168连接总上限，将交互拆成8副本（每副本3/1/10池），总进程12，100用户/100节点/100Worker档通过；监控P99约0.85秒。模板`team-capacity-100.json`与env.example一致性自动检查。800Worker/100节点×8卡档失败，不能据此承诺八卡百节点同时执行业务容量；按已验证100Worker边界选择配置，保留更大候选失败和长期验收待办。诊断树只复制要修改的顶层和reasons列表，节点树在请求内只读；测试验证原缓存快照不被改变。
