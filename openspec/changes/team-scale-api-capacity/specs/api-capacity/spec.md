## ADDED Requirements

### Requirement: 独立容量预算
四角色API SHALL 分别控制HTTP准入、排队长度及等待、数据库池及连接等待。12进程百人推荐拓扑缺少显式覆盖时 SHALL 使用已验证的推荐档；显式旧四/五进程拓扑 SHALL 保持原额度行为。

#### Scenario: 页面处理名额超过数据库连接
- **WHEN** 页面HTTP准入设置为20、连接池为10
- **THEN** 可准入20个请求但最多借出10个连接，不使用溢出连接，用户操作保留独立额度

#### Scenario: 队列取消或满载
- **WHEN** 排队请求取消、超时或达到队列上限
- **THEN** 释放等待位置，超时或满载返回可重试503，不泄漏处理许可

#### Scenario: 新四角色部署缺省容量
- **WHEN** 操作者使用四角色 Compose 且未设置容量覆盖
- **THEN** 启动8交互、2控制、各1 Worker数据与批量进程，池额度合计168，批量入口队列192且最多等待2秒，PostgreSQL默认可容纳180预算和20预留

#### Scenario: 现有部署显式覆盖
- **WHEN** 操作者显式设置旧副本数、旧批量队列或其他容量值
- **THEN** 系统使用显式值，校验进程数、连接预算和PostgreSQL上限，不暗中改变运行中的部署

### Requirement: 分类总截止与配置校验
系统 SHALL 校验请求等待不超过总预算、Worker预算小于HTTP超时，并保持多进程数据库总预算检查。

#### Scenario: Web等待长于Worker
- **WHEN** 页面预算12秒而执行控制预算4秒
- **THEN** 两类使用各自截止，不延长Worker控制等待或借用控制连接

#### Scenario: 非法或漂移配置
- **WHEN** 额度非法、类别未知、总连接超限或角色配置不同
- **THEN** 拒绝非法启动或健康检查报告不一致，不静默忽略配置

### Requirement: 容量结论有验证依据
系统 SHALL 为百人团队及百节点提供混合负载验证，区分节点/设备Worker/执行数与模拟/真实业务，保留失败与未验证边界。

#### Scenario: 多卡节点候选规模
- **WHEN** 验证100节点每节点8卡
- **THEN** 按800Worker生成控制/结果/日志流量，同时包含用户页面与管理操作，不将单纯心跳通过称为整平台容量通过

#### Scenario: 数据库池对照与未知边界
- **WHEN** 评估数据库池大小与等待时间
- **THEN** 固定API拓扑和请求负载，区分准入拒绝、连接超时、锁竞争及SQL变慢，记录未测量项，不将数据库连接硬上限当作业务容量保证
