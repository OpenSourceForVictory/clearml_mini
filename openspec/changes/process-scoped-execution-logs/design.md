## Context

动机和范围见 proposal.md。当前 `runner/host_episode.py` 捕获逐回合 stdout 并转发，stderr 继承公共管道；`runner/command_sdk.py` 直接运行子进程；外层 host_supervisor/log_capture 和 DockerCollector 已失去可靠回合归属。API logs-v2 以 Run 为键，保留 256 KiB，追加锁 Run 且要求租约有效；不能用该上传接口读取终态历史文件。现有 Agent 负责监控和服务协调，不是通用文件服务。

`execution-directory-visibility` 已设计 Run/execution_id 与扫描目录展示，但尚未实施；本变更复用其组件及授权模型，并增加启动时登记的可信日志根。`ExecutionData` 是扫描/清理目录清单，不应承担实时日志分片索引。

## Goals / Non-Goals

目标：可定位、可按进程查看、可限额保留的日志；在不改变业务启动、参数、环境、设备分配和结果判定的前提下支持宿主机和容器。覆盖普通命令、直接协议、SDK 命令适配和原生 SDK。

不采集业务自行写到任意位置的日志；不把单进程并发/多回合按文本强行切分；不提供全文检索、永久归档、SSH、任意文件下载或自动重建所有业务镜像；不要求业务输出遵循新日志格式。

## Decisions

### 1. 身份、作用域与逻辑文件

唯一身份为 execution_id + scope + episode_id（仅 episode scope），另存随机 generation。Run.id 是尝试记录身份，不是 execution_id；service_instance_id 是关联元数据，不用服务名称作文件名。

| 实际启动契约 | scope | 界面名称 |
| --- | --- | --- |
| Runner/Worker 准备、回合切换、取消及清理诊断 | task | 执行诊断 |
| 一个业务进程处理整任务，包含单进程原生 SDK 多回合 | business | 任务公共日志 |
| host per_episode 或实际逐回合启动的 sdk-command | episode + N | 回合 N 日志 |
| 服务实例业务进程 | service | 服务实例日志 |

一个 scope 是一份逻辑日志，stdout/stderr 作为记录来源保存在同一文件，避免单进程用户需要找两份文件。超限后轮转为多个物理分片，界面连续查看。不得通过出现 STARTED 文本或任务类型推断 scope；runner 根据实际启动分支上报明确日志布局。

节点布局（新执行）：

```text
<execution_root>/logs/
  manifest.json
  task/log-000001.jsonl
  business/log-000001.jsonl
  episodes/000001/log-000001.jsonl
  episodes/000002/log-000001.jsonl
  service/log-000001.jsonl
```

只有使用的 scope 创建目录。实际根来自该执行存储快照，不根据最新配置重建。manifest 记录执行/槽位、布局版本、scope、generation、范围、关闭/故障标记及应用配置版本；不写完整命令、令牌或登录环境。JSONL 每条含 scope 内递增序号、采集时间、stream、text 和 gap；不承诺 stdout/stderr 的业务真实跨流先后顺序，不拼出不存在的业务时间。控制字符按纯文本显示，不渲染 HTML 或执行终端转义。

### 2. 在业务进程边界采集，统一采集基础库

Runner 负责明确进程边界与 scope。共享采集库并行排空两个管道，按字节分块、增量 UTF-8 解码，无效字节替换；超长行同样有界。stdout 原始字节先进入现有协议解析，不通过日志 JSONL 再解析 final。协议事件不受日志轮转预算影响，原有协议校验和事件上限继续有效。

节点只保留一套 scope 文件，外层采集器不要再次全量复制业务正文。执行诊断汇总仅包含启动/结束/错误与有限尾部；兼容 v2 可继续提供全执行有限摘要，但不承诺包含所有回合。原生 SDK 单进程归入 business，SDK 包装器管理诊断归 task。子进程发生异常时保留其退出码，不因日志失败合成业务 exit_code。

对 `host_episode`、`command_sdk`、`cs_entry`、`service_entry` 和宿主机/容器注入入口作统一接入测试。Docker 为新执行注入专用日志可写挂载，不放业务 output 内，避免日志误作为评测产物上传；只额外挂载该执行日志目录。实际 Runner 必须验证能力，不能只相信 Worker 版本。自带旧 Runner 的镜像明确回退整执行日志，不自动打包改写其镜像。保留 Docker daemon 原有有界日志设置作为启动故障后备，不把 `docker logs` 当逐回合来源。

管道读取与文件写入之间用固定 1 MiB 队列；队列满或写入出错时继续排空诊断输出、累计丢弃标记并保留至多 8 KiB stderr 尾部。写入单独线程，不持有 Worker 启动/租约锁；文件系统卡死标记故障并停止继续排队。无法承诺解除内核不可中断 I/O，由节点运维恢复，但不允许采集任务阻塞主控制循环。

主进程退出后最多等待管道排空 2 秒；后代仍持有管道则标记不完整并交执行进程组清理，不能把旧回合后代接入下一回合。正常结束、取消和强杀分别记录关闭原因，业务状态与日志状态独立。

### 3. 首版两级预算与配置同步

默认值作为管理员可调的首版起点，验证后可以调整，不写成业务模板硬限制：

| 设置 | 默认 | 规则 |
| --- | --- | --- |
| 分片大小 | 4 MiB | 单 scope 物理分片上限，单记录不得超过 8 KiB |
| 单 scope 保留量 | 16 MiB | 按实际磁盘字节计量，包含 JSON 转义和元数据 |
| 单执行日志保留量 | 256 MiB | 不随回合数无限乘增，包含所有 scope、索引和尾部 |
| 整机日志保留量 | 不限制 | 首版不启用整机配额协调；累计日志仍可能耗尽磁盘 |
| 采集内存队列 | 1 MiB / 活动业务进程 | 超额丢弃诊断并计数，不丢协议事件 |

分片、scope、execution 必须为有限正值且分片<=scope<=execution；node 默认为不限制。单次执行预算淘汰最早关闭 scope 的分片，再淘汰活动 scope 的最旧分片；task 诊断及错误尾部在总预算内保留小额优先空间，耗尽时仍标记丢失，不能突破硬预算。整机不做容量淘汰；沿用执行数据保留清理，不删除业务产物以腾日志额度。元数据受最大回合数和总字节预算限制，淘汰仅保留压缩的区间/统计，不为每个丢弃块无限新增标记。

首版经用户确认不实现整机额度账本或跨账号申请通道。Runner 在执行专用日志目录内协调分片、scope 和执行预算，Worker 不转发正文；不得宣称整机磁盘总量受控。

管理员在机器“数据保留”中配置，API 保存期望 revision，Worker 控制通道上报 applied_revision/error。执行记录固定启动时的 scope/执行限额；首版只允许有限分片/scope/执行预算，配置变更仅用于新执行，不实施整机降额；已有数据沿用保留清理，不阻塞请求；显示回收中及已截断状态。保留天数沿用现有执行数据策略，不新设重复的业务产物清理规则。容量淘汰只针对日志，并记录原因。

### 4. 目录/索引登记与数据模型

新增 migration（编号由实施时仓库 head 决定，不能现在编造）：

- ExecutionLogCatalog：run_id、execution_id、worker/slot、scope/episode、generation、节点已登记日志根、路径映射、布局/配置版本、状态、最早/最新序号、扫描/更新时间、truncation/dropped 信息；唯一 execution+scope+episode 的规范键（非 episode 使用固定哨兵，避免 SQL NULL 唯一约束问题）。
- LogReadRequest：用户/执行/日志代次、范围与方向、状态、claim nonce/期限、响应上限、expires_at；正文是短期有界页，不是日志归档。
- NodeLogPolicy：期望及生效 revision/配置/错误（可复用现有节点连接元数据，但不得改变并发 revision 语义）；选择现有 JSON 配置承载，无需为每个字段新建表。

日志目录创建后立即登记，无需等待磁盘全量扫描；最终关闭/清理必须更新，活动索引最多每 30 秒批量刷新，前台分页响应携带新游标。扫描是恢复和核对来源；删除/缺失状态不能被迟到旧上报复活。执行目录注册需要当前分配身份，终态历史更新只能修改既有目录/作用域状态，不允许重绑定其他路径或创建新的业务执行。

### 5. Worker 按需读取，不新增 Agent 文件服务

Worker 保存已登记执行与历史根目录的有界索引，独立读取线程负责终态文件；不依赖当前任务 state 或旧 lease，不与心跳共用阻塞调用。Agent 保持监控和服务管理职责。Worker 不运行时显示不可用，首版不承诺仅 Agent 在线仍可读取。

API 流程：

1. 浏览器请求已授权 run 的日志目录索引，选择 log_id。
2. `POST .../log-reads` 提交 log_id、opaque cursor、direction、stream filter、limit_bytes；不收绝对路径。
3. 缓存未命中时返回 202/read_id。相同权限范围、generation、游标、过滤条件可合并节点读取；每个订阅者独立鉴权，不能让另一用户轮询他人的 read_id。
4. Worker 独立短轮询领取本机读取请求（默认 5 秒，可见页面时加速至 1 秒，空闲退避至 30 秒），每次最多 2 个；API 事务只领取，不等待节点。Worker 以登记目录句柄读取一页并 POST 响应。
5. 浏览器短轮询 read_id，返回 ready/expired/offline/missing/cleaned/unsupported/failed；API 请求结束即释放数据库连接，不长事务等待或持有 Run 锁。

默认每页正文 64 KiB、整机并发 2、用户未完成请求 8、全平台活跃/缓存响应槽位 128，缓存正文总量不超过 8 MiB；请求 TTL 30 秒，超额 429 带 Retry-After。到期回收同时在准入路径惰性执行，不能依赖后台清理正常才限制总量。读请求 SQL 锁只作用于请求自身，追加缓存不能拿全局调度锁。兼容摘要沿用现有 v2 的总执行 256 KiB，不另给每个回合乘以 256 KiB。

登记路径仍视为节点输入：root 必须在执行历史白名单，逐级 openat/no-follow；拒绝绝对自选路径、..、符号链接、非普通文件、inode/manifest identity 改变。容器只能写自己的挂载；读取服务重新验证，不把业务可修改 manifest 当授权依据。API 对每次索引、页和下载检查用户权限，Worker 身份必须与登记节点匹配，claim nonce 阻止重放/串页；旧执行结果不因读请求恢复活跃。不能把 token、完整环境或未脱敏异常写入管理日志。

### 6. 游标、下载、离线和清理

游标由 log_id+generation+分片代次+record sequence 绑定，不使用裸文件 offset 作为跨轮转身份。向前/向后分页都返回 first_available/next/has_more、collected_at、source、closed、gap 与 truncation reason。stream 筛选仍推进底层记录游标，避免空页循环。超长文本块可以分段显示，但不重复拼接 UTF-8 边界。

下载只针对一份 scope 的“保留日志”，不支持一次打包全部历史任务。开始冻结最高序号及索引版本，顺序分页、浏览器流式写出；不支持流式保存的浏览器提供最大 8 MiB 的分片下载，不在内存聚合 256 MiB。记录下载范围与缺口，源在读取期间消失则标为不完整或终止，不能报完整成功。不永久 pin 日志、不为慢下载阻止配额轮转。

单页读取与执行数据清理使用同一执行级短锁，最多 2 秒，读取有界页到内存后释放再上传；锁冲突返回可重试。轮转与单页读取协调保护打开的分片，清理可以在页间生效。既有清理移动到 staging 时索引置清理中，后续读取不再跟随旧路径；已经返回的有限页是历史快照。任务/批次删除先关闭读取并删除短期缓存，再按现有外键顺序处理索引；迟到 Worker 响应不得重建已删除任务。

节点离线时返回带 source=platform_cache 的已有有限页或 v2 全执行摘要；不能把公共摘要冒充该回合日志。节点恢复后使用原代次续读，重启产生新代次时显式换代/缺口，不重复启动业务。未完成日志最后上报为开放，不能仅凭任务终态就假称日志完整。

### 7. 界面设计

具体交互见 ui.md。复用 execution-directory-visibility 的身份/复制展示；两个变更共同使用一个组件，不在本提案修改其已提交计划。日志目录来自 catalog，旧执行目录仍来自扫描，两种来源显示清楚。

任务详情“任务公共日志”在单进程模式展示 business；逐回合模式展示回合列表和独立“执行诊断”。每回合新进程提供“查看回合日志”；单进程回合行提供“查看公共日志”。服务实例行提供“查看实例日志”。打开统一右侧抽屉，关闭就停止轮询；显示节点/卡、执行 ID、scope、实际路径、采集/缓存时间、数据来源及截断/清理状态。

旧任务/旧能力只有原公共日志入口，不展示空的回合日志；启动失败但未产生业务进程时引导执行诊断。任务与结果的两套统计保持现有语义，日志状态作为第三种诊断状态，不覆盖业务结果。

## Risks / Trade-offs

- [离线历史完整日志不可用] → 有限平台摘要和明确来源，永久归档留作独立需求，不假装数据库保存全文。
- [大量回合导致旧日志淘汰] → 执行总限额及淘汰区间可见，回合结果独立保留。
- [日志可包含业务秘密] → 沿用任务可见性，不主动打印环境；不承诺任意业务正文自动脱敏。
- [NFS 慢写/不可中断 I/O] → 有界队列、控制线程隔离，验证退化行为；不承诺解除内核阻塞。
- [Docker 和多层包装重复采集] → 作用域显式握手，单一正文来源，兼容外层仅摘要；测试协议事件恰好一次。
- [连接池再次受压] → 异步短请求、硬并发/字节预算、无等待节点事务；使用受限连接池压测作为必需验收。
- [原 SDK 任意自行启动后台程序] → 不能可靠拆分的仍按 business 公共日志，不基于猜测改归属。

## Migration Plan

1. 先完成关联设计的执行身份/目录组件和本变更测试；新增表迁移在专用 PostgreSQL 验证升级、保留旧日志和回滚边界。
2. 备份，先更新迁移和 API/前端，feature 默认关闭；老 Worker 继续 v2。
3. Worker/Runner 新增 `process_logs_v1` 能力，按执行固定协商版本。先排空并升级明确选择的宿主机/容器测试节点，不因 API 更新自动全量升级。实际 Runner 缺能力回退并说明。
4. 真机验证后启用新执行；活动执行保留旧格式。新日志路径不改用户 work/output/cwd。仅更新 API 无法获得新节点文件；Runner 自带于业务镜像且不能由适配器注入时需要重建相应镜像。
5. 回退先停止新能力准入并等待活动执行结束，保留新增表和节点日志；旧 API 只读公共缓存，不保证读取新分 scope 文件。降级表会删除索引/临时页，必须单独备份确认，不把降级作为默认回滚。

设计完成不等于实施或上线；验收矩阵见 validation.md。

## 待决设计缺口：普通业务账号与整机配额通道

记录日期：2026-11-19。用户明确要求先保留当前设计、讨论配额通道，随后要求先记录缺口。本节仅记录问题和备选方案，不构成方案批准，不修改前述 Runner 采集/落盘及 Worker 私有配额账本的职责约定。

**缺口**：Runner 可能以已批准的普通业务账号运行，无法直接访问 Worker 私有目录中的整机配额账本。原设计说明了短锁和额度预留，但没有定义跨账号申请、授权、回收通道；同一节点多个卡的 Worker 还必须共享唯一的节点预算，不能各自重复分配整机额度。不能简单放开私有目录权限解决。

**讨论过的备选方案（均未选定）**：

- Runner 采集正文，经受限本机通道交给 Worker 统一落盘、核算配额。该方案改变落盘职责，用户没有批准采用。
- 保留 Runner 直接写日志，仅通过本机 Unix socket 向配额协调端申请有限额度；正文不经过 Worker。按实际写入字节消耗额度，预留计入整机总量，崩溃后核对文件再释放未用额度。这是讨论建议，尚未确定实现方式。

**后续需要确认**：协调端由谁承载及多 Worker 如何共用；宿主机业务账号、容器 UID 和专用 socket 挂载的授权方式；执行/scope/代次绑定和请求幂等；额度分块大小、实际字节核对、崩溃与重启恢复；轮转/清理与额度回收竞态。通道失联或额度耗尽时必须保持有界排空，标记日志缺口，不阻塞业务管道或改写退出码。平台采集日志配额不等同于业务账号任意写文件的文件系统配额。

待选定通道后补充测试：普通账号可申请但不能读写私有账本、跨执行越权拒绝、容器连通与权限失败、多 Worker 并发不超分、重复申请/回包、崩溃预留回收、通道中断和额度耗尽时业务继续运行。这些是待补充的验收项，未实施、未测试。

## 不依赖配额通道的实施边界（2026-11-19）

用户随后授权继续不依赖通道的部分。本阶段只提交独立编码、队列和分页读取模块及测试，不改变 Runner 落盘职责，不选择上述任一配额通道。队列累计丢弃字节与故障，保留记录的序号跳跃由读取器标记 gap；不将日志丢失转成业务退出异常。生产采集器仍需将这些状态写入原子索引与关闭登记，尚未接入。

读取器要求调用方提供可信历史目录身份与分片索引，并在最终接线时协调清理短锁。内部页最小 16 KiB、最大 64 KiB，以容纳完整的最大记录及元数据；开发中的 API 请求预算需在接线时统一适配。内部文件游标增加分片 inode 和 byte offset 作为定位信息，执行/scope/generation/序号仍绑定，不能把旧三字段逻辑游标直接用于文件读取。文件同 inode 原地篡改不是内容认证，本阶段不承诺校验任意业务正文真实性；索引授权不得来自业务侧 manifest。2 秒是循环检查和线程 join 的限期，不是解除内核阻塞 I/O 的保证。

## 已确认首版范围（取代此前配额待决阻塞）

用户确认先默认不限制整机日志总量，保留分片、scope、单执行及内存/分页限额。因此跨账号整机配额通道延期且不再阻塞首版。Runner 继续在单执行日志挂载内写文件，执行内短锁及总预算由同一执行目录管理，普通业务账号无需访问 Worker 私有目录。相关旧备选讨论仅为历史记录。首版累计磁盘占用无整机上限；磁盘故障标记缺口，业务结果不变。

## 轮转提交失败的恢复补充（0.21.7）

故障测试发现先删除分片再提交索引会破坏历史可读性。执行锁内先持久化 prune.json（执行身份、代次、限定 scope 内待删除文件及 inode），再提交 manifest；提交后只清理 manifest 已不引用的文件，最后移除意图。恢复根据已提交 manifest 判断保留或删除，禁止按任意路径和被替换 inode 清理。Writer 和 Worker 历史索引同步共用恢复实现。实际进程退出覆盖提交前、提交后、删除后三个位置；不将其表述为断电一致性证明。
