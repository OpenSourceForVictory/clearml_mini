# Proposal

## Why

当前集合运行、服务部署和推理地址分配分散在不同页面，用户需要手动部署服务并复制地址，平台无法完整追踪批次与服务的依赖关系。需要统一任务提交向导，将集合、客户端、服务端、资源和运行关系作为一次可恢复的提交管理。

## What Changes

- 扩展现有集合运行向导，支持选择已有集合或创建可复用集合，选择客户端模板、配置业务参数和资源申请。
- 支持外部推理地址列表或根据服务端模板创建平台管理的服务实例；宿主机与Docker均沿用运行模板的执行方式。
- 单独配置服务地址的独占/共享访问语义，不与GPU独占/共享混淆；不引入推理服务池。
- 平台维护批次、服务实例、客户端任务和执行尝试的对应关系；服务健康后才允许关联客户端领取任务。
- 原子创建集合、批次和所需服务，提供幂等提交、无副作用预检、权限检查、进度与失败诊断。
- 提供批次结束后自动停止或保留服务选项，正确处理取消、暂停、重试、服务失败以及节点失联后的清理。
- 统一集合、客户端和服务端的类型化参数契约，区分平台注入、业务配置、运行配置和资源申请；支持显式服务引用及参数来源预览。
- 提供普通命令、统一JSON输入和可选SDK接入；普通批处理无需推理地址或伪造评测结果，逐回合协议作为增强能力。
- 默认由平台选择托管服务节点、分配端口、等待健康并注入客户端地址；用户仅声明业务、资源需求及期望并发，节点固定和参数映射属于高级配置或模板作者职责。
- 集合、客户端模板和服务端模板支持复制成新草稿并修改参数、另存新版本；向导内支持复制编辑，已提交执行快照不受后续编辑影响。

## Capabilities

### New Capabilities
- `evaluation-orchestration`: 统一评测提交、服务依赖、执行绑定及关联服务生命周期。

### Modified Capabilities
无。保留现有批次和单独服务部署API；本变更增加编排入口并复用现有资源账本及端点互斥规则。主规范platform中的早期ClearML投递描述不作为新编排实现依据，现有数据库调度器和Worker执行协议为实际实现基础。

## Impact

- 前端：`run-wizard.tsx`、集合选择/创建、服务配置组件、批次详情与监控。
- API：新增编排预检与提交、可用服务模板与目标节点查询，以及归属明确的关联服务查询/控制。
- 数据：持久化编排定义、请求摘要、服务依赖和每次客户端执行的服务绑定，提供数据库升级与兼容测试。
- 调度：服务健康门槛、领取时再检查、现有端点占用和资源配额协同；调度器内禁止网络探测。
- 执行：复用宿主机/Docker服务入口与客户端入口，Worker只接收平台已解析的服务地址，不自行选择服务。
- 测试：提交原子性、幂等与权限、状态机与故障、资源竞争、前端交互、数据库并发及真实两端最小协议验收。
