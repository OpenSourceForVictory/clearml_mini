# Design

## Context

见 proposal.md。host_episode.py 在子进程退出 0 后检查 final 数量和类型，sdk.py 将所有异常转为同一 error 字符串。episode_contract.py 已允许 ERROR 携带 error 和 exit_code；backend/app/episodes.py 原样保存 result JSON。frontend/src/cs.tsx 把 ERROR 统一显示为执行异常。

现场证据：三个回合触发 `direct protocol episode must emit exactly one final result`，最终出现 `CS client startup failed: 3 of 3 business episodes had execution errors; remaining episodes were attempted`。该证据只能证明结果数量或结构不合法，无法区分缺失与重复。

## Goals / Non-Goals

目标：让既有协议错误成为受控、可操作的诊断，准确显示子进程退出状态。
不自动修补业务 final、不将业务异常降级为成功，不更改调度、回合数或容器执行机制。

## Decisions

1. 使用内部专用结果校验异常，错误码/文案仅来自固定白名单。区分 missing、multiple、invalid；SDK 对此类错误生成安全 error 文本并受控记录 stderr；未知异常继续通用脱敏消息和堆栈。不能直接将任意异常 str 写入平台事件。
2. 复用 ERROR.error 和 exit_code，不增加事件字段及数据库列，以兼容已部署的事件校验器。UI 用固定诊断标识匹配解释；旧通用 ERROR 不推断原因。
3. 程序退出状态只来自回合 exit_code；退出 0 为正常结束，非零异常退出，缺失未上报；原生 SDK 回合不对应独立进程时显示不适用。协议结果列对已知校验错误显示结果校验失败，对有效 COMPLETED 保持业务结果。新增两个独立汇总：程序执行统计（正常结束、异常退出、运行中、退出码未上报）与平台协议回合结果统计（业务成功、业务失败、结果校验异常、结果未上报）。以同一执行尝试的全部回合为统计范围，不能仅统计当前分页。未启动回合保留待执行/未执行信息，不算程序失败；已终止但没有退出码不能算运行中。普通命令的协议结果统计不适用。旧进度字段保持兼容，新增汇总由后端同一份回合记录计算并测试分页一致性。三次 exit_code=0 + 协议错误应得到程序正常结束 3 次、协议结果校验异常 3 回合。有效协议 success=false 属于业务失败，不属于协议校验异常。
4. 检查 runner 客户端入口的外层异常包装，使用能涵盖启动、运行与结果处理的中性文案；避免已完成回合被显示为只在启动时失败。
5. 不读取结果文件替代 stdout，SDK 包装命令仍读取 MINI_EVAL_RESULT 并分类文件缺失/无效错误；直接协议不接受日志前缀 JSON，不选择重复 final 中任意一条。上述替代方案会悄悄改变协议且掩盖业务问题。

## 批次结果页面

- 批次详情顶部并列两块：「程序执行」展示正常结束、异常退出、运行中、退出码未上报；「回合结果（平台协议）」展示业务成功、业务失败、结果校验异常、结果未上报。生命周期（排队、取消、超时、清理）仍单独保留，不能代替任一结果。
- 任务列表独立两列，同样区分程序执行与协议结果；逐回合详情显示明确退出码、结果状态及安全诊断。批次列表使用相同口径的简要汇总，不再用一个“成功”暗指两种结果。
- 批次只聚合各任务最新尝试的全部记录，与任务筛选、分页无关；历史尝试在详情中单独展示且不重复计数。普通命令不加入协议结果分母，混合批次标明不适用任务数。
- 程序执行以业务进程启动次数为单位：每回合启动的模板每个子进程计一次，一次启动跑多回合的模板只计一次，不把同一个退出码复制到每回合。UI 明确标注“次”和“回合”；只有包装器退出码而无业务进程退出证据时不推断业务异常退出。保留整次执行退出码作为单独诊断。
- 正常退出 3 次但协议校验异常 3 回合：两块分别呈现上述数字；原有 FAILED 生命周期不被改成 SUCCEEDED，展示“任务结束，结果异常”解释原因，不将其计为程序异常退出。
- 协议成功率仍按有效已完成协议回合加权，异常和未上报独立展示，不把它们当业务失败或当成功；普通命令不进入该分母。无有效结果时显示暂无数据。
- 后端提供批次与任务的两组汇总，复用同一分类函数，避免 UI 按分页数据自行累计。补跑资格及调度状态不随文案改动。

## Risks / Trade-offs

- 老 Worker 仍报通用错误 → 保留历史显示和未分类提示，不声称旧数据可恢复精确原因。
- 日志含敏感数据 → UI 仅显示受控诊断，不把业务 stdout 原文放入 error。
- 普通命令与 SDK 行为回归 → 测试正常、非零、未知异常、停止/继续策略和 Docker 路径。
- 文本诊断标识形成契约 → 固定标识并测试跨 Runner/API/UI 传递，暂不扩展事件协议。

## 审查后确认的边界

用户已确认两套统计扩展到报告、CSV 和批次比较，修复普通命令 null 成功率相减的 TypeError。复用 `outcomes` 分类函数，旧 summary/progress 字段兼容保留；新 UI 和报告新字段使用统一口径。Runner 新诊断放在既有 episode_contract 模块以兼容 SDK 打包清单。

原生 SDK 回合没有独立业务子进程，回合退出码不适用；单进程旧记录仅有包装器非零退出码时保持未知，不冒充业务退出。单进程外层正常退出可证明同步业务进程正常返回；非零不能区分初始化、业务、结果和 teardown 失败，不从错误文本猜测。回合业务退出码已知的情况使用实际记录。

## Migration Plan

无数据库迁移或协议字段变更。实施后更新平台界面与实际运行节点 Worker/Runner；容器使用打包 Runner 的场景按现有镜像更新流程处理。本变更不授权现场部署；发布时检查实际产物版本。回退可使用原 Runner/UI，历史 ERROR 数据仍可读取。

## 2026-11-19 已确认补充：整任务普通命令展示

用户确认整任务启动、未接协议的普通命令只显示一条执行记录，不显示计划回合表及回合翻页；配置中的总回合数保留，不改变实际传参。按任务模板快照的 task_type 与实际进程模式判断，不只依赖 episode_reporting。SDK 命令适配仍属于逐回合进程，协议单进程仍展示回合结果。

普通命令整任务的执行统计使用平台执行退出码，非零计执行异常（包括包装器启动错误，不声称是业务子进程退出）；生命周期保留启动失败、超时、取消和未知状态，缺少退出码不算正常。协议任务继续保持包装器退出码与业务退出码的区别。API 新增展示模式，整任务普通命令不补造计划回合；历史记录保留数据库，不修改事件或结果。任务详情和批次入口一致。无数据库迁移、不修改 Worker/Runner、不部署，日志配额缺口继续待决。
