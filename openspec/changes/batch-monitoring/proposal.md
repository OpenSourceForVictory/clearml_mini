# Proposal

## Why

运行向导已解决提交前检查，但提交后仍只有长列表和逐任务详情，用户难以定位批次卡在哪里、哪些回合已完成以及哪些失败需要补跑。需要统一批次监控入口和持续更新的等待解释，补齐提交后的使用流程。

## What Changes

- 将运行批次列表整理为摘要和详情入口，提供可直接打开、刷新恢复的批次详情视图。
- 按已提交任务快照只读计算等待原因，补充批次并发、停用资源池和等待调度轮转等情况；展示更新时间、原因和建议操作，不承诺排位或预计开始时间。
- 汇总任务状态和最新尝试的回合进度、目标成功率、执行异常、未上报任务数量；按任务名、状态及等待原因筛选。
- 在同一详情视图查看任务尝试、日志、回合结果和产物，保留现有权限校验及分页接口。
- 对选中的 FAILED/TIMED_OUT 任务批量重试，明确每项成功或跳过原因；沿用清理与配额限制，用预期尝试标识防止并发重复重试。
- 本阶段不做跨批次对比、精确等待时间、优先级调整、自动重试策略或推理服务配置库。

## Capabilities

### New Capabilities

- `evaluation-monitoring`: 已提交评测批次的等待诊断、进度汇总、任务排查与显式批量补跑。

### Modified Capabilities

无。保持现有任务状态机、逐回合协议、预检与单任务重试契约。

## Impact

涉及 backend/app/batches.py、preflight.py、scheduling.py、main.py 的重试逻辑和 frontend/src/cs.tsx；新增批次监控与批量重试接口、前端详情组件、中文文档和回归测试。复用现有 PostgreSQL 数据，无计划中的结构迁移或 Worker 协议升级。主规格尚有早期 ClearML 投递描述，本变更沿用实际 PostgreSQL/Docker 执行架构，不恢复旧投递实现。
