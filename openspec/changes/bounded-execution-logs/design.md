# Design

## Context
worker/host_supervisor.py 当前将 stdout/stderr 各截到最前 256 KiB；host_backend.logs 先 read_bytes 后切片；client.send_logs 每次最多 4 个 2048 字符请求，与心跳串行。Docker 两次 logs 调用重复读取保留输出。API logs 获取全局调度锁，用 count(rows) 校验序号，累计 256 KiB 后拒绝追加。客户端界面按游标轮询，服务日志每次读取全量。

## Goals / Non-Goals
目标：输出与请求量有界，最新错误持续可见，日志慢请求不影响租约；宿主机和 Docker、普通命令和协议模式均验证。
不提供无限日志归档、全文搜索或跨输出流严格时间排序；不改变模型成功率或任务总时限。

## Decisions
1. 新增可协商日志 v2。节点日志采用固定大小分段环形文件，默认单执行最多 4 MiB（含 stdout/stderr），按字节逻辑偏移、流标识、采集代次定位；UTF-8 增量解码，不依赖字符数作字节游标。滚动覆盖和重启采集缺口显式记录。宿主机 supervisor 持续排空管道；Docker 使用独立可停止的 logs 跟随采集器，初次/恢复读取限制尾部大小，对无法无缝恢复的区间标识缺口，不宣称 exactly-once 原始输出。
2. 结果与回合事件独立持久化。宿主机 final.json 与事件 journal 保留；Docker Runner 将协议事件及最终记录写到平台已有输出挂载中的专用有界文件，保持旧 stdout 协议输出兼容。没有新 Runner 的旧容器继续走旧日志链路。普通命令仍依据退出码；不能因尾部没有 final 就覆盖独立结果。
3. 每个执行一个日志发送器，独立于控制心跳线程；每次最多 16 KiB、至多每 2 秒一个请求，无新数据不发送，失败指数退避至 30 秒。日志 journal 与执行 journal 分离，固定 pending 内容先落盘再发送；控制路径不等待日志发送器网络返回。结束时最多 5 秒补传，未传完标识尾部缺口，结果与清理不能无限等待日志。取消后可停止采集，关闭后拒绝新写入。
4. v2 使用独立日志状态/块表，保存 next_sequence、first_sequence、保留字节数与最后一次 ACK 摘要。平台窗口默认 256 KiB，追加后淘汰旧块；不再用行数推断下个序号。每次最多一个批量事务，日志事务不更新 Run.log_bytes。接受当前 pending 重传；更旧序号只能确认已持久接受并返回 resync，不能用已淘汰正文冒充内容一致性校验。
5. PostgreSQL 上传先锁所属 Run 行，再锁日志状态行；完成/批次删除在更改或删除 Run 前遵循相同顺序。日志路径不获取全局调度锁；带全局调度锁的控制路径只按 global→Run→日志状态顺序取锁，不反向获取，避免死锁。持锁后重新核验 worker/执行生命周期。用实际 PostgreSQL 并发测试证明删除、结束、迟到上传与重试一致性。旧接口兼容保留，后续旧 Worker 退役后再清理。
6. 新读接口返回 first/next 游标、chunks 和 gap/truncated，按 run/attempt 授权。前端两面板共享读取逻辑，打开后每 2 秒增量读取、失败退避，终态读尽后停止；本地展示保留 256 KiB。历史 v1 只读适配，不重写旧日志。

## Risks / Trade-offs
- 快速输出超过限速 → 环形淘汰并展示缺口，保证最新内容，不承诺完整历史。
- Docker 采集断线 → 新代次和缺口记录，禁止静默拼接；日志可缺失但业务结果不能依赖其完整性。
- 并发删除/完成 → 固定锁顺序与 PostgreSQL 竞态测试；新表纳入批次删除顺序。
- 线程共享状态 → 独立日志状态文件和 API 客户端，禁止无锁并发修改执行 journal。
- 长时间日志保留 → 单执行窗口有界，全部任务累计容量仍依赖既有数据保留策略。

## Migration Plan
新增日志状态/块表与迁移测试；API 先发布，旧接口继续可用，Worker/Runner 按能力选择 v2。已有正在执行的 journal 固定旧模式，不在执行中切换。先在实验平台验证宿主机/容器高输出程序，再升级选定节点。回退 Worker 需待 v2 执行清理完成；API 回退前停止 v2 新执行且保留新增表，不自动删除 v2 历史。
